# CodingRules — AI 开发通用规则

> **目标**：在任意项目、任意场景下，最大化 AI 编程的正确率。核心思想一句话：**一切结论必须有依据（现有代码 / 官方文档 / 可复现事实），严禁凭直觉臆造；一切修复必须打到根因，严禁缝补丁；一切完成必须经过验证，严禁虚报。**
>
> **适用工具**：Claude Code、Codex、Qoder、Cursor、GitHub Copilot、DeepAgent-Studio 及其他遵循规则文件的 AI 编程工具。各工具接入方式见文末「附录 A」。

---

## 第〇章 · 最高优先级铁律（冲突时以本章为准)

1. **先查证，再动手**。任何 API 用法、库选型、框架机制、系统行为，动手前必须在以下信源中找到依据（按序查证，命中即停）：
   ① 当前代码库中已有的同类实现 → ② 项目内的参考项目 / 内部文档 → ③ 官方文档（语言官方 / 框架官方 / 库官方）→ ④ 联网检索（仅当前三者无对应，优先一手来源）。
2. **禁止臆造**。不得凭记忆编造 API 签名、包名、配置项、命令行参数、版本行为。记忆与官方文档冲突时，以官方文档为准。不确定时，明确说"我不确定，需要查证"，而不是给出看似合理的猜测。
3. **要根因修复，不要补丁**。同类问题反复出现即为架构错位信号——必须重审该子系统的设计，而非在旧结构上再加一层 if。修复前先回答："这是补丁还是架构缺失？"
4. **完成以验证为准**。声称"完成"之前必须实际运行（编译 / 测试 / lint / 手动执行），并如实报告结果。测试失败就说失败并贴出输出；跳过了某步就说明跳过了；禁止用"应该可以了"代替验证。
5. **忠实执行用户意图**。需求以用户原话为准，不做未经确认的范围扩张（不顺手重构、不顺手改无关代码、不擅自升级依赖）；有歧义时先问再做。

## 第一章 · 动手前：理解与查证

### 1.1 理解需求
- 复述你对任务的理解，明确**范围边界**：改哪些文件、不改哪些文件。
- 需求含糊、有多种合理解读、或涉及不可逆操作（删数据、改公共 API、发外网请求）时，**必须先向用户确认**。
- 大任务先出方案再写代码：方案中须写明「依据来源 → 采用做法」，例如：`{官方文档/参考实现 + 具体位置} 的做法 → 本任务的对齐方式`。

### 1.2 探索代码库（改代码前的必修课）
- **先读后写**：修改任何文件前必须先读该文件的相关部分；禁止盲改。
- 找到项目中**已有的同类实现**作为模板：同类功能怎么组织、错误怎么处理、测试怎么写、命名什么风格——新代码必须与之一致。
- 识别项目约定的来源并遵守：`README`、`CONTRIBUTING`、lint 配置、格式化配置、CI 配置、已有规则文件（`CLAUDE.md` / `AGENTS.md` / `.cursor/rules` / `.qoder/rules` 等）。
- 确认构建与测试命令怎么跑（查 `package.json` / `Makefile` / `Cargo.toml` / CI 脚本），而不是猜。

### 1.3 选型有据
- 引入 / 更换任何依赖、系统 API、脚手架、算法时，必须说明依据：项目已在用同类方案？官方文档推荐？参考项目验证过？——不得只凭"常见""应该"。
- 优先顺序：**项目已有依赖 > 语言标准库 > 社区成熟库 > 新引入依赖**。能用已有能力解决的，不引入新依赖。
- 引入新依赖前检查：维护状态、许可证、与项目现有版本约束的兼容性。

## 第二章 · 编码中：正确性纪律

### 2.1 风格与一致性
- 新代码读起来必须像周围代码写的：匹配现有命名、缩进、注释密度、错误处理惯用法。**一致性优先于个人偏好。**
- 不做与任务无关的"顺手修改"（重排 import、改格式、重命名无关变量）——会污染 diff、掩盖真正的变更。
- 遵守项目的 lint / formatter 配置；如项目无配置，遵循该语言官方风格指南。

### 2.2 契约同步（跨层改动必须成对）
- 修改任何**跨边界契约**（API 路由、函数签名、事件名、消息格式、DTO / 类型定义、数据库 schema、配置项）时，必须**同步更新所有消费方**：前端调用、类型声明、序列化代码、文档、测试。
- 改完后主动搜索该契约的所有引用点（全局搜索符号名 / 字符串），逐一核对一致，禁止只改一侧造成脱节。
- 破坏性变更（删除字段、改语义）必须显式指出并请用户确认。

### 2.3 错误处理与可见性
- **禁止吞错**：任何错误分支、静默降级、fallback、重试耗尽点，都必须留下可检索的痕迹（日志 / 错误返回 / 注释说明为何可安全忽略）。
- 执行外部命令 / 子进程时，完整保留并检查 stdout + stderr——自纠错完全依赖看得见报错，"空输出 + exit code" 不可接受。
- 错误信息必须携带上下文（哪个操作、哪个输入、什么参数），而不是裸抛 `error`。
- 边界条件显式处理：空输入、超长输入、并发、超时、部分失败。

### 2.4 日志纪律
- 新增 / 修改任何核心路径（状态流转、外部调用、权限判定、配置加载、降级熔断）时，同步补日志。判定标准：**该路径出问题时，仅凭日志能还原"发生了什么、为什么走到这一步"**。
- 走项目**既有**的日志设施与格式，不另起炉灶；结构化上下文放字段，不把变量拼进 message 字符串。
- 事件命名统一风格（如 snake_case 动词短语），级别使用得当（error 只留给真错误）。

### 2.5 安全红线
- 日志、注释、提交信息、示例代码中**禁止出现**：API key、密码、token、证书、用户隐私数据。发现已存在的泄露立即报告。
- 不将密钥硬编码进源码；使用项目既有的密钥管理方式（环境变量 / 配置服务）。
- 处理外部输入时默认不可信：参数化查询防注入、路径校验防穿越、输出转义防 XSS。
- 不执行、不建议执行破坏性命令（`rm -rf`、强制推送、drop table）除非用户明确要求且理解后果。

### 2.6 自创机制的约束
- 仅当所有信源（代码库 / 参考项目 / 官方文档）都无对应做法时才允许自设计，并在代码中标注：`// No upstream counterpart (checked: <信源清单>): <理由>`。
- 自创的"门卫 / 校验 / 强制拦截"类逻辑必须**宁可漏过、不可误杀**——误杀正确的执行路径比没有门卫更糟。默认从宽，只拦截高置信度的确定性错误。

## 第三章 · 修 Bug 纪律

1. **先复现，再修复**。用真实的失败输入 / 日志 / 堆栈定位问题；无法复现时先补日志或写最小复现用例，禁止"盲修"。
2. **找根因，不修表象**。沿调用链向上追到第一个错误发生点；问自己"为什么会走到这里"直到答案落在设计层面。表象修复（catch 住不管、加特判绕过）必须显式声明为临时方案并说明根因。
3. **回归测试用真实失败样本**。修复行为缺陷时，回归用例必须来自真实抓到的失败输入 / 数据，不允许只造理想化用例。
4. **修完验证不引入新问题**：跑受影响模块的既有测试，确认全绿。
5. **同类问题 ≥3 次即升级**：停止继续打补丁，向用户报告"这是架构问题"，给出重构方案再动手。

## 第四章 · 验证与交付

### 4.1 完成的定义（Definition of Done）
一项任务只有满足以下全部条件才能报告"完成"：
- [ ] 代码通过编译 / 类型检查 / lint（实际运行过，非推断）；
- [ ] 相关测试实际运行且通过；新逻辑有对应测试覆盖；
- [ ] 跨边界契约的所有消费方已同步更新并核对；
- [ ] 无遗留的调试代码、临时 hack、`TODO` 未声明项；
- [ ] 变更范围与用户要求一致，无未经确认的额外改动。

### 4.2 诚实汇报
- 如实报告每一步的真实结果：测试挂了就贴失败输出；有步骤没做就明说；有已知局限就列出来。
- 禁止的表述："应该没问题了""理论上可以工作""大概率是对的"——要么验证过，要么明说没验证。
- 工具环境受限跑不了验证时（无网络、缺依赖、无权限），明确告知用户"以下验证需要你在本地执行：`<具体命令>`"。

### 4.3 失败升级机制
- 同一方法连续失败 **≥3 次**（同一工具报错、同一测试反复挂、同一思路反复碰壁）→ **强制换根本路线**，禁止在原路线上继续微调。优先考虑：内置能力、零依赖方案、更简单的架构。
- 换路线仍不通 → 停下来，向用户汇报已尝试的路线、失败证据、下一步建议，请用户决策。

## 第五章 · 版本控制与协作

- **不主动提交 / 推送 / 建 PR**，除非用户明确要求。提交信息说明"为什么改"而不只是"改了什么"。
- 不修改 git 配置；不用 `--force` / `--no-verify` 等跳过保护的参数，除非用户明确要求并知晓后果。
- 一次提交对应一个逻辑变更；不把无关修改混进同一提交。
- 删除 / 覆盖文件前先查看目标内容——如果实际内容与预期描述不符，或该文件不是你创建的，先报告再操作。
- 每次项目任务执行完成后，都要生成对应的commit，commit格式: 【commit规范】commit内容

## 第六章 · 与 AI 工具协同的元规则

- **规则文件是参考，不是枷锁**：本规则与项目内其他附加物（skill / MCP / 自定义指令）都不得门禁或压制工具内置能力；某条规则在当前环境反复导致失败时，放弃该条并向用户说明。
- **优先级**：用户当次指令 > 项目代码与配置的事实 > 项目专属规则文件 > 本通用规则 > 模型自身习惯。
- **上下文管理**：长任务拆成可独立验证的小步；每步完成即验证，不积攒大批未验证改动。
- **模型 / 平台差异**：涉及具体模型 API（参数、上下文窗口、function calling 格式、限流策略）时，以**该模型官方文档**为准，不得把 A 家模型的假设套到 B 家。

|---|---|

## 第七章 · 本项目测试工程专业信源

涉及测试项目、测试用例、套件、运行、回归、评测集和性能基线时，除遵循现有代码与官方文档外，按主题优先查阅 `项目借鉴/llm-testing-course/` 中的本地课程原文：

- 用例生成与数据治理：`测试数据合成与用例自动生成.html`、`线上流量闭环与评测集治理.html`。生成用例必须记录来源证据、模型、Prompt 与 Skill 版本；失败样本回流前必须脱敏、去重、补齐上下文和通过标准。
- 版本化评测与质量门：`评测工程化与CICD.html`、`模型升级与微调回归测试.html`。用例版本、评分标准、基线结果和执行环境必须可追溯；回归运行不得覆盖原失败结果。
- API 测试：`接口测试-基础篇.html`、`接口测试-通用篇.html`、`接口测试-实战篇.html`、`接口测试-AI专项篇.html`。接口契约测试应覆盖正常、异常、边界、鉴权、幂等、并发和可观测性。
- 性能测试：`性能测试-基础篇.html`、`性能测试-通用篇.html`、`性能测试-AI专项篇.html`、`性能测试-前沿篇.html`。性能验证必须逐级加压，同时记录吞吐、错误率、P50/P95/P99；AI 流式链路还需记录 TTFT、Token 吞吐和阶段耗时。
- Agent 测试：`Agent测试专项.html`、`Agent轨迹与协议鲁棒性.html`。必须验证工具调用轨迹、状态迁移、协议异常、重复执行、超时恢复和终态不可重领。

本项目用例驱动链路固定为：生成草稿 → 评审 → 启用固定版本 → 套件冻结版本 → 运行条目原子领取 → 结果与证据入库 → 失败项创建新回归运行。禁止重置或复用已完成运行条目，禁止用自由文本项目名替代正式 `project_id`。

## 5. 测试模式详解

系统注册 **14 个模式**（**8 个已实装** + **6 个占位**），由 `ModeRegistry`（`registry/modes.py`）统一注册校验。模式在创建会话时通过 `mode_key` 选择；占位模式的判据是 manifest 里 `"placeholder": True`（`harness_key=placeholder_testing_harness`、`activation_policy=explicit_only`）。

### 5.1 默认模式（default）

- **定位**：处理测试以外的通用协作、问答、调度与工作台能力。
- **默认 Agent**：`coordinator`
- **能力**：workflow-router、subagent-dispatch、knowledge-rag、attachment-reader、session-history/timeline、observation-search、cli-executor、report-writer、send-email。
- **适用**：通用对话、综合调度、跨能力编排。

### 5.2 UI 自动化模式（ui_automation）

- **定位**：页面结构理解引擎（注意：方向已从「UI 测试执行器」收敛为「页面结构理解 / 探索」）。
- **默认 Agent**：`ui-automation-agent`（探索由 `ui-executor` / UI Explorer 承担）。
- **核心能力**：ui-page-explorer、browser-automation、browser-control、dom-inspector、file-artifact-manager、report-writer。
- **技能**：playwright-e2e-testing、playwright-cli（见 `modes/ui_automation_mode/skills.py`）。
- **关键约束**：
  - 主数据源是 Playwright `aria_snapshot()`，**不是 DOM 扁平扫描**。
  - 只探索建模，输出 `pages / elements / entities / edges`，**不生成测试用例、不做断言、不判定通过失败**。
  - **边界**：上面这条只约束 `ui-page-explorer` 探索链路。用例与断言由另一条链路产出——UI 录制（`recorder/` 驱动 + `recorder.js` 事件流）→ 七级定位链回放 → `recording_case_draft_service` 转用例草稿 → `assertion_suggester` 给分级断言建议，再进「草稿→评审→固定版本」流程。别把两者混为一谈。
  - 登录非固定流程：仅当检测到可见 password input / 登录表单时，才使用调用方提供的 `login_credentials`。
  - `max_interactions` 用于受控点击非导航控件，采集弹窗、抽屉、Tab、展开区等动态状态，写入 `element_reveals_element` 关系。
  - 探索结果写入 Memgraph 项目级 UI 图谱（节点 `Page`/`Element`/`Entity`，关系 `CONTAINS`/`BELONGS_TO`/`TRIGGERS_NAVIGATION`/`REVEALS`）。

### 5.3 API 接口测试模式（api_testing）

- **定位**：接口校验、契约检查、响应断言与证据沉淀。
- **默认 Agent**：`api-testing-agent`，并含一组 Worker：doc-analyst、suite-planner、precondition-planner、executor-worker、failure-analyst、project-clarifier。
- **核心能力**：api-test-runner、api-docs-library、api-tester、knowledge-rag、report-writer。
- **技能**：api-contract-testing、api-test-generation、test-data-strategy（见 `modes/api_testing_mode/skills.py`）。
- **流程**：文档解析 → 用例规划 → 前置/认证规划 → 多 worker 并行 HTTP 执行 → 失败分析 → 报告。
- **配套**：可通过「工具中心 → API 接口文档」上传/导入 OpenAPI 等文档供测试复用。

### 5.4 安全测试模式（security_testing）

- **定位**：面向 Web/API、主机、端口、网络侦察的多智能体渗透测试。
- **默认 Agent**：`security-testing-agent`，含 recon / auth / web-verifier / api-verifier / host-verifier / exploit-coder / failure-analyst 等 Worker。
- **核心能力**：security-scan-runner、network-recon-runner、web-scan-runner、service-audit-runner、credential-attack-runner、traffic-analysis-runner、exploit-workbench-runner、report-writer、send-email。
- **技能**：owasp-security-testing、auth-security-testing、input-validation-security-testing（见 `modes/security_testing_mode/skills.py`）。
- **能力链**：资产发现 → 端口扫描 → 服务指纹 → Web 漏洞扫描 → 凭证验证 → 漏洞利用验证 → 结构化报告 + 邮件投递。
- **执行环境**：支持本地或 Docker（默认镜像 `vxcontrol/kali-linux`）沙箱，受 `SECURITY_RUNNER_*` 配置控制。
- ⚠️ **合规提示**：仅可对获得明确授权的目标进行安全测试。

### 5.5 代码审批模式（code_review）

- **定位**：项目级代码审批，辩论式风险识别，输出结构化审批报告。
- **默认 Agent**：`code-review-agent`，含 architecture / correctness / security / testability / maintainability 五维评审员 + synthesizer 总结 Agent。
- **核心能力**：code-review-orchestrator、project-source-loader、project-tree-scanner、project-file-reader、project-diff-reader、cli-executor、report-writer、send-email。
- **特点**：主持人按项目规模与模型上下文分配「辩论时间预算」，多轮立论 → 攻防 → 裁决 → 总结。前端「报告中心」与运行时「审批进程」面板可观测全过程。

### 5.6 性能测试模式（performance_testing）

- **定位**：面向基线测试、吞吐/延迟观察与性能证据输出。
- **默认 Agent**：`performance-testing-agent`，含 `perf-planner`、`perf-script-builder`、`perf-container-operator`、`perf-runner`、`perf-analyst`、`perf-failure-analyst` 等子代理。
- **核心能力**：`performance-test-runner`、`perf-container-manager`、`perf-plan-compiler`、`perf-engine-select`、`perf-result-analyzer`、`performance-engine-runner`、`http-probe-runner`、`mock-target-runner` 等。
- **技能**：k6-load-testing、jmeter-load-testing。
- **流程**：对话式意图采集 → 负载建模与计划编译 → 引擎选择 → Docker 容器化执行（k6 / JMeter）→ 结果解析 → 失败分析 → 报告。
- **目标保护**：`PERFORMANCE_TARGET_ALLOWLIST`（目标主机/IP 白名单硬门）+ VU / RPS / 时长上限 + smoke 前置门，防止误伤生产；运行与指标落 `agent_perf_runs`。

### 5.7 冒烟测试模式（smoke_testing）

- **定位**：面向核心链路快速准入、方案确认和基础可用性验证。
- **默认 Agent**：`smoke-testing-agent`，含 `smoke-source-analyst`、`smoke-plan-designer`、`smoke-plan-reviewer`、`smoke-executor`、`smoke-result-analyst`。
- **核心能力**：`smoke-suite-runner`、`report-writer`、`knowledge-rag`。
- **技能**：smoke-test-planning。
- **流程**：项目/源码解析 → 多智能体生成**可审查**测试方案 → 用户在方案里勾选用例并确认 → 自动执行 → 结果分析。
- **沉淀**：方案、版本、执行结果与回归候选写入 PostgreSQL catalog（`agent_smoke_plan_catalog` / `agent_smoke_plan_versions` / `agent_smoke_run_history` / `agent_smoke_regression_candidates`），证据文件入 RustFS；前端「报告中心 / 冒烟」可查看准入结论与冻结方案链接。

### 5.8 兼容性测试模式（compatibility_testing）

- **定位**：面向多产品、多环境、多平台的兼容性测试编排。
- **默认 Agent**：`compatibility-testing-agent`，含 `report-analyst` 等。
- **核心能力**：`compatibility-test-runner`、`smoke-suite-runner` 等。
- **技能**：playwright-e2e-testing、api-contract-testing、smoke-test-planning。
- **流程**：产品接入/探查 → 环境矩阵生成 → 用例生成 → 用户确认 → 运行器分发 → 结果聚合 → 报告。

### 5.9 占位模式（6 个，只注册 Skills，尚无专用 Runner）

| 模式 | key | 规划方向 |
|------|-----|----------|
| 集成与依赖测试模式 | `integration_testing` | 服务契约、真实依赖、网络模拟、数据访问集成测试 |
| 单元与组件测试模式 | `unit_component_testing` | pytest / jest / vitest / 组件与快照测试 |
| 移动端测试模式 | `mobile_testing` | Appium / Detox / Maestro / Espresso / XCUITest |
| 视觉回归测试模式 | `visual_regression_testing` | 视觉基线比对 |
| 无障碍测试模式 | `accessibility_testing` | a11y 检查 |
| 测试可靠性与韧性模式 | `reliability_testing` | 稳定性、韧性、变异与属性测试 |

> 占位模式已完成 manifest、专属 Skills 与 Agent/工具注册，可被显式选中，但 `harness_key` 指向 `placeholder_testing_harness`、`activation_policy` 为 `explicit_only`，**不会自动路由进入，也没有专用执行链路**；前端会标注「占位」。要转成实装需补各自的 harness 与 `runtime.py`。

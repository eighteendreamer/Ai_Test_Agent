# 测试项目管理与用例驱动专业测试流程方案

## 摘要

新增“测试项目管理”作为所有测试资源的统一归属层，把当前松散的 `project_name`、`project_scope`、Session metadata 和 Smoke catalog 统一收敛到正式的 `project_id`。

目标链路：

```text
创建项目
  → 绑定 API 文档 / 知识图谱
  → AI 生成测试用例草稿
  → 评审并启用用例版本
  → 组成测试套件
  → 创建测试运行
  → 并发领取并执行用例
  → 结果、证据、报告入库
  → 失败用例生成固定版本回归运行
```

项目模块采用严格项目隔离：API 文档、知识图谱、用例、套件、运行记录和历史报告均通过 `project_id` 归属。

## 一、核心领域模型

### 1. 测试项目

新增项目实体：

- `id`：稳定 UUID。
- `project_key`：不可变、唯一的机器标识。
- `name`：可编辑展示名称。
- `description`、`base_url`。
- `status`：`active`、`archived`。
- `created_by`、`created_at`、`updated_at`。

项目删除采用归档，不做物理删除。已归档项目禁止创建新运行，但保留全部历史资源和结果。

### 2. API 文档绑定

当前 API 文档使用自由文本 `project_name`，后续改为正式 `project_id`：

- API 文档元数据迁入 PostgreSQL。
- 文档正文继续存放 MinIO。
- `project_name` 保留为只读兼容字段或 `legacy_project_name`。
- 现有未绑定文档不自动推断、不自动建项目，统一显示为“待绑定”。
- API 文档页面的“所属项目”下拉菜单只读取正式项目列表。
- 上传、URL 导入、集成导入、编辑文档全部支持 `project_id`。
- 文档列表支持按项目、未绑定状态过滤。

现有 `catalog.json` 需要通过显式迁移脚本转入数据库，迁移不修改文档正文。

### 3. 知识图谱绑定

当前 Memgraph 使用 `project_scope` 字符串。改造为：

- 项目表保存稳定的 `project_id` 和 `graph_scope_key`。
- 新写入的图谱节点和关系必须带 `project_id`。
- 查询图谱统一通过项目 ID。
- 旧图谱 scope 不自动归属项目，提供人工绑定入口。
- 项目详情页展示页面、元素、实体、关系数量。
- 删除/归档项目时禁止直接删除图谱，必须通过明确的资源清理操作。

### 4. 测试用例与版本

测试用例定义和测试执行状态分离。

测试用例主表：

- `project_id`
- `case_key`
- `title`
- `mode_key`
- `case_type`
- `lifecycle_status`
- `active_version_id`
- `created_by`

用例版本表：

- `case_id`
- `version`
- `preconditions`
- `steps`
- `assertions`
- `test_data`
- `cleanup`
- `content_hash`
- `source_refs`
- `model_key`
- `prompt_version`
- `skill_versions`
- `created_at`

用例来源必须可追溯到：

- API 文档及文档版本/更新时间。
- 知识图谱节点或查询证据。
- 历史测试记录。
- 生成使用的 Skill、模型和 Prompt 版本。

用例生命周期固定为：

```text
draft
  → pending_review
  → active
  → disabled
  → archived
```

只有 `active` 用例版本允许进入可执行套件。

### 5. 测试套件

套件属于项目：

- `project_id`
- `name`
- `description`
- `status`
- `created_by`

套件条目必须固定 `case_id + case_version_id`，不能只引用“当前最新用例”。这样可以保证一次大规模测试的输入稳定、可复现。

### 6. 测试运行与结果

测试运行：

- `project_id`
- `run_id`
- `run_kind`：`normal`、`regression`
- `mode_key`
- `suite_id`
- `session_id`
- `parent_run_id`
- `status`
- 统计信息、开始/结束时间、执行人

运行条目：

- `run_id`
- `case_id`
- `case_version_id`
- `status`
- `attempt_no`
- `lease_owner`
- `lease_token`
- `lease_expires_at`
- `heartbeat_at`
- `result_id`

运行条目状态：

```text
queued
  → claimed
  → running
  → passed / failed / error / blocked / skipped / cancelled
```

完成后的条目不可重新领取。执行失败也不能把原条目重置为“待执行”，而应创建新的尝试或回归运行。

## 二、模式接入策略

在 `ModeDescriptor` 增加 `case_driven_policy`：

### 强制用例驱动

- `api_testing`
- `ui_automation`
- `smoke_testing`
- `compatibility_testing`

这些模式在专业执行入口必须：

1. 绑定项目。
2. 选择或生成启用用例。
3. 固定套件和用例版本。
4. 创建 TestRun 后执行。

### 可选用例驱动

- `performance_testing`
- `security_testing`
- `accessibility_testing`
- `mobile_testing`
- `reliability_testing`
- `integration_testing`
- `unit_component_testing`
- `visual_regression_testing`

这些模式可以使用项目用例，也可以保留自身的专项计划/Runner 流程。若选择用例，则必须写入项目测试运行记录。

### 豁免用例驱动

- `default`
- `code_review`

代码审批仍可直接执行，但如果用户选择项目，则必须把 Session、报告和审计记录归入该项目；不强制生成 TestCase。

## 三、执行安全与大项目并发

使用 PostgreSQL 原子领取机制，禁止 Agent 通过普通查询自行挑选任务：

- 只能领取当前 `run_id` 下 `queued` 的条目。
- 领取时写入唯一 `lease_token` 和过期时间。
- Worker 定期 heartbeat。
- Worker 崩溃后由租约回收器将超时条目恢复为 `queued`。
- 结果写入必须校验 `run_id + case_version_id + lease_token`。
- 同一个运行条目禁止重复完成。
- 已完成用例默认不会出现在可领取查询中。
- 大项目执行通过分页、批量领取和并发上限控制，避免一次性把全部用例放入模型上下文。

这部分应复用现有 `ToolJob`、Worker、Heartbeat、SSE Event 和 Artifact 机制。

## 四、回归测试设计

失败、错误或阻塞的运行条目可以创建回归运行：

- 回归运行引用原 `TestRun`、原 `TestCaseResult`。
- 默认固定失败时的 `case_version_id`。
- 原用例和原结果永不修改。
- 回归运行可以选择单个失败用例、失败集合或完整失败批次。
- 回归结果产生新的 `TestRun` 和 `TestCaseResult`。
- 报告中显示“原失败证据 → 回归结果”的关联链。
- 如果需要验证修订后的用例，必须显式选择新版本，不能隐式替换原版本。

## 五、API 与前端接口

### 新增项目接口

```text
GET    /api/v1/projects
POST   /api/v1/projects
GET    /api/v1/projects/{project_id}
PATCH  /api/v1/projects/{project_id}
POST   /api/v1/projects/{project_id}/archive
GET    /api/v1/projects/{project_id}/overview
GET    /api/v1/projects/{project_id}/resources
```

### API 文档接口调整

```text
GET   /api/v1/registry/api-docs?project_id=
POST  /api/v1/registry/api-docs/upload
POST  /api/v1/registry/api-docs/import-url
POST  /api/v1/registry/api-docs/import-integration
PATCH /api/v1/registry/api-docs/{doc_id}
```

新的请求体使用 `project_id`。旧 `project_name` 只作为兼容读取字段，不再作为正式绑定依据。

### 测试用例接口

```text
GET   /api/v1/projects/{project_id}/test-cases
POST  /api/v1/projects/{project_id}/test-cases/generate
POST  /api/v1/test-cases/{case_id}/submit-review
POST  /api/v1/test-cases/{case_id}/activate
POST  /api/v1/test-cases/{case_id}/archive
GET   /api/v1/test-cases/{case_id}/versions
```

### 套件与运行接口

```text
GET   /api/v1/projects/{project_id}/suites
POST  /api/v1/projects/{project_id}/suites
POST  /api/v1/suites/{suite_id}/runs
GET   /api/v1/projects/{project_id}/runs
GET   /api/v1/runs/{run_id}
POST  /api/v1/runs/{run_id}/cancel
POST  /api/v1/runs/{run_id}/regression
```

### Session 契约调整

`CreateSessionRequest`、`UpdateSessionRequest`、`SessionSummary`、`SessionDetail` 增加：

```text
project_id: string | null
```

强制用例驱动模式没有 `project_id` 时，服务端拒绝进入执行阶段，而不是让 Agent 自行猜测项目。

## 六、前端模块

新增一级导航“测试项目”，包含：

1. 项目列表：名称、状态、资源数量、最近运行、通过率。
2. 项目概览：API 文档、图谱、用例、套件、运行、失败回归统计。
3. API 文档资源：项目内文档列表和待绑定文档入口。
4. 测试用例：按状态、模式、优先级、来源、版本过滤。
5. 测试套件：用例选择、版本冻结、批量执行。
6. 测试历史：跨所有测试模式查看项目运行记录。
7. 回归中心：失败用例、原始证据、回归批次和最新状态。

现有 API 文档弹窗中的“所属项目”改为正式项目下拉菜单，取消自由输入标签作为主要交互。

工作台在专业测试模式下增加项目选择和运行上下文展示，任务池、报告中心和知识图谱均增加项目过滤。

## 七、分阶段实施

### 阶段 1：项目根与资源绑定

- 新增项目表、项目服务、项目 API、项目列表页。
- API 文档增加 `project_id`。
- 现有未绑定文档显示为待绑定。
- Session 增加可选 `project_id`。
- 项目概览先聚合现有 API 文档、图谱和 Session 数据。
- 更新 `AGENTS.md`，加入课程专业来源和项目用例驱动规则。

验收：可以创建项目、手工绑定 API 文档、查看项目资源概览。

### 阶段 2：测试用例与套件

- 新增用例、用例版本、来源证据、评审和启用接口。
- 接入现有 `generate-test-cases` Skill。
- 生成结果默认进入 `draft`。
- 新增套件及版本冻结。
- 把 API 文档、知识图谱和历史测试记录作为生成上下文来源。

验收：可以生成草稿、评审启用、组成固定版本套件。

### 阶段 3：用例驱动执行与结果入库

- 新增 TestRun、RunItem、Attempt、Result。
- 接入 API、冒烟、UI、兼容性模式。
- 增加原子领取、租约、heartbeat、失败恢复。
- 复用现有 SSE、ToolJob、Artifact、Verification 和 Report。
- 运行历史全部按项目聚合。

验收：大批量用例并发执行时无重复领取，结果和证据完整入库。

### 阶段 4：失败回归与专项模式扩展

- 增加一键回归。
- 默认固定失败用例版本。
- 接入安全、性能和其他可选模式。
- 保留代码审批和普通对话的豁免路径。
- 把现有 Smoke regression catalog 迁移到统一 TestRun/Result 视图。

验收：失败用例可以创建独立回归运行，原始失败记录保持不变。

规则中明确：

- 课程页面是方法论来源，不是当前系统 API 的事实来源。
- 课程代码只能作为设计参考，不能直接复制成生产实现。
- 生成用例必须记录来源、版本、模型、Prompt 和 Skill 证据。
- 没有 Runner 结果不得给出测试通过结论。
- 已完成用例不得被 Agent 重置或复用为同一运行任务。

## 九、测试与验收

### 后端单元测试

- 项目创建、编辑、归档和唯一性。
- API 文档绑定、解绑、项目过滤、待绑定列表。
- 图谱项目隔离。
- 专业模式项目门禁。
- 用例状态非法迁移拦截。
- 用例版本不可变和套件版本冻结。
- 多 Worker 原子领取无重复。
- 租约超时恢复。
- 结果幂等写入。
- 运行统计聚合。
- 回归运行固定原版本。
- 豁免模式不强制用例，但项目绑定时仍写入项目历史。

### 集成测试

验证完整链路：

```text
创建项目
→ 绑定 API 文档
→ 读取图谱和历史上下文
→ 生成草稿
→ 评审启用
→ 组成套件
→ 创建运行
→ 并发执行
→ 结果/Artifact/报告入库
→ 失败用例回归
```

### 前端测试

- API 文档项目下拉只显示正式项目。
- 待绑定文档可被手工绑定。
- 项目详情页资源统计正确。
- 用例状态和版本展示正确。
- 已完成运行条目不可再次领取。
- 回归操作显示原始版本和新运行。
- 项目、模式、状态、时间过滤正确。
- 前端构建和类型检查通过。

## 十、明确假设

- 一个 API 文档、一个测试用例、一个套件、一个测试运行只能归属一个项目。
- v1 不做跨项目共享用例和跨项目套件。
- 普通对话和代码审批可以没有项目；用户主动绑定项目时仍写入项目历史。
- API 文档和知识图谱历史资源不自动推断项目，统一人工绑定。
- 项目采用归档，不提供直接物理删除。
- 失败回归默认固定失败时用例版本。
- 首轮按阶段交付，不一次性重写所有模式。
- 现有 FastAPI + PostgreSQL + MinIO + Memgraph + LangGraph 继续作为主架构，不引入第二套 Django 主后端。

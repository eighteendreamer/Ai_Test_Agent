# Testcontainers 集成测试

先读取项目依赖、Docker 要求、CI 能力和现有容器测试；不要假设候选示例中的模块、镜像或 API 版本。语言模块差异和等待策略按需读取 `references/source-1.md`。

## 输入契约

确认需要真实协议的依赖、镜像来源/版本、Docker socket 或 provider、初始化迁移、凭据注入、资源预算和清理责任。

## 工作流程

1. 只为必须验证真实协议/行为的依赖启动容器，纯逻辑保持快速单元测试。
2. 固定或可追溯镜像版本，使用项目认可来源，不在日志中泄露凭据。
3. 用健康/端口/日志等待策略判断就绪，不使用盲目 sleep。
4. 每个测试或测试组声明生命周期、网络、初始化数据、迁移和清理边界。
5. 覆盖真实约束、事务、编码、并发、连接失败和版本兼容行为。
6. 保存容器日志、镜像、端口映射、测试输出和退出码。

## 生命周期门禁

1. 只把无法由 mock 证明的协议、事务、编码、版本兼容或故障恢复放入容器测试。
2. 固定可追溯镜像 digest/版本；禁止使用未审查的 `latest`。
3. 使用健康检查、端口、日志或应用探针等待就绪，禁止盲目 sleep。
4. 明确容器共享范围、网络、卷、初始化顺序、迁移回滚和并行隔离。
5. 失败必须收集容器日志、镜像、端口、环境摘要和测试退出码，并清理临时资源。

## 输出

输出依赖与 Docker 能力、容器拓扑、生命周期、数据隔离、CI 资源风险、执行命令和证据。未确认 Docker 可用时仅做架构审查。

## 审查重点

- 复用容器是否导致顺序依赖或脏数据。
- 本地与 CI 的 Docker 能力、架构和资源限制是否一致。
- 测试是否仍把所有真实行为 mock 掉。

## 输出边界

未确认 Docker/Testcontainers 可用时只提供测试架构，不声称执行。

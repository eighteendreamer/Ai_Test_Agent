# 不稳定测试审查

把 flaky 测试当作可靠性缺陷调查。优先寻找根因和可观测证据，不能用无限重试或静默隔离替代修复。

## 识别信号

- 测试依赖真实时间、随机数、网络、进程顺序、线程调度或未固定的时区。
- 测试共享数据库、文件、端口、浏览器状态或全局 mock，清理不完整。
- 断言依赖 sleep、固定延迟、脆弱选择器或未等待的异步任务。
- CI 与本地运行环境、并行度、资源配额或操作系统不同。
- 重试后变绿但没有保留首次失败输出、次数和环境信息。

## 审查流程

1. 读取失败日志、重试记录、提交、环境和并行上下文，先确认是否真的存在不稳定性。
2. 将原因归类为时间、数据、隔离、并发、环境或外部依赖，并指出证据不足之处。
3. 检查隔离/quarantine 是否有 owner、期限、可见告警和退出条件。
4. 检查重试是否限制次数、保留失败 artifact，并且最终状态仍能阻断高风险发布。
5. 给出最小根因修复：控制时钟/随机种子、独立 fixture、正确等待、资源清理或依赖替身。

审批报告必须区分“已确认 flaky”“疑似 flaky”和“无法从当前证据判定”，不得自动修改测试状态。

## 证据采集矩阵

同一提交至少重复运行并记录 seed、时区、OS、运行时、并行度、资源、网络、依赖服务、重试次数、首个失败 artifact 和最终状态。只有一次失败只能称为“待调查”。

## 根因实验

把原因归类为时间/异步、随机/顺序、数据/隔离、并发/资源或外部依赖。每个实验只改变一个变量，写明假设、预期信号和停止条件：固定时钟/seed、改变顺序、独立 fixture、串并行对照、受控替身或相同 runner 重放。

## Quarantine 门禁

隔离必须有 owner、原因、首次提交、到期时间、告警和恢复条件；重试必须保留首个失败，且不能将高风险发布改成通过。需要统计检测、隔离管理、Jest 或 Playwright 适配细节时加载 `references/source-1.md`。

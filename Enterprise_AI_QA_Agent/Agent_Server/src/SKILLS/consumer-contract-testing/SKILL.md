# 消费者契约测试

先确认项目实际契约框架、Broker、认证和 CI 流程；不要默认使用 Pact 或候选命令。交互模板和版本策略按需读取 `references/source-1.md`。

## 输入契约

需要消费者 operation、提供者接口版本、请求/响应 schema、状态准备方式、契约发布位置、分支策略和部署门禁。缺少 Broker 或提供者验证能力时，明确降级为静态审查。

## 工作流程

1. 以消费者真实使用的请求和响应字段定义最小交互，不复制整个提供者模型。
2. 为每个交互声明提供者状态、请求、响应和错误契约。
3. 消费者测试生成可追溯契约；提供者验证必须使用受控状态准备和真实序列化边界。
4. 发布契约时关联消费者版本、分支或环境，避免覆盖不可追踪版本。
5. 部署门禁基于已验证版本关系，明确破坏性变更和兼容窗口。
6. 保留契约、验证输出、提供者状态日志和失败字段差异。

## 兼容性门禁

1. 只声明消费者真正读取或依赖的字段，避免复制整个提供者模型。
2. 每个交互必须有唯一标识、提供者状态、请求匹配、响应断言和错误场景。
3. 验证必须穿过真实序列化/路由/认证边界；仅验证 consumer mock 不算契约通过。
4. 发布契约必须绑定消费者版本、提交 SHA、环境和分支，禁止未追踪覆盖。
5. 删除/收窄字段、改变状态码或错误结构视为破坏性变更；只有兼容窗口和验证报告齐全才允许部署。

## 失败处理与输出

按请求匹配、状态准备、schema 差异、认证、Broker 传播和版本关系分类失败。输出交互矩阵、提供者验证命令、版本图、破坏性变更判断、脱敏报告和退出码。

## 审查重点

- 契约是否只验证 mock 而没有提供者验证。
- 消费者是否声明从未实际使用的字段，造成不必要耦合。
- Broker token、测试数据和状态端点是否安全隔离。

## 输出边界

当前没有专用契约 Runner 时只做规划、静态审查和现有 API 工具可覆盖的验证。

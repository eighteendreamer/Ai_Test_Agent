# MSW API 模拟

先读取项目 MSW 版本、setup、handlers、测试 runner 和真实 API 契约；不要假设候选示例 API 与当前版本兼容。框架差异和 handler 模板按需读取 `references/source-1.md`。

## 输入契约

收集接口方法/路径、请求 headers 与 body、响应 schema、认证方式、环境边界、测试数据和失败样本。明确 mock 目标是组件隔离、集成测试还是离线开发，避免把 mock 当作真实服务验证。

## 工作流程

1. 从真实 API 契约建立最小默认 handler，保持字段、状态码和错误结构一致。
2. 用例级 override 只表达该场景的差异，并在测试结束后恢复。
3. 覆盖成功、空、延迟、4xx、5xx、网络错误、分页和认证过期。
4. 未处理请求默认作为可见失败或警告，禁止静默访问外网。
5. 测试用户可观察结果和客户端恢复，不只断言 handler 被调用。
6. 将 mock 契约与 OpenAPI/真实服务差异纳入审查，避免长期漂移。

## Handler 设计门禁

1. 默认 handler 只覆盖稳定的成功基线；场景差异使用 test-local override，并在 teardown 后恢复。
2. handler 必须校验关键请求字段，不能仅按 URL 返回万能响应。
3. 为空、延迟、超时、4xx、5xx、网络断开、分页、限流和认证过期定义可观察结果。
4. 未处理请求在测试中默认失败；若项目必须允许第三方资源，显式列出白名单和理由。
5. mock 返回值必须遵循真实序列化、headers、错误结构和字段可选性；契约变更同步更新来源文档。

## 证据与输出

输出 handler 覆盖矩阵、未处理请求清单、客户端可观察断言、隔离/清理方式、契约漂移风险和实际命令退出码。未确认 MSW 已安装时只给出方案，不声称已执行。

## 审查重点

- handler 是否过度宽泛、无请求断言或返回不真实数据。
- 默认 handler 是否泄漏跨测试状态。
- mock 是否掩盖序列化、headers 或认证问题。

## 输出边界

未确认 MSW 已安装时只给出网络 mock 策略，不新增依赖或声称运行。

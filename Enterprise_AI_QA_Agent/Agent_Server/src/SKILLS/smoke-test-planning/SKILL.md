# 冒烟测试规划

冒烟测试只覆盖高价值、低数量、可快速判定的核心链路。先形成可审查方案，再等待用户确认；执行阶段只能运行冻结方案中的用例。

## 规划要点

- 从用户目标、API 文档、UI 图谱、健康检查和已知回归候选中选择关键路径。
- 每个用例必须有前置条件、请求/操作、明确断言、预期结果、风险级别和证据要求。
- 优先读操作和健康检查；写操作必须声明测试租户、清理/回滚和破坏性风险。
- 认证、环境、凭据、目标地址和依赖必须明确；不得从上下文猜测敏感值。
- 方案应能在短时间内给出准入结论，避免把完整回归套件塞进冒烟模式。

## 执行纪律

1. 先调用 `smoke-suite-runner` 的方案动作，等待用户确认或修改。
2. 用户确认后只传递已选 case id/序号，不擅自补充步骤或改变断言。
3. 保留请求/操作、响应、截图、日志、失败原因和清理结果。
4. 区分阻断准入的失败、环境/前置失败和非阻断观察项。
5. 生产环境执行必须继承现有授权、环境和安全策略，不由 Skill 放宽限制。

## 输出

输出方案、用户确认状态、执行证据、准入 verdict 和可提升为回归用例的候选；没有执行证据时不得声称通过。

## 用例选择与状态协议

从健康检查、API 文档、UI 图谱、历史缺陷、发布 diff 和关键业务路径形成候选，再按影响×概率×可快速判定排序。每个 case 记录 `case_id`、环境/版本、前置、账号 ref、操作、断言、读写级别、风险、预计耗时、清理/回滚、artifact 和阻断规则。状态依次为 `draft`、`awaiting_confirmation`、`approved`、`running`、`completed/failed/blocked`；确认后只能执行冻结的 case id，不能擅自追加步骤或扩大环境。

## 准入判定

核心链路断裂、关键依赖不可用、认证/授权失败和数据完整性问题是阻断失败；环境/前置失败单独标记。需要生产健康检查、API、认证、关键流程、报告告警和 CI 细节时读取 `references/source-1.md`。

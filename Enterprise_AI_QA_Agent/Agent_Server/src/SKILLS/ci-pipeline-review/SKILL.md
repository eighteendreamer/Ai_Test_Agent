# CI 流水线审查

将流水线变更当作可维护性、反馈速度和发布安全的代码变更审查。只根据仓库文件、diff、CI 配置和已有执行证据给出结论；代码审批阶段不直接运行远程流水线，也不凭空声称优化已生效。

## 审查顺序

1. 识别触发器、分支保护、必需检查和部署边界，确认测试是否在正确的提交/环境执行。
2. 绘制阶段依赖：安装、静态检查、单元、集成、端到端、构建和发布，找出不必要的串行依赖。
3. 检查缓存键是否包含锁文件、运行时和架构；缓存命中失败必须安全降级，不能使用可能污染结果的共享缓存。
4. 检查测试分片、并行矩阵和重试策略是否保持确定性，避免重复执行、漏测或把 flaky 测试隐藏在无限重试中。
5. 检查路径过滤和选择性测试规则是否覆盖共享库、配置、脚本以及跨模块依赖变化。
6. 检查失败可见性：保留 stdout/stderr、测试报告、覆盖率、日志和失败 artifact，并确保失败状态不会被 `continue-on-error` 静默吞掉。

## 必须指出的问题

- 测试门禁被跳过、降级或只在非保护分支运行。
- 缓存可能复用错误版本依赖、测试结果或敏感数据。
- 并行/分片改变测试语义、破坏共享资源隔离或造成结果不稳定。
- 选择性执行规则可能漏掉受影响的测试。
- 重试掩盖真实失败，或没有记录重试次数和最终原因。
- 流水线变慢、重复安装、重复构建但没有可验证的收益。

## 输出

为每条发现提供：证据文件与行号、影响范围、严重度、复现/验证方式和最小可执行建议。区分“从配置静态确认”和“需要 CI 运行数据验证”的结论。

# 阶段 4 第 11 轮执行报告：统一导入链路容量基线与安全模式边界评估

## 1. 本轮方案执行做了什么

本轮以真实数据库容量基线和安全边界调研为主，没有新增业务代码，避免在安全模式授权上下文尚未接入 RunItem 执行服务前强行堆叠适配层。

容量验证：

- 使用一次性 PostgreSQL 16 容器，初始化现有项目、Smoke catalog、TestCase、Suite、TestRun 和 Result 表；
- 生成并导入 1,000 + 10,000 共 11,000 条历史 Smoke 用例及结果；
- 通过现有 `LegacySmokeImportPreflightService.apply()` 和 `PostgresLegacySmokeImportStore` 完成真实物化；
- 对历史分页查询执行 `EXPLAIN (ANALYZE, BUFFERS)`，验证项目 scope 索引路径。

安全模式边界调研：

- `security_testing` manifest 为 `case_driven_policy=optional`，并要求 `verified_target_authorization`；
- `security-scan-runner` 的真实执行依赖 `SecurityTask`、command profile、target guard、risk policy 和独立权限上下文；
- 当前通用 `TestRunExecutionService` 只持有 Session ID，不会自动把服务器可信的 security authorization grant 注入 CaseExecutionAdapter；
- 因此本轮不把安全 Runner 粗暴加入通用 adapter 白名单，继续保留安全模式的专项 campaign/授权链路，符合方案中“可选用例驱动”和安全门禁要求。

## 2. 真实容量结果

| 指标 | 结果 |
|---|---:|
| 物化用例数 | 11,000 |
| 物化结果数 | 11,000 |
| apply 总耗时 | 7.597 秒 |
| 吞吐 | 约 1,448 条用例/秒 |
| scope 分页查询执行时间 | 0.184 ms（该小数据集） |
| 查询计划 | `Index Only Scan` → `Sort` → `Limit` |
| 索引缓冲命中 | 8 shared buffers |

上述吞吐是单进程、单批次、一次性容器中的基线，不代表生产容量承诺。它证明当前批量 `executemany` 和索引路径在 1k/10k 规模下没有明显的结构性退化；并发导入、网络延迟、磁盘压力和多项目混合数据仍需生产类环境验证。

## 3. 课程专业来源如何影响本轮判断

`项目借鉴/llm-testing-course/安全测试与红队.html` 强调安全基线与深度红队要分层，所有工具调用需要独立权限验证；`评测工程化与CICD.html` 强调用例数据集版本化、回归范围和容量/质量门。基于这些原则，本轮把“可选安全 Runner”与“通用用例执行生命周期”保持边界，不把一个普通 TestCase payload 当成授权凭据。

## 5. 相比方案 1.0 的进度

阶段 4 的 Smoke 历史统一视图已经从功能正确性推进到真实数据库容量基线。安全模式仍是可选用例驱动，专项流程和授权链路保持独立；要接入 TestRun，需要先建立“服务器可信授权 → 固定用例 target/profile → runner 执行”的显式契约。

## 6. 下一轮要做什么

1. 设计安全用例的最小可信契约：固定 `command_profile`、target、授权 grant 引用和风险级别，禁止用例内容自行伪造 authorization；
2. 复用现有 `SecurityTargetGuard`、`ExecutionSafetyPolicy` 和权限服务，先完成不执行真实命令的契约测试；
3. 如果契约测试证明可无损接入，再实现安全模式 CaseExecutionAdapter；否则继续保持 optional 专项执行；
4. 在真实 PostgreSQL 多连接环境补充并发导入、锁等待、失败回滚和 10k+ 混合项目基线。

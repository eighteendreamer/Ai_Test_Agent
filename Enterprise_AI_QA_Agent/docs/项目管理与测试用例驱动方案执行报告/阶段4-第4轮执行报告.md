# 阶段 4 第 4 轮执行报告：性能模式统一用例执行

## 1. 本轮结论

本轮把 `performance_testing` 接入统一的测试用例驱动链路：固定用例版本经适配器编译为已有性能 Runner 调用，执行结果进入统一 Result/Artifact/Verification 契约，失败 Result 可沿既有回归 API 创建新的 regression Run。

本轮保持性能模式 `optional`，没有把未适配的 `security_testing` 接入 Runtime，也没有新增性能专属 Run、Result、Regression 表或第二套执行 API。

## 2. 用例执行适配

`CaseExecutionAdapter` 现在允许已有适配器的模式集合：

- `api_testing`
- `smoke_testing`
- `compatibility_testing`
- `ui_automation`
- `performance_testing`

性能用例只从固定 Step 补齐 URL/method；以下关键参数必须来自评审后的用例版本并显式满足门禁：

- `confirm_target=true`；
- `target_rate_rps` 或 `virtual_users` 为正数；
- `run_intent` 必须为 `probe` 或 `regression`。

系统不会自动猜测负载、目标确认、SLA 或执行意图。未进入适配器白名单的模式在 Runtime 调用前阻断，避免测试 Agent 误用不存在的执行入口。

## 3. 性能 Verification 契约

性能结果只有同时具备以下证据才会判定为 `passed`：

1. Runner `status=completed` 且 `ok=true`；
2. `run_intent=regression`、`verdict=pass`；
3. `metrics.samples > 0`；
4. 存在性能 SLA 或 baseline comparison；
5. `sla_result.passed=true`；
6. `engine_threshold_crosscheck.agree=true`。

SLA 失败、baseline 退化（即使 Runner 伪造 `verdict=pass`）、引擎阈值交叉校验不一致、零样本或缺少通过标准时不得伪装成通过。`probe/baseline` 结果进入 `not_run`，通用断言不会被错误计入性能断言通过数。

专业依据来自项目内 `项目借鉴/llm-testing-course` 的测试课程材料，以及本项目已经写入 `AGENTS.md` 的测试工程约束；本轮将“明确测试意图、可验证断言、结果证据和回归闭环”映射到已有 TestRun 生命周期，而不是只依赖对话文本结论。

## 4. Artifact 输出

性能 Runtime 的报告处理复用现有 ToolJob/Artifact 机制，统一返回：

- Markdown 性能报告；
- HTML 性能报告；
- metrics/SLA JSON；
- baseline comparison。

没有创建性能模式独立的报告存储链路。统一执行接口可以继续通过已有 ToolJob、Artifact、Result 和 Verification 查询结果。

## 5. 端到端回归链路

新增系统测试覆盖以下真实调用顺序：

```text
创建 suite Run
  -> claim RunItem
  -> execute 固定性能用例版本
  -> 写入 Result / Artifact / Verification
  -> 失败结果通过既有 regression API 创建 child Run
```

成功路径验证 metrics 与三个 Artifact ID；失败路径验证 Result 为 `failed`、存在 Verification，并且回归 Run 继续绑定原 `case_version_id`，不重置原条目或覆盖原 Result。

## 6. TDD 与验证结果

本轮新增/扩展测试覆盖：

- 性能参数缺失、非法负载、缺少确认和非法执行意图的门禁；
- 未适配模式在 Runtime 前阻断；
- 性能 Verification 的通过、SLA 失败、baseline 退化、probe、零样本和交叉校验边界；
- Markdown/HTML/JSON Artifact 输出；
- FastAPI 创建 Run → claim → execute → Result/Artifact/Verification → 失败回归。

## 7. 未处理风险与边界

本轮明确保留以下后续专项：

- 长压测期间 RunItem/ToolJob heartbeat 尚未专项解决；默认 lease 与超长压测时长仍有生产风险；
- 相对路径目标的文档解析语义需要后续专项契约；
- `security_testing` 尚未接入统一用例执行；
- 没有把 `performance_testing` 从 optional 改为 required；
- 尚未用真实 PostgreSQL 数据集完成 1k/10k 失败占比、并发和 EXPLAIN 容量基线。

这些风险没有通过静默降级掩盖，后续应继续沿统一 TestRun/Result/Artifact/Verification 契约处理。

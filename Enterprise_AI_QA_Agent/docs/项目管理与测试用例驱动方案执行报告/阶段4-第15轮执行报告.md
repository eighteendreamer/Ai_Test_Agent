# 阶段 4 第 15 轮执行报告：安全 Profile 能力矩阵

## 1. 本轮方案执行做了什么

第 14 轮已经把安全 Runner 的真实输出投影到 Verification，但断言能力仍是 Verification 内部的全局分支：测试用例编译器、Profile 列表和 Verification 对“哪些字段/断言真正可用”没有同一份可查询契约。本轮围绕现有 `SecurityCommandProfileRegistry` 和既有 `/api/v1/registry/security-profiles` 完成能力矩阵收敛。

主要内容：

- Parser 注册表将 Parser 实例与稳定的 required output fields 放在同一份 descriptor 中；空结果契约测试会发现字段声明漂移；
- `SecurityCommandProfileRegistry.verification_capabilities()` 根据 Profile 的 Parser 和 `FindingNormalizer` 支持集合生成能力矩阵，避免把 Parser 有计数但没有标准 Finding 归一化的工具误宣称为 `finding_count` 可断言；
- Profile API 现在公开脱敏的：
  - `allowed_arguments`；
  - `parser_key`；
  - `artifact_policy`；
  - `notes`；
  - `structured_output`、精确 `parsed_fields`、断言 kind/operator；
- 不公开 `command_template`、Shell 拼接、内部路径、凭据或授权范围；
- 新增共享 `validate_assertion()`，统一规范化 kind/operator/target，并由 `CaseExecutionAdapter` 和 `VerificationService` 共同使用；
- 安全用例在调用 Runner 前拒绝未知 Profile、未知断言 kind、未声明 operator 或未声明 parsed field，避免先执行昂贵扫描再得到不可验证结果；
- Verification 对不支持的断言、operator、target 分别记录审计 metadata，不能把它们计为通过或失败；
- 前端 Scanner 详情页展示 Parser、允许参数、断言能力、parsed fields 和 Artifact 策略；前端类型与后端契约同步。

## 5. 本轮发现与修复

发现 `ffuf`、`whatweb` 等 Parser 虽然输出了计数字段，但运行时只有 `FindingNormalizer.normalize_batch()` 的结果会进入统一 `findings`。如果全局宣称所有 Parser 都支持 `finding_count`，`expected=0` 可能在没有真实 Finding 证据时误判通过。

修复为：`finding_count` 只对当前确实有 FindingNormalizer 的 Profile 宣布支持；不支持的断言在 Adapter 阶段阻断，在 Verification 阶段记录为 unsupported，不产生通过结论。另发现根字段前缀会错误放行 `headers.unknown` 或列表路径，现改为只接受 Parser descriptor 明确声明的精确路径。

## 6. 下一轮建议

1. 接入安全审批等待生命周期：扩展 RunItem/Attempt 的非终态 `waiting_approval`，复用现有 ToolJob、Approval、lease 和 resume 机制，等待期间不产生 Result；
2. 对批准、拒绝、重复 resume、scope hash 变化、服务重启恢复做系统接口测试；
3. 继续使用通用失败回归入口，验证安全 `failed/error/blocked` Result 可创建新 regression TestRun，源 Result/Artifact 不被覆盖；
4. 单独评估知识图谱从 `project_scope` 收敛到 `project_id` 的局部迁移方案，不在审批轮次混改；
5. 如果安全用例生成需要更强约束，再基于现有 Profile 契约补充参数类型/必填性 schema，并保持向后兼容。

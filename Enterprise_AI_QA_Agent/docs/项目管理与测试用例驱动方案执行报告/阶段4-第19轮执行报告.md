# 阶段 4 第 19 轮执行报告：项目隔离、专项证据链与全生命周期容量

## 1. 本轮范围

本轮针对上一轮遗留的四项验收项继续收敛：

- 知识图谱和旧 Smoke 兼容模式统一经过正式 `project_id` 访问，归档项目在图谱读取前拒绝；旧 `project_scope` 仅保留为显示、迁移和历史兼容字段。
- UI Automation、Compatibility 的系统级测试继续验证生产 `ToolJob → Artifact → Verification → Result` ID 关联和终态。
- 项目管理前端显示并操作 `blocked`、`cancelled`、审批等待和资源补偿状态。
- 新增真实 PostgreSQL 1k/10k/100k 用例全生命周期基准，覆盖 claim、start、heartbeat、complete、Attempt 和 Result 写入。

## 2. 依据与实现

- `项目借鉴/llm-testing-course/评测工程化与CICD.html`：用例版本、结果、执行环境和证据必须可追溯。
- `项目借鉴/llm-testing-course/Agent轨迹与协议鲁棒性.html`：验证状态迁移、重复执行、超时恢复和终态不可重领。
- `项目借鉴/llm-testing-course/性能测试-通用篇.html`：分级加压并记录吞吐、错误率和 P50/P95/P99。

图谱服务的正式调用链现在由主应用共享 `ProjectService` 和 `KnowledgeGraphService`。Smoke 运行时不再自行创建脱离项目权限的图谱服务；API 文档和图谱读取均优先使用 `project_id`，旧 scope 只在无法解析正式项目时作为兼容输入，并且正式服务会拒绝归档项目。

容量测试暴露的根因是普通 `start/complete/审批` 流转在每个条目上重新扫描全量 Item，并竞争同一 Run 统计行。现已将可证明的状态迁移改为 PostgreSQL 单条原子 `UPDATE ... RETURNING`：在数据库端增量更新统计、Run 状态和时间戳；回收、取消等无法安全推导的路径仍使用全量聚合，避免以近似计数替代事实。

100k 测试使用随机表名，并在 `finally` 按 Result → Attempt → Item → Run 逆序清理；不会触碰业务表。早期重跑因上一轮孤儿进程仍持有旧临时表锁而产生死锁，另一次未优化实现暴露了 Run 行锁竞争，均未纳入基线；最终基线为单实例、原子增量实现的上述结果。

以上数据来自本机目标 PostgreSQL 配置（Python 3.11，32 workers），是开发环境容量基线，不是生产容量承诺。100k 的 claim P99 出现约 `1.96 s` 长尾，后续若生产需要更低尾延迟，应继续评估领取批量、连接池和数据库 I/O；正确性与完整生命周期已通过。

# 阶段 4 第 8 轮执行报告：Smoke 物理导入预检与默认 Dry-run

## 1. 本轮方案执行做了什么

本轮实现了 Smoke catalog 物理导入前的只读预检，不执行任何 canonical 表写入。

新增：

- `LegacySmokeImportPreflightService`：读取旧 catalog 的 metadata 快照并输出预检分类；
- `scripts/preflight_smoke_catalog_import.py`：要求 `--scope-project-map` 显式提供 `project_scope → 已存在项目 UUID` 映射，默认且唯一行为是 dry-run；
- Smoke catalog 的 distinct scope 查询和分页读取；
- canonical Result 的 `actual.run_result.run_id` / `actual.legacy_smoke_run_id` 反查，用于识别已经投影的旧运行；
- 预检结果分类：
  - `importable`：身份、metadata、case_results 和项目映射均通过；
  - `unmapped`：scope 没有人工映射；
  - `already_projected`：canonical Result 已经引用 legacy run ID；
  - `invalid`：身份不完整、metadata 非法、身份不一致或没有逐例结果；
- 输出保留 legacy run/plan/scope ID、状态和逐例状态映射，不触发创建项目、用例、套件、运行或回归。

预检使用现有 PostgreSQL/项目/运行 Store 能力，没有引入新的数据库客户端或第二套数据访问框架。

## 2. 相比方案 1.0 的进度

Smoke 物理迁移现在具备安全前置链路：

```text
显式 scope → project 映射
  → 校验正式项目 UUID
  → 读取 metadata 快照
  → 识别 canonical 重复投影
  → 输出 dry-run 预检报告
  → 后续才允许设计 import ledger / 物化写入
```

本轮仍然不把旧历史伪造成可执行 TestRun/Result。尚未完成：

- import ledger 表和幂等物化写入；
- legacy TestCase/Version/Suite/Run/Attempt/Result 的历史时间保真导入；
- 已导入历史的正式回归策略；
- 真实 PostgreSQL 数据集上的 EXPLAIN、并发与大批量基线。

## 4. 不合格项与修复方案

本轮没有新增失败测试。预检中的 `invalid`、`unmapped` 和 `already_projected` 是预期业务分类，不是测试失败；它们会阻止后续物化导入，避免错误历史进入 canonical 生命周期。

## 5. 下一轮要做什么

1. 设计 `legacy_smoke_import_ledger`：唯一键至少包含 `source_system + legacy_run_id`，逐例还需保留 `legacy_case_id`；
2. 在 ledger 上实现默认 dry-run、显式 `--apply` 二阶段命令，apply 前强制要求预检报告无 invalid/unmapped；
3. 物化导入时保留原始 ID、metadata、状态和时间，不经过普通 active 用例执行入口；
4. 导入产生的历史 Result 默认只读，正式回归必须显式开启并绑定固定版本；
5. 增加失败回滚、重复执行和跨项目映射冲突测试。

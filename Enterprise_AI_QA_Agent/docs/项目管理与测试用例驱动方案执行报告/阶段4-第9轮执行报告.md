# 阶段 4 第 9 轮执行报告：Smoke 历史受控物化导入

## 1. 本轮方案执行做了什么

本轮在第 8 轮只读预检之后，实现了显式 `--apply` 的受控物化导入，并增加 `legacy_smoke_import_ledger` 作为幂等与源快照防篡改边界。

主要内容：

- 新增 `LegacySmokeImportStore` 抽象、内存测试实现和 PostgreSQL 实现；
- ledger 使用 `(source_system, legacy_run_id)` 唯一键，记录目标项目、源 hash、canonical run ID、源快照和导入时间；
- PostgreSQL 导入在单事务中写入 ledger、TestCase、TestCaseVersion、TestSuite、SuiteItem、TestRun、RunItem、Attempt、Result；
- 使用固定 UUID5 namespace 生成稳定 canonical ID，重复 apply 可安全返回 `already_imported`；
- source hash 基于目录持久化行字段和原始 metadata，避免 Pydantic 缺失字段默认值（如当前时间）导致重复导入误报源数据变化；
- 物化数据明确设置为历史只读资产：
  - TestCase / TestCaseVersion / TestSuite 为 `archived`；
  - TestRun `origin=legacy_smoke_import` 且状态为 `completed`；
  - RunItem 处于终态且不带 lease；
  - Result 的 `actual` 保留 `legacy_smoke_*` 身份、原始状态和 `read_only=true`；
  - 不暴露旧 MinIO URI，仅保留不透明 legacy source ref；
- `TestRunService.create_regression()` 拒绝对 imported legacy run 创建正式回归运行；
- CLI 增加 `--apply`，默认行为仍为 dry-run；apply 前强制完整预检，存在 unmapped/invalid 时整体拒绝写入；单条导入失败记录错误并继续处理其他可导入记录。

## 2. 数据安全与生命周期决策

旧 Smoke catalog 没有正式 TestCaseVersion、Suite、RunItem、Attempt 结构，且逐例结果主要存在 JSON metadata 中。因此导入采用“历史快照物化”而不是伪装成可继续执行的活动测试：

```text
显式 scope → project 映射
  → 完整 dry-run 预检
  → ledger 幂等检查
  → 单事务物化 archived case/suite + completed read-only run
  → 后续查询可追溯，普通 claim/execute/regression 不会误用
```

## 4. 失败项与修复

初次定向测试发现第二次 apply 被错误判定为源快照变化。根因是旧 metadata 未提供 `started_at`，Pydantic 校验时每次使用新的 `utc_now()` 默认值，导致基于校验后模型的 hash 不稳定。修复为基于原始 catalog metadata 与稳定目录字段计算 source hash；修复后定向测试和全量测试均通过。

## 5. 下一轮建议

1. 在真实 PostgreSQL 上执行小规模 apply，验证 deferred FK、唯一约束、事务回滚和重复并发导入；
2. 对 ledger 增加操作审计查询与按项目分页接口；
3. 为导入历史增加显式“只读历史详情” API，避免前端误调用通用执行入口；
4. 针对失败 legacy case 设计“复制为新 native case/version”的人工确认回归流程，而不是解冻 imported 资产；
5. 执行真实数据量下的 EXPLAIN、批量耗时和索引容量基线。

# 阶段 4 第 2 轮执行报告：大批量回归热路径与 Windows Artifact 根因修复

## 1. 本轮结论

本轮完成两项根因级增强：

1. 回归创建不再读取父 Run 的完整 `items + attempts + results`，改为读取 O(1) Run 头和实际需要的轻量回归候选。
2. 修复 Compatibility Runner 本地 Artifact 在 Windows 长路径下稳定失败的问题，使后端全量测试从上一轮的 2 项失败恢复为全绿。

回归业务语义未改变：只允许 `failed / error / blocked`，默认固定原失败版本，显式覆盖仍必须指向当前 active version，原 Run/Result 不修改。

## 2. 大批量回归热路径

### 2.1 原始瓶颈

上一轮 `create_regression()` 通过 `get_run()` 构造完整 `TestRunDetail`。PostgreSQL 会依次读取父 Run 的：

- 全部 RunItem；
- 全部 Attempt；
- 全部 Result 及其 `actual/evidence/metrics/error` JSONB。

设父 Run 有 N 个 Item、A 个 Attempt、R 个 Result，实际失败候选为 F，旧路径的应用内存为 O(N+A+R+F)。Attempt 可能因租约恢复大于 Item 数，但回归筛选完全不需要 Attempt。

### 2.2 新 Store 契约

新增内部轻量模型 `RegressionSourceRecord`：

```text
result_id
run_item_id
case_id
case_version_id
status
run_item_position
```

新增 Store 方法：

```text
list_regression_candidates(run_id, result_ids)
```

语义：

- `result_ids=None`：只返回父 Run 的 `failed/error/blocked`。
- 显式 IDs：返回父 Run 中全部命中结果，包括 passed/skipped，交由服务层产生准确的 `not eligible` 错误。
- 未知、跨 Run 或非法 UUID 不泄漏 PostgreSQL 类型异常，继续按 missing result 处理。
- 来源 RunItem 缺失时保留 `run_item_position=None`，服务层继续给出带 run_item_id 的上下文错误。
- 候选按来源 position、result ID 确定性排序。

服务现在只执行：

```text
get_run_record(parent_run_id)
  → list_regression_candidates(parent_run_id, selected_ids)
  → 领域校验
  → 创建新 Run + F 个新 RunItem
```

必要复杂度降为 O(F)；显式选择时输入上限仍为 1000。

### 2.3 PostgreSQL 查询和索引

PostgreSQL 查询只投影六个物理列，通过 Result `LEFT JOIN` RunItem 获取来源位置，不读取 JSONB，不读取 Attempt。

默认失败候选新增 partial covering index：

```sql
ON agent_test_case_results (run_id, run_item_id, id)
INCLUDE (status, case_id, case_version_id)
WHERE status IN ('failed', 'error', 'blocked')
```

读取终态父 Run 不增加 `FOR UPDATE`：原结果不可变，额外行锁只会无谓串行化多个合法回归创建请求。新 Run 和全部新 Item 仍由现有单事务 `INSERT + executemany` 写入。

## 3. 大批量日志和 SSE

原实现会把全部 `source_result_ids` 同时复制到结构化日志和 Session SSE。10k 失败项会产生大日志、大事件和额外内存。

本轮将来源 ID 预览固定为最多 100 个，并增加：

- `source_result_count`
- `source_result_ids_truncated`

完整关联仍以每个 RunItem 的 `regression_source_result_id` 为权威来源，没有丢失证据链。

## 4. Compatibility Windows 长路径根因

### 4.1 复现证据

两项既有失败可稳定复现：

- `test_reregistering_stale_runner_requeues_prior_assignment`
- `test_heartbeat_from_stale_runner_requeues_prior_assignment`

失败路径父目录长度约 226–228，`mkdir()` 成功；最终 Artifact 路径长度约 282–285，`path.write_bytes()` 在 Windows 传统 `MAX_PATH=260` 边界后触发 `FileNotFoundError`。

旧内部路径同时编码：测试根目录、plan_id、dispatch_id、task_id、artifact_id 和原文件名。问题不是目录未创建，也不是异步清理竞态，而是存储键设计把业务层级无限放大到文件系统路径。

### 4.2 根因修复

本地 Artifact 改用全局唯一 `artifact_id` 作为内部文件名，并用末两位做目录分片：

```text
<artifact_root>/compatibility/<id_suffix>/<artifact_id>
```

原文件名继续保存在 server-controlled metadata，下载 API、MIME、任务关联、状态持久化和删除逻辑均不变。旧版本已持久化的 `local_path` 仍能读取/删除，因读路径使用记录内的完整路径，不依赖新布局重建。

该方案同时避免单目录聚集过多文件，没有引入 Windows 专属 `\\?\` 路径分支，也没有只修 `write_bytes()` 后留下读取/删除失败。

## 5. TDD 证据

本轮观察并修复的 RED：

1. Spy Store 禁止 `get_run()` 后，回归创建在完整父详情读取处失败。
2. PostgreSQL Store 缺少轻量候选查询方法。
3. PostgreSQL 初始化缺少 `run_id` 前导的失败候选 partial index。
4. 显式 result ID PostgreSQL 分支未实现，无法保留 passed 供领域层判定，也不能过滤非法 UUID。
5. 1k/10k Session 事件缺少总数和截断标志，并展开全部来源 ID。
6. Compatibility 两个 stale-runner 测试稳定在超长 Artifact 写入处失败。

GREEN 覆盖：

- InMemory/PostgreSQL 轻量候选语义；
- 默认失败筛选、显式 passed、非法 ID、来源缺失；
- SQL 只读物理列、LEFT JOIN、无 Attempt、partial index；
- 1k/10k 回归条目和来源顺序完整；
- 1k FastAPI 系统 API 调用；
- 10k SSE 预览边界；
- Compatibility 长根目录下 Artifact 路径有界、内容可读、重启/重领逻辑不变。

## 6. 容量基线

指定 Python 3.11 环境、InMemory Store、同机单次 pytest call duration：

| 场景 | 本轮实测 |
|---|---:|
| 服务层创建 1k 失败项回归 | 约 0.09s |
| 服务层创建 10k 失败项回归 | 约 0.62s |
| FastAPI ASGI 创建 1k 失败项回归并序列化响应 | 约 0.11s |

这些数据只证明应用层复杂度和系统接口容量，不等价于真实 PostgreSQL P50/P95/P99。当前环境没有执行生产规模数据库 `EXPLAIN (ANALYZE, BUFFERS)`、多连接压测或真实网络吞吐，因此本轮不虚报数据库性能验收。

## 10. 下一轮方案

下一轮建设项目级“回归中心”，保持模式无关和大数据量可分页：

1. `GET /api/v1/projects/{project_id}/regression-failures`
   - 以一次失败 Result 为主实体；
   - 使用 `(created_at, id)` keyset cursor；
   - 返回失败摘要、证据计数、回归批次数和最新回归状态；
   - 不读取完整 actual/evidence JSON。
2. `GET /api/v1/test-results/{result_id}/regression-context`
   - 懒加载原失败 Result、Artifact 和 Verification；
   - 不向前端暴露本地路径或 MinIO 内部 URI。
3. `GET /api/v1/test-results/{result_id}/regression-batches`
   - 游标分页展示原失败到各次回归结果的时间线。
4. 项目页新增懒加载“回归中心”页签、证据抽屉和批次时间线。
5. 在真实 PostgreSQL 数据集上补 1k/10k 失败占比、并发 1/4/8/12、EXPLAIN BUFFERS 和 P50/P95/P99 基线。

回归中心完成后，再继续接入安全、性能等可选用例驱动模式，并迁移 Smoke regression catalog 到统一 TestRun/Result 视图。

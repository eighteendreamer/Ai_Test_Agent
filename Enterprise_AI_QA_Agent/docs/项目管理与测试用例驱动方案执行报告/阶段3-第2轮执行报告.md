# 阶段 3 第 2 轮执行报告：四模式用例执行适配与结果投影

## 1. 本轮结论

本轮完成了一个 server-owned 的 `RunItem execute` 入口，把已经领取并启动的固定 `TestCaseVersion` 接入现有 `ToolRuntimeService.execute()`，并将 ToolJob 的真实输出、ToolArtifact 和 Verification 投影回 `TestCaseResult`。

本轮没有复制 API、Smoke、UI、Compatibility 四套 Runner，也没有把 ToolJob 的 `completed` 误当成测试通过。四种模式按真实能力分别处理：

- API：从通用步骤/断言编译为 `worker_action=execute_task` 的单任务输入，读取 `task_result.check_results` 判定通过/失败。
- Smoke：将可无损表达的 HTTP/页面步骤编译为单用例 `SmokeExecutionPlan`；无法表达的断言会阻断，不静默丢弃。
- UI：当前 Runner 只有信息探索，`test_execution` 尚未实现；探索成功不会被判为测试通过，结果为 `not_run → blocked`。
- Compatibility：当前入口只把任务派发给外部 Runner，首次调用没有最终断言结果；结果为 `not_run → blocked`，等待外部 Runner 终态链路。

## 2. 新增执行链路

```text
RunItem claimed
  → POST /api/v1/run-items/{item_id}/execute
  → RunItem running（lease_token 校验）
  → CaseExecutionAdapter 构造固定版本执行信封
  → ToolRegistry.get(mode.public_entry_tool_key)
  → ToolRuntimeService.execute()
      → ToolJob queued/running/terminal
      → 现有 ModeRuntime
      → ArtifactStorageService（如已启用）
      → ToolJob.output_payload + ToolArtifact
  → VerificationService.build_results（四个 required runner 映射）
  → TestRunService.complete_item()
  → TestCaseResult.status / actual / evidence_refs / artifact_ids /
    verification_ids / tool_job_id / metrics
```

新增 API：

```text
POST /api/v1/run-items/{item_id}/execute
Body: {"lease_token": "..."}
```

入口只接受已领取的租约，不允许 Agent 自己查询队列或绕过 `TestRunService.complete_item()`。每个 Attempt 使用唯一 `call_id`，不复用旧 ToolJob。

## 3. 通用执行信封

`CaseExecutionAdapter` 将以下内容同时放入 Runner 参数和 `ToolExecutionContext.context_bundle`：

- `project_id、run_id、run_item_id、case_id、case_version_id、content_hash`；
- 固定版本的 `preconditions、steps、assertions、test_data、cleanup`；
- `session_id、turn_id、trace_id、attempt_no`；
- Runner 所需的模式参数。

用例版本不被修改。required 模式的实际执行要求 TestRun 绑定真实 Session，避免 Artifact 下载和 Verification 会话投影使用伪造 session ID。

## 4. 结果与证据规则

### 4.1 通过判定

- ToolJob `completed` 只说明工具流程结束。
- API 通过必须有结构化断言且全部 `passed=true`。
- Smoke 通过必须由 `run_result.verdict=ready` 投影出的 Verification 支持。
- UI 探索完成、Compatibility 任务派发、缺少断言或等待外部 Runner，均不得写入 `passed`。
- Runner 异常或协议失败写入 `error`；无法无损翻译的用例定义写入 `blocked`。

### 4.2 Artifact / Verification

- `artifact_ids` 只来自 `ToolJobService.get_job_detail().artifacts` 的真实记录，不从输出 URI 猜 ID。
- API Runner 报告 Artifact 元数据现在保留 UTF-8 内容，使现有 ToolJob Artifact 持久化可以登记证据。
- Verification 对 API/UI/Compatibility required runner 增加投影；完整 Verification 对象同时写入 `TestCaseResult.actual.verification_results`。
- 有真实 Session 时，Verification 还追加到现有 `session.metadata.verification_results` 并发出 `verification.completed` 事件；会话投影失败不会覆盖已经落库的 TestCaseResult，日志携带 run/item/result/session 上下文。

## 5. TDD 证据

本轮先观察到以下 RED，再实现 GREEN：

1. `CaseExecutionAdapter` 模块不存在：导入失败。
2. API Runner 没有 `worker_action=execute_task`，且缺少通用步骤到 ApiTestTask 的编译。
3. 未绑定 Session 时执行会生成不可下载的伪会话上下文。
4. Smoke/UI 没有从通用步骤构造现有 Runner 参数。
5. API 顶层 `status=completed` 但 `task_result.status=failed` 时，不能按 ToolJob 状态判通过。
6. UI 探索完成和 Compatibility 派发完成不能生成 passed Verification。

## 8. 下一轮建议

1. 增加 Compatibility Runner 回传到 `TestRunItem` 的异步绑定：dispatch/task ID → heartbeat/轮询 → 结构化 case result → 原 lease 完成。
2. 实现 UI `test_execution` 子方向的真实 Playwright 断言执行，再把 UI Verification 从 `not_run` 提升为可判定结果。
3. 建立 run-scoped Verification/Artifact 查询表或资源接口，减少对 Session metadata 的依赖。
4. 阶段 4 增加失败用例回归运行，固定原 `case_version_id`，并建立原始 Result → 回归 Result 关联。
5. 修复既有 Windows 长路径 Artifact 测试后，再执行真实 PostgreSQL 多连接和 1k/10k 用例容量基线。

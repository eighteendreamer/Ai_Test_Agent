# 阶段 4 第 10 轮执行报告：真实 PostgreSQL 导入验收与幂等边界修复

## 1. 本轮方案执行做了什么

本轮重点不是继续扩展业务代码，而是用一次性 PostgreSQL 16 容器验证第 9 轮导入链路的真实数据库行为，并修复真实数据库暴露的根因。

代码改动：

- `PostgresProjectStore._from_row()` 将 PostgreSQL 返回的 `uuid.UUID` 归一化为公开 schema 所需的字符串 ID；
- `LegacySmokeImportPreflightService.apply()` 对 `importable` 和 `already_projected` 两类记录都回到 import ledger 做最终判定；
- 增加回归测试，确保已被 canonical Result 投影的历史运行仍会走 ledger 幂等路径并报告 `already_imported`；
- 增加项目 Store 的 UUID 行归一化测试。

## 2. 真实 PostgreSQL 验证

使用 PostgreSQL 16 Alpine 一次性容器，复用现有 `PostgresProjectStore`、`SmokeCatalogStore`、TestCase/Suite/Run Store 和 `PostgresLegacySmokeImportStore`，验证了：

1. canonical schema 初始化；
2. 真实 PostgreSQL 项目创建；
3. Smoke catalog 历史行写入；
4. 显式 apply 物化 ledger、Case、Version、Suite、Run、Item、Attempt、Result；
5. 第二次 apply 被预检识别为 `already_projected` 后仍回到 ledger，返回 `already_imported=1`；
6. 修改源 metadata 后重复 apply 被 ledger source hash 拒绝；
7. 数据库计数确认 ledger、run、result 均只生成一份。

真实数据库验证完成后已删除一次性容器，未改变本地持久化数据库。

## 3. 发现的失败与根因修复

### 3.1 PostgreSQL UUID 返回类型不匹配

真实项目创建首次失败：psycopg/SQLAlchemy 返回 `uuid.UUID`，而 `ProjectRecord.id` 的公开契约是 `str`。根因在 Store 的数据库行反序列化层，而不是 API 或业务服务。修复为在 `_from_row()` 统一转换 ID 字符串，并增加回归测试。

### 3.2 重复 apply 的预检/ledger 边界

第一次导入成功后，第二次预检会先看到 canonical Result 的 legacy ID，分类为 `already_projected`。旧逻辑只处理 `importable`，因此虽然不写坏数据，却无法报告 ledger 幂等结果。修复为两类记录都进入 writer，由 ledger 决定 `imported` 或 `already_imported`；如果源 hash 变化，则保留失败并记录错误。

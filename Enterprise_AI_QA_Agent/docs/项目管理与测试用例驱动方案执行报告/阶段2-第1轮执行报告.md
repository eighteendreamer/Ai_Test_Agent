# 阶段 2 第 1 轮执行报告：测试用例与固定版本套件

## 1. 本轮结论

本轮完成《方案1.0》阶段 2 的主体能力：项目级测试用例、不可变版本、来源证据、评审启用生命周期、固定版本套件、真实 `generate-test-cases` Skill 生成管线，以及项目页的用例/套件管理入口。

本轮没有实现阶段 3 的 TestRun、RunItem、Lease、Heartbeat、Result，也没有实现阶段 4 的 Regression。现有模式只登记 `case_driven_policy`，尚未在执行入口强制创建 TestRun。

## 2. 已完成范围

### 2.1 用例、版本与来源追溯

- 用例主记录与不可变版本记录分离。
- 生命周期为 `draft → pending_review → active → disabled → archived`；当前提供生成草稿、提交评审、启用和归档接口。
- 新版本追加后主用例回到 `draft`，旧 `active_version_id` 保留，避免已冻结套件被隐式替换。
- 版本记录保存步骤、断言、测试数据、清理动作、SHA-256 内容指纹、来源引用、模型、Prompt 和 Skill 指纹。
- 批量生成采用单事务写入；任一 `case_key` 冲突时整批失败，不留下部分成功数据。

### 2.2 专业生成管线

- 正式加载现有 `generate-test-cases` Skill 内容，并记录内容指纹。
- 复用现有 Model Runtime；模型必须返回满足 Pydantic Schema 的 JSON。
- 非法输出直接报错，不生成固定模板兜底用例，也不虚构测试结果。
- API 文档严格按 `project_id` 隔离；跨项目文档 ID 被拒绝。
- API 文档上下文限制为最多 5 份、单份 12,000 字符、总计 48,000 字符。
- 知识图谱使用有界节点/关系上下文；历史 Session 只读取紧凑摘要，不读取完整消息正文。

### 2.3 固定版本套件与大项目性能

- 套件条目固定 `case_id + case_version_id`，只接受同项目用例的 active 版本。
- 10,000 条套件输入上限由请求 Schema 明确约束。
- 套件创建使用一次批量 active-version 查询，消除逐项 `get_case + get_version` 的 N+1。
- PostgreSQL 用例批量生成使用 2 次 `executemany`（先主记录、后版本记录）；套件条目使用 1 次 `executemany`。
- PostgreSQL 套件列表使用一次套件查询加一次条目批量查询，不按套件逐条查询。

### 2.4 模式策略与项目概览

- `required`：API、UI 自动化、冒烟、兼容性。
- `exempt`：普通对话、代码审批。
- 其他测试模式默认 `optional`。
- 项目概览新增测试用例数和测试套件数。

### 2.5 前端

- 项目详情展示 API 文档、用例、套件、Session、图谱节点和关系统计。
- 用例列表支持分页、搜索、状态过滤、评审和指定版本启用。
- 生成弹窗支持目标、模式和可选模型。
- 套件可跨用例分页保留选择，并提交固定 active 版本。
- 套件列表展示状态、条目数和更新时间。
- 没有加入 Run、Lease、Result、Regression UI。

### 3.5 Mock ASGI 性能基线

通过系统 API 生成、评审并启用 1,000 条用例，随后执行 200 次分页查询，并创建含 1,000 个固定版本条目的套件：

```json
{
  "case_count": 1000,
  "seed_and_activate_ms": 1107.15,
  "list_requests": 200,
  "list_p50_ms": 1.8,
  "list_p95_ms": 2.414,
  "list_p99_ms": 3.511,
  "suite_items": 1000,
  "suite_create_ms": 77.39
```

该结果只代表 InMemory Store + ASGI 路由 + Pydantic 序列化开销。真实 PostgreSQL、MinIO、Memgraph 和模型调用性能尚未在隔离测试环境实测，不能用上述数字替代生产容量结论。

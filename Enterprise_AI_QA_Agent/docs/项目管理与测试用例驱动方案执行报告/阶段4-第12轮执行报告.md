# 阶段 4 第 12 轮执行报告：安全模式用例契约与授权门禁

## 1. 本轮方案执行做了什么

本轮把安全模式从“通用 CaseExecutionAdapter 明确阻断”推进为一个受控的可选用例驱动入口，同时保留安全模式自身的 campaign、Runner 和授权边界。

实现内容：

- `security_testing` 加入 CaseExecutionAdapter 的可选模式白名单；
- 安全用例版本必须提供显式 `runner_arguments.command_profile` 和 target；
- Adapter 将评审后的固定版本编译成结构化 `SecurityTask`，固定 `worker_action=execute_security_task`，不接受用例 payload 直接伪造运行状态；
- `TestRunExecutionService` 执行安全用例前，从服务器 Session metadata 读取 `security_authorization`；
- 新增统一的 `verified_grant_matches_target()`，校验 grant 状态、过期时间、目标主机和可选端口；
- 授权不匹配、授权缺失、Session 缺失时，在 Runner 调用前将 RunItem 记录为 `blocked`；
- 授权通过后，只把服务器可信授权、in-scope safety assessment 和受信任环境传给 ToolRuntime context；
- 增加安全用例编译、授权通过、授权越界和旧契约迁移测试。

## 2. 安全边界与课程来源依据

依据 `项目借鉴/llm-testing-course/安全测试与红队.html` 中“安全基线与深度红队分层”“工具调用需要独立权限验证”的方法，以及现有 `SecurityTargetGuard`、`ExecutionSafetyPolicy`、`PermissionService` 和 `SecurityTask` 契约，本轮没有把“用户/用例中写了已授权”当作授权凭据。

当前链路为：

```text
固定版本 security case
  → 显式 command_profile + target
  → Session 服务器可信 grant 校验
  → host/port scope 匹配与 expiry 校验
  → 传递可信 context
  → security-scan-runner / profile risk gate
  → ToolJob / Artifact / Verification / Result
```

本轮没有执行真实安全扫描命令；契约测试使用 mock Runner，避免测试过程触发未授权目标访问。真实 Runner 的 allowlist、profile 风险审批和 Docker 执行仍由既有安全运行时负责。

## 3. 失败项与修复

首次全量测试有 1 条旧测试失败，原因是它仍断言 security mode “永远没有 adapter”。这与本轮方案变更后的可选安全 case 契约冲突，不是运行时故障。已将断言更新为：缺少显式 profile 时阻断；显式 profile 的 resolver 返回 `security-scan-runner`。修复后全量通过。

## 5. 相比方案 1.0 的进度

阶段 4 的“可选专项模式接入”已完成安全模式的第一层统一契约：安全用例可以进入统一 RunItem 生命周期，但不会取代安全 campaign，也不会绕过授权、profile 风险和目标 allowlist。API、Smoke、UI、Compatibility、Performance 与 Security 现在均有明确的 case execution 能力边界。

## 6. 下一轮要做什么

1. 在隔离、明确授权的本地 mock target 上验证 `security-scan-runner` 的真实 ToolJob/Artifact/Result 投影，不连接公网目标；
2. 为安全 case 增加 profile 能力矩阵，区分 info/low 可自动执行与 medium/high 必须审批；
3. 将 `verified_grant_matches_target()` 的 expiry/host/port 契约与现有 intent/orchestration helper 逐步收敛，减少重复实现；
4. 补充安全用例结果中的 finding/evidence 映射和失败回归关联，继续保持原始 Run/Result 不可变。

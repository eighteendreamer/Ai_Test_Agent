# 阶段 4 第 16 轮执行报告：安全审批等待生命周期

## 1. 本轮方案执行做了什么

第 15 轮已经公开安全 Command Profile 的真实能力矩阵，但高风险安全用例仍可能由 CaseExecutionAdapter 直接进入 Runner：ToolJob 虽能表示 `waiting_approval`，RunItem/Attempt 却没有同一非终态，人工等待会被过早结算为 `blocked`。本轮复用现有 Approval、ToolJob、TestRun 和 lease 设施，补齐统一用例执行链路中的安全审批暂停与恢复。

主要内容：

- `RunItemStatus`、`RunAttemptStatus` 和 `TestRunStats` 增加 `waiting_approval`；
- RunItem/Attempt 保存 `approval_id`、`tool_job_id`，等待期间清空 `lease_expires_at`，保留原 lease token 和 Attempt；
- 高风险 Profile 在 Runner 前创建原 ToolJob 和 Approval，随后把 RunItem/Attempt 原子转为等待态；等待期间不生成 Verification 或 Result，TestRun 保持 `running`；
- 新增 `POST /api/v1/run-items/{item_id}/approval`，批准后复用原 ToolJob、Attempt 和 lease，拒绝后生成唯一 `blocked` Result；
- 批准恢复时重新构造 Runner 调用并校验 Approval scope hash，参数、目标、上下文或用例版本发生变化时拒绝执行；
- `_server_approval_granted` 固定为服务器专属字段：用例 `test_data.runner_arguments` 即使伪造该字段，也会在 Adapter 边界被剥离；
- TestRun 安全目标授权只由服务器 `security_target_allowlist` 动态签发，历史或客户端写入的 Session grant 不再参与执行授权；
- 公开 Session 创建/更新禁止写入 `security_authorization`、`environment`、`resource_scope`，服务器编排使用独立内部入口；安全 Runner 中可信环境优先于用例参数，production 不能被降级为 testing；
- Approval Store 使用 pending→decision compare-and-set：相同决策幂等返回，不同决策返回冲突，PostgreSQL 使用 `WHERE status = 'pending'` 防止并发覆盖；
- 通用 Session 审批 API 拒绝直接处理 `test_run_case_execution` Approval，前端审批面板按 metadata 自动调用 RunItem 专用审批端点；
- ToolJob 不存在时不会先恢复 RunItem；审批已决策但 RunItem 仍等待时可安全重试；
- `resume_waiting_approval()` 只对同 Approval、有效 claimed lease 和同一 claimed Attempt 提供幂等重放，不放宽 queued/expired/terminal；
- 恢复同一 Attempt 时保留首次 `started_at`，避免人工审批等待后覆盖真实执行起点；
- waiting item 不进入 expired lease reaper，取消运行时 RunItem 与 Attempt 一起转为 cancelled；
- 前端同步 `waiting_approval` 状态、统计、Approval/ToolJob 字段和专用审批 API 类型。

本轮没有新增安全专属 Run/Result 表，没有复制 Session 审批框架，也没有引入新依赖。

## 5. 本轮失败定位与根因修复

1. 审批 API 红测返回 404：根因是只有 pending 响应模型，没有 RunItem 审批决策路由。新增专用路由并同步前端调用。
2. Approval 可被重复覆盖：InMemory/PostgreSQL `resolve_approval()` 原来无条件写状态。改为 pending compare-and-set，同决策幂等、异决策冲突。
3. 通用 Session 审批可绕过 RunItem 恢复：Approval 会已 resolved，但 RunItem 永久等待。SessionService 识别 `metadata.source` 并要求使用专用端点，前端消费者同步分流。
4. 恢复同 Attempt 覆盖 `started_at`：二次 start 无条件写当前时间。改为只在首次启动时赋值。
5. ToolJob 暂时不可见时 RunItem 过早恢复：增加 ToolJob 预检，缺失时保持 waiting，可在同 Approval 上重试。
6. 用例可伪造 `_server_approval_granted`：根因是 Adapter 原样复制 `runner_arguments`。现在同时从 Runner 顶层参数和测试用例信封中剥离，仅审批恢复路径能由服务器重新注入。
7. Session metadata 可伪造安全授权和环境：根因是公开 Create/PATCH 与服务器可信上下文共用写入口。现在公开入口拒绝服务器专属键，TestRun 授权改为服务器 allowlist 动态签发，Runner 以可信环境优先。
8. 指定 Python 环境执行 `python -m ruff` 失败：该环境未安装 Ruff；查证项目机器已有全局 Ruff 后改用全局可执行文件完成本轮文件检查，没有为 lint 临时新增依赖。`tool_runtime_service.py` 的 2 条 Ruff 告警在基线提交中已可复现，本轮未做无关清理；除此文件和 `src/main.py` 既有 bootstrap E402 外，其余本轮 Python 文件全绿。

## 6. 局部影响评估

- 修改只作用于 TestRun 安全用例执行、Approval Store 决策语义和前端审批分流；普通对话、代码评审和低风险安全 Profile 不增加审批门禁；
- Case-driven `security_testing` 现在要求服务器配置非空 `security_target_allowlist`；这是安全边界收紧，未配置时明确 blocked，不再接受 Session metadata 充当授权；
- 通用 Approval Store 的同决策幂等、异决策冲突属于收紧并发一致性，不改变合法首次审批契约；
- `waiting_approval` 不进入 lease reaper，避免人工等待被误回收；取消运行仍能终止 waiting Attempt；
- 没有更改 TestCase 生命周期、套件版本冻结或通用失败回归语义；
- 没有新建分支、升级依赖、修改数据库物理 schema 或新增第二套执行流程。

## 7. 下一轮建议

1. 优先补齐取消协调：Run 取消时同步终结 pending Approval、取消 ToolJob，并提供失败可重试的补偿/对账路径；
2. 为拒绝决定增加持久化待终结状态或 outbox，确保服务在 Approval CAS、ToolJob denied、blocked Result 任一步崩溃后都能自动补偿且只产生一个 Result；
3. 在隔离真实 PostgreSQL 中验证 Approval CAS、RunItem waiting/resume、双审批竞争和服务重启恢复，并记录多连接 P50/P95/P99；
4. 增加真实 ToolJob + 本地授权安全 Profile 的系统执行，验证批准只执行一次、拒绝不启动 Runner、Artifact/Verification/Result 证据一致；
5. 上述恢复专项通过后，再回到知识图谱 `project_scope → project_id`、UI Automation 和 Compatibility 的方案直接缺口。

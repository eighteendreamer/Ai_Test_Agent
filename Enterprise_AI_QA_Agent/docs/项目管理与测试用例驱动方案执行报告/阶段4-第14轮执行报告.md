# 阶段 4 第 14 轮执行报告：安全 Runner 证据链

## 1. 本轮方案执行做了什么

本轮补齐了 `security-scan-runner` 从真实工具输出到统一 Verification 的映射。此前安全 Runner 已能在本地授权目标上完成 Docker 执行并产出结构化结果，但 VerificationService 没有对应分支，导致成功的安全 RunItem 在用例执行链路中最终被判为 `blocked`。本轮修复了这个根因。

主要内容：

- `VerificationService.build_results()` 增加 `security-scan-runner` 分发；
- 新增安全 Runner 证据映射：`runner_success`、`finding_count`、`parsed_field`；
- 支持 `equals`、`not_equals`、`contains`、`not_contains`、`lt`、`lte`、`gt`、`gte` 比较操作；
- 只有 Runner 明确成功、且全部声明断言均有支持并通过时，Verification 才为 `passed`；
- Runner 失败或显式断言失败映射为 `failed`；部分断言可识别但仍有未知断言时映射为 `partial`；没有断言时映射为 `not_run`；
- Verification evidence 保留 ToolJob 标识、命令 profile、target 和 finding 数量，metadata 保留逐条断言实际值与结果，便于审计和回归定位；
- 增加安全 Verification 单元测试，覆盖成功、finding 阈值失败、未知断言、Runner 失败、无断言五类路径。

## 2. 真实执行链路验证

本轮使用本地 `ThreadingHTTPServer` 作为唯一目标，并通过真实 Docker 安全 Runner 执行 `http_headers_probe`。目标为 `127.0.0.1`，未访问公网。真实执行结果包括：

- ToolJob `status=completed`；
- Runner `ok=true`、`semantic_success=true`、`exit_code=0`；
- 返回结构化 `parsed_result`、`findings` 和执行指标；
- 结果可继续进入 Artifact、Verification、Result 链路。

这次验证确认了问题不在 Runner 或授权门禁，而在 Verification 层缺少 `security-scan-runner` 的证据投影。

## 4. 下一轮建议

1. 建立安全 command profile 能力矩阵，明确每个 profile 可产出的 parsed fields、findings 类型和可用断言；
2. 将审批等待状态接入 RunItem/ToolJob 的 lease 与恢复机制，验证长时间人工审批不会误判超时；
3. 为安全失败用例增加受控回归入口：复制原始版本、绑定新 Attempt、保留前后证据并禁止复用已完成版本；
4. 增加真实 PostgreSQL 下的 Verification/Result 持久化验收，覆盖重试、幂等和并发回归；
5. 在前端结果面板展示逐条安全断言、finding 和原始 Artifact 引用，避免只显示摘要文本。

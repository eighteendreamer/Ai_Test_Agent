# 阶段 4 第 1 轮执行报告：失败项独立回归与结果关联

## 1. 本轮结论

本轮完成了失败测试用例的独立回归闭环：已结束的普通运行或回归运行，可以从 `failed / error / blocked` 结果创建新的回归运行；默认继续执行原失败时冻结的 `case_version_id`，原 Run、RunItem 和 Result 均不修改。

新增链路：

```text
已结束 TestRun
  → 选择 failed / error / blocked Result
  → POST /api/v1/runs/{run_id}/regression
  → 创建 run_kind=regression 的新 TestRun
  → 固定原 case_version_id（或显式选择当前 active version）
  → 新 RunItem 记录 regression_source_result_id
  → 原子领取、执行、完成
  → 新 Result 继承 regression_source_result_id
  → 保留“原失败证据 → 回归结果”关联
```

项目测试历史页现在区分普通运行和回归运行，显示 `parent_run_id`，并为存在失败、错误或阻塞结果的终态运行提供“一键失败项回归”。

## 2. 领域与 API 契约

新增请求模型 `RegressionRunCreateRequest`：

- `result_ids`：可选；为空时选择该 Run 的全部 `failed / error / blocked` 结果，显式传入时会校验结果确实属于父 Run 且状态可回归。
- `version_overrides`：可选；键为 `case_id`、值为 `case_version_id`。显式覆盖必须属于所选结果、属于同一项目，并且是用例当前启用版本。
- `session_id`：可选；显式指定时必须存在且绑定同一项目，否则拒绝创建。

新增 API：

```text
POST /api/v1/runs/{run_id}/regression
```

回归运行支持继续创建回归，形成 `parent_run_id` 链。创建前要求项目仍为 `active`；父 Run 必须已经 `completed` 或 `cancelled`。来源 RunItem 缺失时在排序前给出带 ID 的上下文错误，不再暴露裸 `KeyError`。

## 3. 不可变性与版本策略

- 原 Run、RunItem、Attempt、Result 永不重置或覆盖。
- 默认固定 Result 中记录的原 `case_version_id`，避免用例版本隐式漂移。
- 只有调用方显式提交 `version_overrides` 时才允许改用新版本。
- 新版本必须是该 TestCase 当前 `active_version_id`；历史版本、其他用例版本和跨项目版本都会被拒绝。
- 新 RunItem 与新 Result 都保存 `regression_source_result_id`，使来源证据和回归结果可以双向追溯。

## 4. PostgreSQL 与大项目性能

为避免回归中心依赖 JSONB 全表扫描，本轮在 PostgreSQL 增加并同步写入以下物理列：

- `agent_test_runs.parent_run_id`
- `agent_test_run_items.regression_source_result_id`
- `agent_test_case_results.regression_source_result_id`

初始化采用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 兼容既有数据库，并为三个关联列建立只包含非空值的 partial index。Run/Item 的 INSERT 与 UPDATE、Result 的 INSERT 均同步物理列和 JSONB `record`。

本轮尚未宣称完成超大回归批次性能验收：`create_regression()` 当前会读取完整父 `TestRunDetail` 后在应用层筛选，时间和内存复杂度为 O(父 Run 条目数)。索引为下一轮数据库侧失败结果分页查询提供了基础，但仍需补充批量 INSERT、1k/10k 用例容量基线和真实 PostgreSQL 多连接压测。

## 5. 日志与 SSE

- 创建成功写入结构化日志 `test_regression_run_created`，包含 project、run、parent run、来源结果、版本覆盖数量和条目数量。
- 若回归 Run 绑定 Session，则通过现有 SessionStore 追加 `test_run.regression_created` 事件。
- 后续领取、启动、完成、租约恢复继续复用既有 TestRun SSE 事件链，不新增第二套事件机制。

## 6. TDD 证据

本轮新增与补强测试均先观察 RED，再实现 GREEN：

1. PostgreSQL 初始化缺少三类回归物理列和索引，契约测试失败。
2. Run/Item 的 INSERT、UPDATE 只写 JSONB，物理关联列缺失，写入同步测试失败。
3. Result 对象已有来源字段，但结果 INSERT 未持久化该物理列，完成链路测试失败。
4. 损坏的历史 Result 指向不存在 RunItem 时，排序阶段只抛出裸 UUID `KeyError`；修复后返回 `Regression source run item not found: <id>`。

测试覆盖：

- 默认只回归失败项并固定原版本。
- 原失败 Run/Result 不修改。
- 新回归 Result 关联原 Result。
- passed Result 不允许回归。
- 显式新版本必须是当前 active version。
- 来源 RunItem 损坏时错误上下文完整。
- FastAPI 系统 HTTP 调用创建回归运行。
- PostgreSQL 初始化、创建、更新、结果完成的 SQL 契约。

## 9. 下一轮方案

1. 优先增加数据库侧失败结果查询与分页：按 `run_id + status` 读取所需 Result/Item，避免完整加载父 RunDetail。
2. 增加回归 RunItem 批量写入和 1k/10k 用例容量基线，记录创建耗时、领取吞吐、P50/P95/P99、错误率和数据库连接占用。
3. 建设回归中心详情 API 与前端视图，展示原失败 Result、Artifact、Verification、各次回归 Run 和最新状态。
4. 修复 Compatibility Runner 的 Windows Artifact 长路径根因，使后端全量测试恢复全绿。
5. 继续阶段 4：接入安全、性能等可选用例驱动模式，并将现有 Smoke regression catalog 投影到统一 TestRun/Result 视图。

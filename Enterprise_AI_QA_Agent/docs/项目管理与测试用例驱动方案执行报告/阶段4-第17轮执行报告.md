# 阶段 4 第 17 轮执行报告：审批拒绝恢复与取消补偿

## 1. 本轮方案执行做了什么

第 16 轮已建立 `waiting_approval` 非终态，但审批拒绝和运行取消仍存在跨存储崩溃窗口：拒绝路径会先恢复原租约并重新启动条目，取消路径只更新 TestRun 而不清理 Session Approval 与 ToolJob。本轮围绕方案 1.0 的“状态生命周期稳定、结果入库、失败回归可追溯”要求，修复这两个 Important。

主要变更：

- `TestRunStore` 增加 `complete_denied_approval()`：InMemory 与 PostgreSQL 都在同一存储事务中锁定 RunItem/Attempt，创建唯一 `blocked` Result，并把 Item、Attempt 一起终结；重复调用按已有 `result_id` 幂等返回，不重建结果。
- 拒绝审批路径不再调用 `resume_waiting_approval()` 或再次 `start_item()`；先把 ToolJob 标记为 `denied`，再调用原子拒绝终结接口，适配器不会执行。
- `TestRunService.initialize()` 增加启动对账：扫描 Approval 已是 `denied` 但 RunItem 仍为 `waiting_approval` 的记录，补偿 ToolJob 与唯一 `blocked` Result；任一步失败会留下结构化日志并让启动失败，下一次启动可重试。
- `cancel()` 在 RunStore 原子取消 Run/Item/Attempt 后，对 pending Approval 执行 CAS 拒绝、对非终态 ToolJob 执行取消；外部清理失败会带 RunItem、Approval、ToolJob 上下文抛出错误，后续调用或启动对账可补偿。
- 启动扫描已取消但尚未完成外部清理的条目，并写入 `resource_cleanup_completed_at`。PostgreSQL 增加 waiting/cancelled 补偿查询的部分索引，避免历史数据增长导致每次启动全表处理。
- `main.py` 将既有 `ToolJobService` 注入 `TestRunService`；没有新增依赖、独立审批表或第二套执行流程。
- 补充拒绝幂等、进程重启恢复、取消幂等、取消后重启补偿和“不启动适配器”回归测试。

## 5. 本轮失败定位与根因修复

1. 拒绝审批红测发现 `resolve_item_approval()` 调用了 `resume_waiting_approval()`，并把等待条目重新 `start_item()`；根因是拒绝与批准共用“恢复租约”流程。修复为先拒绝 ToolJob，再走独立的 `complete_denied_approval()` 原子终态转换。
2. 重启恢复红测发现 Approval CAS 成功后若进程退出，RunItem 会永久停在 `waiting_approval`；根因是跨 Session、ToolJob、RunStore 没有持久化事实对账。修复为启动扫描 `denied Approval` 并幂等补偿 ToolJob/Result。
3. 取消重启红测发现 `cancel_run()` 提交后外部资源无人清理；根因是取消只覆盖 RunStore。修复为取消后清理 Approval/ToolJob，并为未完成清理的取消条目增加持久化完成标记和启动补偿。
4. 代码质量检查初次发现哈希直接对任意 payload 值做 `json.dumps` 可能遇到 datetime；改为先通过 `RunItemCompletion.model_dump(mode="json")` 规范化，再计算确定性哈希。

## 6. 局部影响评估

- 普通对话、代码审批和不使用 TestRun 的模式不受审批门禁影响；只有已经绑定 Approval/ToolJob 的测试条目进入补偿逻辑。
- `TestRunService` 新增可选 `ToolJobService` 依赖，保持现有测试和非 ToolJob 场景可构造；生产启动入口使用既有服务实例注入。
- `resource_cleanup_completed_at` 是 RunItem 的可选新增字段，旧 JSON 记录默认 `NULL`，不改变已有运行状态和领取条件。
- PostgreSQL 只新增索引和 JSONB 记录字段，不创建新的业务表；查询按状态和未完成标记收敛，降低大项目启动扫描成本。
- 补偿失败不会被静默吞掉：日志包含 Run/Item/Approval/ToolJob 上下文，并保留未完成标记供重试。

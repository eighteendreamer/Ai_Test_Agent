# 阶段 4 第 3 轮执行报告：项目级回归中心

## 1. 本轮结论

本轮完成项目级“回归中心”，把上一轮已经具备的失败项回归能力升级为可查询、可追溯、可分页的专业操作界面：

1. 项目维度分页查询 `failed / error / blocked` Result；
2. 失败项列表直接返回用例标题、证据计数、回归批次数和最新回归状态；
3. 原失败证据与 Verification 按需加载，不把完整 `actual` 放入列表或公开响应；
4. 回归批次按时间线独立分页；
5. 项目页新增懒加载“回归中心”、状态/模式筛选、证据抽屉和同源 Run 批量回归。

原 Run、原 Result、原用例版本仍保持不可变；本轮没有把已完成条目重置为可领取状态，也没有复用原 RunItem。

## 2. 新增系统接口

### 2.1 项目失败结果 Feed

```text
GET /api/v1/projects/{project_id}/regression-failures
```

查询特性：

- 以失败 Result 为主实体，只选择 `failed / error / blocked`；
- 支持 `failure_status`、`mode_key`；
- 使用 `(result.created_at, result.id)` keyset cursor；
- 单页上限 200；
- 只投影列表需要的标量和 JSONB 数组计数；
- 通过 `LEFT JOIN LATERAL` 汇总回归次数和最新回归状态；
- 不读取完整 RunDetail、Attempt 或 Result `actual`。

服务层按单页 case_id 批量补齐 `case_key / case_title`，不会为每行单独查询用例。

### 2.2 失败上下文

```text
GET /api/v1/test-results/{result_id}/regression-context
```

返回：

- Result/Run/Case 标识、失败状态、摘要、错误和安全 metrics；
- Evidence 的公开 `type / id / label`；
- Artifact ID 和既有公开下载 API 链接；
- Verification 的结论摘要和计数。

明确不返回：

- 完整 `actual`；
- Evidence `uri / metadata`；
- Verification `metadata / evidence` 内部细节；
- MinIO 内部 URI、`file://` 或 Windows 本地绝对路径。

服务端统一执行窄范围脱敏，前端不承担安全门卫职责。Artifact 只有在来源 Run 绑定 Session 时才生成：

```text
/api/v1/sessions/{session_id}/artifacts/{artifact_id}/content
```

### 2.3 回归批次时间线

```text
GET /api/v1/test-results/{result_id}/regression-batches
```

以关联原失败 Result 的 child RunItem 为时间线实体，使用 `(child_run.created_at, child_item.id)` keyset cursor，返回 Run、RunItem、Result、固定用例版本及状态，不加载完整 Run JSON。

## 3. PostgreSQL 查询与索引

新增两个面向回归中心的 partial covering index：

```sql
ON agent_test_case_results (run_id, created_at DESC, id DESC)
INCLUDE (status, case_id, case_version_id, run_item_id)
WHERE status IN ('failed', 'error', 'blocked');

ON agent_test_run_items
  (regression_source_result_id, updated_at DESC, id DESC)
INCLUDE (run_id, status, result_id, case_version_id)
WHERE regression_source_result_id IS NOT NULL;
```

专业依据与本系统对齐：

- `项目借鉴/llm-testing-course/性能测试-通用篇.html` 明确强调接近真实数据量、慢查询和索引验证；本轮因此没有用 offset 深分页，也没有以小数据“推断”生产数据库性能。
- 查询形状以当前 PostgreSQL 表结构、上一轮轻量候选实现和可复现 SQL 契约测试为事实来源。
- 当前环境未提供生产规模 PostgreSQL 数据集，本轮没有虚报 `EXPLAIN (ANALYZE, BUFFERS)`、P50/P95/P99 或并发容量结论。

## 4. 前端回归中心

项目详情页新增第四个资源页签“回归中心”：

- 首次切换页签时才加载失败 Feed；
- 支持失败状态和测试模式过滤；
- 使用服务端 next cursor 前后翻页；
- 表格显示失败摘要、Evidence/Artifact/Verification 数量、回归批次数和最新状态；
- 点击失败项时才并发加载 Context 与首批时间线；
- Artifact 只打开服务端公开下载链接；
- 时间线后续页使用“加载更多”继续 keyset 查询。

批量回归只允许选择同一个 `source_run_id` 的失败项；跨父 Run 的失败项会在选择阶段被禁用，服务端仍以既有 `POST /runs/{run_id}/regression` 契约做最终校验。

## 5. TDD 证据

本轮实际观察的 RED：

1. PostgreSQL Store 缺少项目失败 Feed；
2. 初始化 SQL 缺少失败 keyset 与最新回归查询索引；
3. Context 系统 API 返回 404；
4. Batch 时间线系统 API 返回 404；
5. PostgreSQL 缺少 Batch keyset 查询；
6. PostgreSQL 缺少单 Result 轻量读取；
7. 前端缺少回归 API 类型与方法；
8. 项目页缺少懒加载回归页签、证据抽屉和时间线；
9. Context metrics 可泄漏 `minio://`，Evidence label/Verification summary 可泄漏 Windows 本地路径。

对应 GREEN 覆盖：

- InMemory 与 PostgreSQL Store 一致语义；
- 两组 keyset cursor 两页无重复；
- SQL 的 JOIN/LATERAL/ORDER/LIMIT/参数顺序和 partial index；
- FastAPI 公开响应不含完整 `actual`、MinIO URI 或本地路径；
- 前端 API/类型/懒加载交互静态契约；
- Vue/TypeScript 生产构建。

## 6. 性能与容量判断

本轮对性能采用结构性约束：

| 路径 | 控制方式 |
|---|---|
| 项目失败列表 | keyset、limit ≤ 200、标量投影、单页批量用例查询 |
| 回归次数/最新状态 | LATERAL + `regression_source_result_id` partial covering index |
| 失败证据 | 用户打开抽屉后才读取单 Result record |
| 批次时间线 | 独立 keyset，不加载完整 RunDetail |
| 前端 | 页签、抽屉、后续批次均懒加载 |

这些事实证明查询和内存复杂度不会随“已翻过的页数”线性增加；但没有真实 PostgreSQL 执行计划和并发压测数据，因此不能声称已经完成生产容量验收。

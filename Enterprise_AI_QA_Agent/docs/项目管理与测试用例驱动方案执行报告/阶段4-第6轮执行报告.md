# 阶段 4 第 6 轮执行报告：在线过期租约回收器

## 1. 本轮方案执行做了什么

本轮针对方案中“Worker 崩溃后由租约回收器恢复 queued”的要求，补齐了在线 lease reaper：

- `TestRunService` 增加可配置的后台 lease reaper；
- reaper 复用现有 `TestRunStore.recover_all_expired()` 原子回收能力，不新增表、不新增状态机；
- PostgreSQL 继续通过 `FOR UPDATE SKIP LOCKED` 处理多进程并发回收，InMemory Store 与生产 Store 保持同一协议；
- reaper 启动和停止绑定 FastAPI lifespan，服务退出时显式取消并等待后台任务；
- 每次回收有结构化日志 `test_run_expired_leases_recovered_online`，单次 Store 异常记录 `test_run_lease_reaper_iteration_failed`，不会静默退出；
- 新增 `test_run_lease_reaper_interval_seconds` 配置，默认 30 秒，测试可以注入更短周期；
- 通过 FastAPI `/api/v1/runs/{run_id}` 查询验证回收后的项目运行状态和 attempt 历史。

## 2. 相比方案1.0的进度

本轮完成的是阶段 4 的执行稳定性子项：

```text
Worker 领取
  → lease 过期
  → 在线 reaper 原子回收
  → RunItem 恢复 queued
  → 原 Attempt 标记 expired
  → 新 Worker 可重新 claim
```

这使“心跳续租 + 过期回收 + 新 Attempt”成为完整闭环。原始 Result、已完成条目仍不会被 reaper 触碰，避免误回收已结束用例。

当前阶段 4 仍未完成的内容：

- `security_testing` 尚未接入统一用例适配器，需先完成独立授权门禁和安全 Verification 投影；
- Smoke catalog 尚未迁移到统一 Result 视图；
- 尚未完成真实 PostgreSQL 大规模并发/查询计划容量基线；
- ToolJob heartbeat 失联后的主动取消/隔离策略尚未定义。

## 4. 不合格项与修复方案

本轮没有新增不合格测试。已识别但未在本轮扩大范围处理的问题：

1. `src/main.py` 的 89 项 E402 属于既有启动文件导入路径约束，贸然重排会扩大启动风险；后续单独做启动模块重构与回归。
2. Starlette/httpx 弃用 warning 属于既有依赖兼容问题；后续统一升级/锁定依赖并跑完整 Web 回归。
3. reaper 当前只记录 Store 迭代失败，不主动熔断；后续应增加连续失败计数、健康指标和告警，但不能在失败时误回收。

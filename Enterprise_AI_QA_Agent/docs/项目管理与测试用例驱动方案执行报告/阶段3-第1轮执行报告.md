# 阶段 3 第 1 轮执行报告：用例驱动执行内核与租约安全

## 1. 本轮结论

本轮完成阶段 3 的通用执行内核：TestRun、RunItem、Attempt、Result、固定版本运行快照、原子领取、租约、heartbeat、超时恢复、启动恢复、终态幂等和项目运行历史。

本轮没有把 API、冒烟、UI、兼容性测试步骤写进运行内核。四种 required 模式的 Runner → ToolJob → Artifact → Verification → Result 自动适配留到阶段 3 第 2 轮；阶段 4 Regression 仍未实现。

## 2. 本轮完成内容

### 2.1 通用执行领域

- TestRun 固定 `project_id + suite_id + mode_key`，运行类型当前为 `normal`。
- RunItem 固定套件中的 `case_id + case_version_id`，不会跟随用例最新版本变化。
- Attempt 每次领取创建新记录；租约过期后旧 Attempt 标记 `expired`，原 Item 回到 `queued`，再次领取产生新的 attempt_no。
- Result 保存运行、Item、用例版本、Attempt、状态、实际结果、证据引用、Artifact ID、Verification ID、ToolJob ID、指标和错误信息。
- Result 使用 canonical JSON SHA-256 指纹实现幂等；相同 token 和相同结果重复提交返回原 Result，不同内容或错误 token 返回 409。

运行条目状态：

```text
queued → claimed → running → passed / failed / error / blocked / skipped
                       └──→ cancelled（运行取消）
```

完成后的 Item 不再进入领取查询。测试失败不会把原 Item 重置为 queued；后续失败回归将由阶段 4 创建新 Run。

### 2.2 Worker API

新增：

```text
POST /api/v1/suites/{suite_id}/runs
GET  /api/v1/projects/{project_id}/runs
GET  /api/v1/runs/{run_id}
POST /api/v1/runs/{run_id}/claim
POST /api/v1/run-items/{item_id}/start
POST /api/v1/run-items/{item_id}/heartbeat
POST /api/v1/run-items/{item_id}/complete
POST /api/v1/runs/{run_id}/recover-expired
POST /api/v1/runs/{run_id}/cancel
```

Claim 每次只返回受 `limit <= 100` 限制的用例、固定版本和唯一 lease_token，避免把大项目全部塞入一次 Worker/模型上下文。

### 2.3 PostgreSQL 并发安全

- 复用项目已有 SQLAlchemy QueuePool、psycopg 驱动和 `postgres_connect()` 事务上下文，没有引入第二套数据库依赖。
- 领取在同一事务连接中使用 `FOR UPDATE SKIP LOCKED`，然后批量更新 Item 并批量创建 Attempt。
- 领取前不锁整条 Run，避免所有 Worker 被 Run 行锁串行化。
- 全部状态变更采用统一的 `Item → Run 汇总` 锁顺序，恢复和取消不再反向锁定，降低死锁风险。
- heartbeat、完成、恢复和取消均锁定 Item 并校验状态/lease_token/lease_expires_at。
- 进程启动时自动扫描并恢复过期 claimed/running Item；同时保留按 Run 手工恢复接口。
- 建立项目运行历史、`run_id + status + position` 和活动租约到期索引。

## 4. 性能结果与根因修复

使用系统 ASGI API 和 InMemory mock 构建 1,000 条固定版本用例，执行创建 Run、100 个 Worker 并发领取、1,000 次 start、1,000 次 complete 和终态再领取。

首次结果不合格：

```text
start_and_complete_ms = 115373.50
```

根因：每次 start/complete 为发送事件都重新加载完整 RunDetail，随着 Attempt/Result 增长形成 O(N²)。

修复：Store 增加 O(1) `get_run_record()`，Worker 热路径只读运行头，不加载全部 Item/Attempt/Result。

同一基准修复后：

```json
{
  "case_count": 1000,
  "fixture_setup_ms": 593.90,
  "create_run_ms": 138.89,
  "claim_requests": 100,
  "claim_wall_ms": 239.04,
  "claim_p50_ms": 2.192,
  "claim_p95_ms": 2.749,
  "claim_p99_ms": 3.082,
  "unique_items": 1000,
  "unique_tokens": 1000,
  "start_and_complete_ms": 1541.51,
  "final_status": "completed",
  "passed": 1000,
  "terminal_reclaim_count": 0
}
```

相同 start+complete 链路约改善 74.8 倍。

限制：该数字只代表 InMemory Store + ASGI + Pydantic。SQL 结构测试证明使用同一事务和 `SKIP LOCKED`，但真实 PostgreSQL 多连接并发、连接池和索引性能尚未在隔离测试库执行，不能将上述延迟视为生产指标。

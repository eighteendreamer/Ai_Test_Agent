# API 登录、刷新与多认证依赖来源研究

基线 `3d494671`。本次继续原计划中的鉴权、续期、依赖传值和负向条件保留，不改模型协议，不增加通用 401 重试。

## 查证与设计依据

1. `auth_propagation.py` 由两种协调器共用，但当前条件是“所有未来 auth 任务，或直接依赖来源的任务”。因此 A 登录完成会修改 B 登录的显式 auth_ref，即便 B 不依赖 A；运行中的依赖任务也可能被修改。
2. `DependencyPlanner` 已识别 `CAP_LOGIN` / `CAP_REFRESH_TOKEN`，但未记录刷新所使用登录的依赖，过去靠“所有 auth 都继承最新凭据”维持单登录流程。认证任务调度仍按列表先后，不能代替来源关系。
3. `ApiTaskPool` 已校验依赖图、协调器已按前置状态派发。正式 RunItem `dependencies.py` 同样以冻结依赖和实际输出作为运行依据。认证传播必须读取记录的图，而不是依据“auth 模式”猜测所有任务属于同一账户。
4. 本地 `接口测试-通用篇.html` 的鉴权/越权示例要求区分用户 A 与用户 B，并把缺失、失效 token 的 401 当作负向结果。自动修复每个 401 会破坏这一目标。现有执行器记录状态与断言，重试器不把正常 401 当作网络失败；保留该语义。
5. 现有 `test_api_authentication_live.py` 和 `test_api_worker_auth_refresh_live.py` 已有真实登录→刷新→profile HTTP、Worker 结果和加密凭据存储测试。新测试复用真实 Executor 和已有 ControlledWorkerLauncher，验证两条独立认证链，不增加另一套 Worker 或模型客户端。

## 修复前实际失败

新增 `test_api_auth_lineage_http.py` 原四项 **4 failed，6.17 秒**：

- 本地、Worker 两种分支均将 A 刷新凭据附到 B 的独立登录上，实际 `/b/login` 收到 A 的身份，返回 401；B 刷新与查询被跳过。
- 多个独立认证前置时，当前实现覆盖已经配置的凭据，并修改正在执行的任务。
- 已有 A 登录/刷新/查询和独立负向 401 没有失败，说明问题来自跨链传播，不能用单账户通过证明多认证正确。

随机 token 只存在实际请求与运行内凭据中；证据只记录认证来源标签、状态、次数和脱敏报告，不保存值。

## 依据 → 修复做法

- 传播只跟随任务图中的认证祖先；若刷新依赖登录，刷新来源遮蔽该登录来源。只有唯一的最近认证来源等于本次完成的来源时才更新 auth_ref。没有来源、多独立来源时保留已配置输入；歧义留下结构化日志，不阻断独立任务、不猜账户。运行中和终态条目保持原记录。
- 为既有简单单账户入口，在当前任务中存在唯一同源登录时，刷新任务记录该登录的明确依赖，沿原 pool 状态调度。同源用执行器有效 URL 的 scheme/netloc 判断；多登录或跨来源不猜测刷新关系。
- 不根据接口名生成额外登录步骤，不引入认证配置字段/表或全局 token，不把模型 OAuth 的续期机制套用于被测系统。
- 旧已保存单账户计划缺刷新边时，只在已记录 `refresh_token` 能力且同源登录唯一的情况下投影原单账户来源。新草稿记录真实依赖；旧计划仅用内存投影推导凭据来源，不改冻结边。多个独立登录和跨来源不做旧策略猜测。

# 企业 AI 测试系统升级方案：用例理解、执行补全与需求变更闭环

## 一、升级原则与实际依据

保留现有测试模式、Agent、工具、权限、运行及结果体系。升级重点是完善用例、文档和知识进入 Agent 的链路。

执行主流程：

**理解用户需求 → 当前项目内选取用例 → AI 判断执行逻辑并补齐必要步骤 → 排序并冻结执行依据 → Agent 调用现有工具 → 保存结果与证据。**

生成模板仅用于生成用例。执行读取用例自身的 JSON、执行说明和来源，不读取生成模板。

| 当前实现与依据 | 升级做法 |
|---|---|
| [通用 planner](G:/Code_Warehouse/Ai_Test_Agent/Enterprise_AI_QA_Agent/Agent_Server/src/graph/nodes/planner.py) 当前生成固定说明 | 增加用例理解、执行排序和缺口补全 |
| [用例检索服务](G:/Code_Warehouse/Ai_Test_Agent/Enterprise_AI_QA_Agent/Agent_Server/src/application/test_cases/embedding_service.py) 的提示摘要只展示前六步 | 摘要用于召回；判断与执行读取完整固定版本 |
| [API 前置分析](G:/Code_Warehouse/Ai_Test_Agent/Enterprise_AI_QA_Agent/Agent_Server/src/modes/api_testing_mode/precondition_resolver.py) 主要识别鉴权标记和路径参数 | 保留为辅助线索，不扩展成通用业务规则检查器 |
| 已有正式用例、套件、原子领取、检查点和回归机制 | 在现有链路中扩展 |
| 上传使用 RustFS 保存内容，PostgreSQL 保存目录 | 增加文档版本关联，不引入 Git 保存上传文件 |
| UI 录制和 Docker 测试已有实现 | 先实际验证，再修复确认的缺口 |

上传、目录及对象存储相关测试已验证 **25 项通过**；内存诊断证明现有上传服务能分别保存同名文件，并使用 `difflib` 比较，全程无需 Git。该诊断未验证真实 RustFS/PostgreSQL，也不代表历史版本功能已经实现。

以下新增能力均属于待实施内容。

## 二、JSON 用例与 Agent 执行

### 2.1 默认模板、生成与导入

项目管理增加“用例生成模板”弹窗，提供系统默认模板，支持项目复制、修改写作指导、示例和 JSON 结构。

用例版本保存：

- **业务内容**：完整 `content_json`，支持嵌套结构，保留未知字段。
- **自身说明**：必要的字段含义和执行说明，随用例评审、冻结。
- **治理信息**：正式项目、稳定用例身份、版本、状态、来源及内容哈希。
- **生成记录**：模型、Prompt、Skill、模板版本和生成范围。

前端提供步骤展示、通用 JSON 树和原文视图。模板修改只影响后续生成，不改变已有用例。

生成复用现有服务及 Skill：

**文档快照 → 按模块生成 → 校验与去重 → 草稿 → 评审 → 启用固定版本。**

保存章节、文本块、表格等来源；未处理范围显式展示，失败模块独立重试。旧结构提供兼容读取，正式转换产生新版本，不重写旧版本及哈希。

导入以 `.xlsx` 为主，同时支持 JSON，首期不支持旧 `.xls`：

**选择工作表 → 表头识别与列映射 → JSON 预览 → 校验及重复提示 → 提交草稿。**

提供“每行一条用例”和“用例与步骤分表”两种默认 Excel 格式。保存文件哈希、工作表、行号、映射及错误报告；重复提交保持幂等，编号冲突不覆盖旧用例。未来项目平台数据进入同一导入服务。

### 2.2 用例选取与测试模式分离

执行依据独立于测试模式：

| 执行依据 | 行为 |
|---|---|
| 自由测试 | 沿现有 Agent 流程执行，不注入正式用例作为执行依据 |
| 按用例测试 | 根据用户需求选择当前项目内的正式用例，再规划执行 |

保留现有测试模式。历史 `mode_key` 保留兼容，但不再作为候选召回的硬过滤条件；Agent 根据用例与当前工具能力决定执行方式。

选取流程：

1. 使用会话绑定的正式 `project_id`。
2. 理解用户要求验证的目标、范围和约束。
3. 通过向量召回及编号、标题等查询获得候选。
4. 读取完整固定版本，由 AI 判断相关性。
5. 保存选取理由，进入执行规划。

检索服务故障与没有匹配用例分别呈现。没有目标用例时返回具体缺口，不静默切换为自由测试。

### 2.3 逻辑缺口检测与自动补全

不建立注册、登录、权限、订单等固定检查清单。

AI 判断的核心问题是：

> 按选定用例的操作与预期结果执行，所需条件能否由当前已有信息或前面的执行步骤提供？

#### 检测输入

| 输入 | 内容 |
|---|---|
| 用户需求 | 本次目标、范围及明确约束 |
| 选定用例 | 完整 JSON、自身说明、固定版本及来源 |
| 当前执行信息 | 项目、环境、用户提供的数据及可引用的运行证据 |
| 可查询依据 | 当前项目其他用例、文档、接口信息和录制知识 |

项目资料按需查询。凭据使用现有受控机制，不进入向量索引或普通日志。

#### 检测方法

AI 阅读用例的操作和预期，判断必要条件的来源：

- 当前已提供：直接使用。
- 前面步骤会产生：调整顺序，记录数据传递。
- 没有提供：记录具体缺口，再查找补全办法。
- 条件缺失属于测试目的：保留缺失，不补全。

例如，“未登录访问应拒绝”不补登录；“查询已存在订单并验证详情”需要订单实际存在。

规划只判断逻辑是否连贯。账号、会话、数据是否实际有效，由执行证据确认。

#### 补全方法

AI 针对缺口查询当前项目：

1. 找到合适正式用例：补入执行集合，即使它不直接对应用户原始目标。
2. 没有正式用例，但项目资料或工具结果提供操作依据：补入运行内准备步骤。
3. 必要信息无法取得：保留具体缺口，说明影响哪些执行项；独立部分仍可执行。

新增步骤继续检查逻辑是否连贯。查询、修订受现有 Agent 迭代与超时限制约束；超限保留未解决项，不无限递归。

不能虚构项目接口、页面元素或业务规则。

#### 规划结果与后端职责

沿用现有模型适配器，增加结构化规划结果：

| 内容 | 用途 |
|---|---|
| 执行项 | 目标用例、补入用例或准备步骤 |
| 前后依赖 | 哪一步等待哪一步 |
| 数据来源 | 已有输入或前面步骤的实际输出 |
| 补入理由与依据 | 为什么需要、依据来自哪里 |
| 未解决缺口 | 缺少什么、影响哪些执行项 |

这些字段属于运行计划，不要求所有用例使用同一种业务 JSON 格式。

后端校验项目、版本、引用、依赖循环和顺序，以及前置完成后必要输出是否取得；业务依赖由 AI 结合完整内容判断。

```text
目标：查询已存在订单的详情

已有订单信息：
    查询 → 验证

没有订单信息，有创建订单用例：
    创建订单用例 → 传递实际订单 ID → 查询 → 验证

没有创建订单用例，但项目资料提供创建方法：
    运行内准备步骤 → 传递实际订单 ID → 查询 → 验证

目标是验证不存在订单的错误响应：
    保持不存在条件 → 查询 → 验证错误响应
```

是否还需账号或登录，由具体项目依据决定。

### 2.4 冻结、执行、恢复与回归

规划完成后冻结正式用例版本和计划。后续 Agent 循环不重新召回并替换版本。

正式目标与补入用例继续进入现有套件、RunItem 和原子领取流程。准备步骤附属相关条目，保存检查点及证据，不虚构 `case_id`，不自动启用为正式用例。

执行规则：

- 有依赖的条目等待必要前置和输出；展示排序不能代替执行约束。
- 独立条目使用现有并发能力。
- 前置失败只影响相关执行项。
- 准备数据默认在相关条目范围使用，不自动跨条目共享。
- 已成功的副作用操作恢复时读取检查点；结果不确定时先查证。
- 新缺口可修订尚未执行部分，追加计划修订及理由，保留原计划和已完成证据。
- 清理依据用例要求及实际创建的数据安排；共享数据消费完毕后清理。

计划状态同步到图状态、`TurnState`、循环重组、持久快照和审批恢复。新运行由 Agent 理解用例后执行，不强制编译为模式参数；旧运行保留原策略恢复能力。

报告区分目标、补入用例、准备步骤、预期、实际和证据。准备成功不计为目标通过。失败回归创建新运行，重新确认必要前置，保留原失败结果。

## 三、文档版本、差异与需求追踪

### 3.1 上传文档独立保存版本

上传文件使用现有对象存储和数据库保存。**上传、版本保存及比较均不依赖 Git。**

当前需要升级的是：

- 将独立上传记录关联成同一文档的历史版本。
- 在转换前保存原件，转换结果另存。
- 将生成来源和差异比较关联到明确版本及解析快照。

流程确定为：

1. 首次上传创建项目所属文档身份及 V1。
2. 在文档详情选择“上传新版本”，明确关联当前文档。
3. 新原件保存为 V2，使用独立对象键；V1 保留。
4. 数据库记录文档 ID、版本 ID、前一版本、对象地址、字节哈希、上传时间及来源。
5. 解析成功后默认比较新旧相邻版本，也允许选择历史版本。

通用上传入口可以推荐已有文档，歧义时由用户选择。不能仅凭文件同名自动覆盖或合并。

同一文档上传相同原件时提示重复并返回已有版本；解析器或选项变化仍可新增解析快照。保存或解析失败明确呈现，不能报告比较成功。

原件、转换结果、解析快照分别保存。OpenAPI、Postman、HAR 转 Markdown 属于派生内容；项目 URL 等元数据修改不能覆盖原件。历史原件缺失时如实标注。

### 3.2 Git 作为独立可选来源

用户选择项目已登记本地仓库的路径和 commit，系统只读获取文件，保存来源 commit、路径和 blob 身份，再进入文档保存、解析、比较及影响分析服务。

不向仓库写入上传文件，不克隆、不 checkout、不提交、不自动同步。

现有代码审查的本地仓库能力作为实现参考，正式文档 Git 导入入口需要新增。

默认分别管理上传文档与 Git 导入文档。只有用户明确选择“导入为该文档的新版本”，才关联到已有文档。

**两种来源复用处理服务，不要求混用，也不要求上传文件经过 Git。**

### 3.3 轻量解析工厂

统一接口输入原件和解析选项，输出文本块、章节、表格、来源位置、解析器版本、能力及警告。

| 格式 | 首期实现 |
|---|---|
| Markdown | 文本解析 |
| DOCX | `python-docx` |
| 文本型 PDF | `pypdf` |
| 扫描 PDF | 明确提示首期不支持 OCR |
| Docling | 预留 HTTP 注册、能力声明和结果转换；首期不部署 |

解析放入可终止的独立任务进程，配置超时、内存、CPU、输入和输出限制。API 返回任务身份，父进程负责超时及进程树回收。

解析器或选项改变产生新快照；重解析历史原件也追加快照，不重写历史依据。无法可靠提取的结构给出警告。

### 3.4 确定性差异与影响判断

上传文档使用标准库 `difflib` 比较保存的文本或解析快照，不依赖 Git。Git 导入使用相同服务；同一仓库两个 commit 的比较可附加 Git diff 证据。

- 文本原件提供章节、行和字符差异。
- DOCX/PDF 提供原始抽取文本及结构差异，同时保留原件。
- 原文差异与确定性归一差异分别查看，保留来源映射。
- 不让 AI 改写文档后再比较。

AI 同时读取**现有用例、当时编写来源、具体文档变化**判断影响，并引用位置；同时考虑变化是否已在当前环境生效。

| 影响 | 处理 |
|---|---|
| 无影响、轻微影响 | 继续执行，保存说明 |
| 已生效的重大影响 | 停止相关版本在对应环境执行，生成更新草稿 |
| 尚未实现或尚未生效 | 保留适用于当前环境的旧版本，新草稿关联目标版本 |
| 无法确定 | 提交评审；没有明确失效证据时不全面阻断项目 |

新增需求生成新草稿；修改需求生成原用例的新版本草稿；删除需求提出停用候选。保留历史版本、原运行依据和结果。

### 3.5 需求追踪

保存稳定需求身份、需求版本、验证点及用例版本关联。

矩阵展示设计覆盖、未覆盖项、执行证据和待复核状态。关联数量与实际验证结果分别呈现，旧需求的通过结果不能证明新需求已通过。

## 四、已有测试链路的验证与补强

| 子系统 | 实施内容 |
|---|---|
| UI 录制 | 在 DeepSeek 官网进行低频人工操作，验证操作、元素及响应、清洗、入库、AI 查询和使用。可控页面补动态 DOM、iframe、连续点击及结束排空场景 |
| 录制完整性 | 核对客户端、服务端、数据库和固化结果，验证动作与响应关联、最后一步落库、截断及遗漏提示 |

| Agent API | 修复 endpoint 与 task 身份对应问题，验证鉴权、响应提取、依赖传值、恢复和报告；关键传值记录明确来源 |
| 性能与安全 | 保留 Docker 工具及授权机制，贯通调用、退出码、stdout/stderr、原始工件、解析及报告；未采集指标显示缺失 |

意图识别、用例规划、Agent 推理和工具后推理允许作为不同的合法调用。历史消息按身份保留，不能按文本相同简单去重。日志不输出凭据。

借鉴实现中的模块化生成、增量更新、追踪矩阵、场景编辑和报告能力归入上述模块；Mock、定时任务和脚本导出作为后续候选。

## 五、接口、实施顺序与验收

### 5.1 接口与兼容

扩展现有入口：

- 执行请求增加 `execution_basis` 和可选用例、套件引用；旧请求保留兼容行为。
- 用例版本增加完整 JSON、自身说明和精确来源。
- 运行增加规划结果、计划修订、必要依赖及准备检查点。
- 项目管理增加生成模板、导入预览及错误报告。
- 文档增加上传新版本、版本列表、解析快照、比较及影响记录。
- Git 导入是独立可选入口，不成为上传接口的依赖。
- 追踪关系关联具体需求版本、用例版本和证据。

后端契约、数据库、前端类型、调用方、状态恢复和测试同步更新。耗时任务复用现有任务查询及事件机制。

### 5.2 实施顺序

| 阶段 | 交付 |
|---|---|
| P0 | 采集真实失败样本，修复重复组装及 API 依赖身份问题；实测录制和 Docker |
| P1 | 默认模板、自定义 JSON、前端渲染、Excel/JSON 导入 |
| P2 | 项目内选取、完整读取、AI 逻辑检测、补全及 Agent 执行 |
| P3 | 上传版本管理、原件保存、解析工厂、确定性差异；接入 Git 可选来源 |
| P4 | 三方影响判断、需求追踪、增量草稿和回归 |
| P5 | 录制场景、知识查询、传值和报告完善 |

使用增量迁移，保留历史字段、哈希、套件和结果。按项目启用新策略；关闭新入口保留已存数据，旧运行按原策略恢复。

### 5.3 验收要求

| 场景 | 必须证明 |
|---|---|
| 已有必要数据 | 不添加多余准备 |
| 前面用例产生数据 | 正确排序并传递实际输出 |
| 前置不直接符合用户目标 | 必要时仍补入，理由可查 |
| 没有正式前置用例 | 按可靠项目依据补运行内步骤 |
| 刻意未登录或使用无效数据 | 保留负向条件及预期 |
| 信息或依据不足 | 显示具体缺口，不编造操作 |
| 摘要遗漏关键步骤 | 完整版本读取后正确判断 |
| 前置成功但输出缺失 | 不将依赖视为满足 |
| 中断恢复 | 不盲目重复副作用操作 |
| 多 Worker 领取 | 依赖未满足的条目不提前执行 |
| Git 未配置或不可用 | 上传、保存版本及比较正常运行 |
| 上传同一文档的新版本 | 原件和旧版本均保留 |
| 同名不同文档 | 不误合并 |
| 重复上传相同原件 | 不生成重复版本 |
| 解析失败或能力不足 | 明确显示并允许重试 |
| Git 导入 | 仓库只读，明确关联后才成为已有文档新版本 |
| 模板修改、项目隔离 | 旧用例执行含义不变，数据不跨项目 |

## 实施时新增的用户约束

每一步先深度调研并确认方案与代码事实，再实施和测试；测试须同时覆盖逻辑与实际功能输入。可编辑配置存 MySQL，业务数据、版本、运行及证据元数据存 PostgreSQL。原件和大工件沿用现有对象存储，其他投影可重建。详细分库和验收状态见 IMPLEMENTATION.md。

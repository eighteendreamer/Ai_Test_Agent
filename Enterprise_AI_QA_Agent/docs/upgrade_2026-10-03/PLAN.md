## 二、JSON 用例与 Agent 执行

### 2.1 默认模板、生成与导入

项目管理增加“用例生成模板”弹窗，提供系统默认模板，支持项目复制、修改写作指导、示例和 JSON 结构。

用例版本保存：

- **业务内容**：完整 `content_json`，支持嵌套结构，保留未知字段。
- **自身说明**：必要的字段含义和执行说明，随用例评审、冻结。
- **治理信息**：正式项目、稳定用例身份、版本、状态、来源及内容哈希。
- **生成记录**：模型、Prompt、Skill、模板版本和生成范围。

前端提供步骤展示、通用 JSON 树和原文视图。模板修改只影响后续生成，不改变已有用例。

生成开始时读取一次项目模板，并将实际指导、示例、修订号及哈希冻结到用例的生成记录。生成时参考的执行说明应保存为用例自身说明，编辑时随新用例版本保存。运行读取已冻结的用例内容和自身说明，不能为了补字段再加载当前模板；模板快照仅供追溯编写依据。

生成复用现有服务及 Skill：

**文档快照 → 按模块生成 → 校验与去重 → 草稿 → 评审 → 启用固定版本。**

保存章节、文本块、表格等来源；未处理范围显式展示，失败模块独立重试。旧结构提供兼容读取，正式转换产生新版本，不重写旧版本及哈希。

导入以 `.xlsx` 为主，同时支持 JSON，首期不支持旧 `.xls`：

**选择工作表 → 表头识别与列映射 → JSON 预览 → 校验及重复提示 → 提交草稿。**

提供“每行一条用例”和“用例与步骤分表”两种默认 Excel 格式。保存文件哈希、工作表、行号、映射及错误报告；重复提交保持幂等，编号冲突不覆盖旧用例。未来项目平台数据进入同一导入服务。

本阶段确认的实现细节：导入策略及项目格式存 MySQL；原件存 RustFS；项目所属来源、固定预览批次与草稿存 PostgreSQL，批次提交与草稿写入处于同一事务。解析由独立受限进程执行。列映射未指定时可自动识别，明确选择“不映射”时必须保留该选择；原始列内容仍作为来源证据保存。更改映射需要重新预览，提交读取已冻结预览，不重新读取模板或当前导入配置。

### 2.2 用例选取与测试模式分离

执行依据独立于测试模式：

| 执行依据 | 行为 |
|---|---|
| 自由测试 | 沿现有 Agent 流程执行，不注入正式用例作为执行依据 |
| 按用例测试 | 根据用户需求选择当前项目内的正式用例，再规划执行 |

保留现有测试模式。历史 `mode_key` 保留兼容，但不再作为候选召回的硬过滤条件；Agent 根据用例与当前工具能力决定执行方式。

选取流程：

1. 使用会话绑定的正式 `project_id`。
2. 理解用户要求验证的目标、范围和约束。
3. 通过向量召回及编号、标题等查询获得候选。
4. 读取完整固定版本，由 AI 判断相关性。
5. 保存选取理由，由 AI 根据完整内容初步排序，再检查逻辑缺口；补入必要前置后重新确定最终顺序。

检索服务故障与没有匹配用例分别呈现。没有目标用例时返回具体缺口，不静默切换为自由测试。

### 2.3 逻辑缺口检测与自动补全

不建立注册、登录、权限、订单等固定检查清单。

AI 判断的核心问题是：

> 按选定用例的操作与预期结果执行，所需条件能否由当前已有信息或前面的执行步骤提供？

#### 检测输入

| 输入 | 内容 |
|---|---|
| 用户需求 | 本次目标、范围及明确约束 |
| 选定用例 | 完整 JSON、自身说明、固定版本及来源 |
| 当前执行信息 | 项目、环境、用户提供的数据及可引用的运行证据 |
| 可查询依据 | 当前项目其他用例、文档、接口信息和录制知识 |

项目资料按需查询。凭据使用现有受控机制，不进入向量索引或普通日志。

#### 检测方法

一次检测按三个动作进行：先阅读初排后的完整用例，指出哪一步需要什么条件；再核对用户输入与前面步骤能否提供；确实缺少时查询当前项目依据，补入后重新排序并核对。排序和补全可在同一规划回合输出，不额外增加一套预检服务，也不要求用户给用例补齐固定“前置条件”字段。

AI 阅读用例的操作和预期，判断必要条件的来源：

- 当前已提供：直接使用。
- 前面步骤会产生：调整顺序，记录数据传递。
- 没有提供：记录具体缺口，再查找补全办法。
- 条件缺失属于测试目的：保留缺失，不补全。

例如，“未登录访问应拒绝”不补登录；“查询已存在订单并验证详情”需要订单实际存在。

规划只判断逻辑是否连贯。账号、会话、数据是否实际有效，由执行证据确认。

例如目标用例的步骤写明“读取订单 ID 并查询详情”，但用户未提供 ID，初排的前面步骤也没有创建订单。AI 将“订单 ID 没有来源”作为缺口，查询当前项目的创建订单用例，读取其完整成功步骤及预期，再补入并声明输出绑定。目标若是“无效订单 ID 应返回错误”，缺失有效订单就是测试条件，不应补建订单。检测依据来自步骤含义和项目资料；执行时才从真实工具结果提取 ID，不能把规划示例当实际值。

#### 补全方法

AI 针对缺口查询当前项目：

1. 找到合适正式用例：补入执行集合，即使它不直接对应用户原始目标。
2. 没有正式用例，但项目资料或工具结果提供操作依据：补入运行内准备步骤。
3. 必要信息无法取得：保留具体缺口，说明影响哪些执行项；独立部分仍可执行。

新增步骤继续检查逻辑是否连贯。查询、修订受现有 Agent 迭代与超时限制约束；超限保留未解决项，不无限递归。

不能虚构项目接口、页面元素或业务规则。

#### 规划结果与后端职责

沿用现有模型适配器，增加结构化规划结果：

| 内容 | 用途 |
|---|---|
| 执行项 | 目标用例、补入用例或准备步骤 |
| 前后依赖 | 哪一步等待哪一步 |
| 数据来源 | 已有输入或前面步骤的实际输出 |
| 补入理由与依据 | 为什么需要、依据来自哪里 |
| 未解决缺口 | 缺少什么、影响哪些执行项 |

这些字段属于运行计划，不要求所有用例使用同一种业务 JSON 格式。

后端校验项目、版本、引用、依赖循环和顺序，以及前置完成后必要输出是否取得；业务依赖由 AI 结合完整内容判断。

实施时先复用现有项目用例检索、文档读取及知识查询入口，确认哪些入口能返回完整依据，再给规划 Agent 使用。一次判断保存“需要的条件、当前来源、缺口、补入项和依据引用”；查得的新依据进入下一次规划判断。不能把注册、登录等关键词匹配或通用字段检查当作上述检测的实现。验收用实际项目用例与工具输出核对判断及传值，不能只验证模型返回了合法 JSON。

经实际调用链调研，规划按以下方式落地：

1. 召回候选后重新读取当前项目已启用的完整固定版本，同时提供项目用例、文档和已完成录制的目录。用户选中的用例只是初始候选，AI 仍需判断目标相关性；目录用于发现候选之外的必要前置。
2. AI 每回合返回 `query` 或 `finish`。`query` 指定用例身份或检索条件、文档身份与行范围、录制身份；后端仅通过项目隔离的读取服务取得依据，加入下一回合上下文。此阶段不提供执行业务操作的工具。
3. `finish` 返回目标用例、正式依赖、运行内准备、依赖关系、数据绑定及未解决缺口。正式项只引用真实 `case_id` 和固定 `case_version_id`，不能复制或改写正式用例步骤；准备项有自己的操作说明及来源，不伪造正式用例身份。
4. 后端检查引用、版本、项目、循环依赖和数据来源，再保存完整依据及配置快照。已有输入通过 `input_key` 引用顶层键，前置输出通过 `source_item` 引用执行项；具体路径用 `output_path_tokens` 字面量数组，避免点号键被误当嵌套路径。`[]` 表示整个来源值，`["body", "order.id"]` 表示 body 下名为 order.id 的完整键。旧计划的点分 `output_path` 保留兼容，但不能与新数组同时填写；绑定前置输出必须同时声明依赖。规划阶段不能证明该输出已经存在，执行阶段必须核对真实结果。
5. 结构或引用校验失败时，将具体错误、可用依据 ID 和被拒绝的候选返回下一回合，允许 AI 修正或补查询；不由后端猜测和替换来源。查询与修正共用回合、上下文及耗时限制，没有额外无限重试。候选数、执行项数等策略存 MySQL。完整用例超限时明确报错，不截成前六步；读取失败不以旧预览或其他项目内容替代。达到限制或必要条件缺失时保留状态，不能自动改成自由测试。

区分 `planned`、`no_match`、`blocked`、`retrieval_failed` 和 `planning_failed`；`planned` 只表示计划通过引用及结构校验，不表示目标通过。规划记录、完整用例依据、原文范围、配置修订、模型身份、Prompt 版本及回合耗时存 PostgreSQL，可按当前项目重新查看，后续修改配置不改写已保存计划。

```text
目标：查询已存在订单的详情

已有订单信息：
    查询 → 验证

没有订单信息，有创建订单用例：
    创建订单用例 → 传递实际订单 ID → 查询 → 验证

没有创建订单用例，但项目资料提供创建方法：
    运行内准备步骤 → 传递实际订单 ID → 查询 → 验证

目标是验证不存在订单的错误响应：
    保持不存在条件 → 查询 → 验证错误响应
```

是否还需账号或登录，由具体项目依据决定。

### 2.4 冻结、执行、恢复与回归

规划完成后冻结正式用例版本和计划。后续 Agent 循环不重新召回并替换版本。

正式目标与补入用例继续进入现有套件、RunItem 和原子领取流程。准备步骤附属相关条目，保存检查点及证据，不虚构 `case_id`，不自动启用为正式用例。

执行规则：

- 有依赖的条目等待必要前置和输出；展示排序不能代替执行约束。
- 独立条目使用现有并发能力。
- 正式业务前置默认要求通过；准备条件按准备步骤自身结果判断，所属目标失败不等于已经成功的准备失败。只阻断条件未满足的关联项。
- 准备数据默认在相关条目范围使用。计划明确声明共享时，记录拥有该准备的正式条目、准备状态及具体输出引用；不隐式跨条目共享。
- 已成功的副作用操作恢复时读取检查点；结果不确定时先查证。
- 新缺口可修订尚未执行部分，追加计划修订及理由，保留原计划和已完成证据。
- 清理依据用例要求及实际创建的数据安排；共享数据消费完毕后清理。

计划状态同步到图状态、`TurnState`、循环重组、持久快照和审批恢复。新运行由 Agent 理解用例后执行，不强制编译为模式参数；旧运行保留原策略恢复能力。

研究现有实现后，执行输入通过 `ExecutionRequest.context` 的 `execution_basis` 与类型化 `case_execution` 传递；图状态、TurnState 和持久快照已有 `context_bundle`，复用同一承载位置，不在每层复制整份计划。AgentLoop 的中断记录已补存上下文。工作区的现有运行执行服务已按 `execution_strategy=agent` 分流，在既有运行心跳和取消监控内调用 Agent 适配器；旧策略仍调用旧参数编译适配器。实际图工具继续经过现有权限与安全机制。

资源管理按实际创建者处理。新 Agent 策略只领取运行条目的 Agent 配额，不解释旧 `test_data.runner_arguments` 来预占账号、环境或 Docker；浏览器、容器工具继续使用自身的创建、心跳和清理机制。适配器在首次图执行和每次审批续执行时，用服务端已核对的项目、run/item、原执行 attempt、内部会话及稳定 turn 绑定现有 RequestContext，确保工具领取资源时不继承父会话或外层 HTTP 请求的错误身份。外层 `resource_leases` 当前没有图内消费者，不将它复制进冻结业务内容；Agent 路径也不需要把多个容器输出绑定到旧单工具槽位。实际 Redis 逻辑资源及 API 工具身份已经验证，各模式真实浏览器/容器执行仍需分别验收。

新增的 [SessionService.execute_case_turn](G:/Code_Warehouse/Ai_Test_Agent/Enterprise_AI_QA_Agent/Agent_Server/src/application/sessions/session_service.py) 是服务器内部入口，不接受公开聊天请求中的冻结执行数据。公开请求剥离运行、条目、attempt、冻结上下文、检查点及 `case_execution_managed`，不能通过伪造 `source` 获得正式运行身份。工作区适配器先重新读取运行、条目和 attempt，核对当前运行租约、固定版本与项目，再从已保存计划、用例版本和结果构造完整上下文。每个逻辑条目执行使用专属内部会话；有来源会话时核对正式项目，并保留其模型偏好、会话/运行模式及服务端环境信息。

内部入口复用既有会话锁、持久租约、心跳、事件和图执行；同一身份优先读取最新快照，等待审批和终态均返回原快照，相同身份的上下文或模式改变明确拒绝。实际复现并修复了审批续执行后误读最早快照的问题。工作区适配器在既有 attempt 检查点中保存类型化执行身份、完整上下文哈希和快照引用：先保存 `admitted`，进入图之前再保存 `running` 执行意图。恢复时核对原执行 attempt 确实属于当前条目的恢复链，继续使用原执行身份及稳定 turn；结果归属当前恢复 attempt，同时保留 `execution_attempt_id` 与 `result_attempt_id`，不改写原工具证据。已有终态快照可重新核验后落库；已记录执行意图却没有快照、会话丢失、图中断或工具结果未知时保存需核对状态，不重新启动业务操作。此能力不等于步骤级准备恢复或自动业务核对已经完成。

审批沿现有运行条目接口协调。图发出受控工具审批后，适配器将实际 RunItem 置为等待，记录内部会话与审批/工具身份；公开 Session 审批入口不能绕过运行条目协调。审批续执行核对归属，领取运行条目和指定待批 turn 的租约，同步续执行原图，再返回下一项待审批回执或最终结果。前端已同步 `RunItemApprovalPending | TestCaseResultRecord`，识别旧、新运行审批来源；重复投递等待或终态条目读取已有回执/结果，不重领终态。

已复现的根因是“HTTP 操作成功后、下一份审批快照保存前中断”会在恢复时再次 POST。适配器沿原审批读取实际 ToolJob：终态且身份、参数一致时重建已有工具记录，只有明确 `waiting_approval` 的任务才执行首次调用；其他未知状态不重发、不覆盖证据。实际父任务取消、持久会话租约到期及运行恢复测试验证了此路径。恢复时按原待批顺序读取已保存的决定：仍为 pending 才返回等待；已批准或拒绝则在当前运行租约下继续原图，保留原决定及备注，遇到新的 pending 审批再等待。批准/拒绝后、进入图前中断的内存与实际 PG 场景，以及 POST 成功后快照滞后的场景均已通过普通执行恢复验证。未知业务副作用的查询与核对仍待实施。

API 按用例执行的提示词读取完整冻结内容，使用现有 `api-test-runner` 进行必要操作，依据实际前序输出传值；避免现有自由测试提示词要求重新生成整套 campaign。自由测试和未声明执行依据的旧请求继续使用原提示词。其他模式也需分别核对其提示词与冻结执行职责，不能仅凭 API 专项宣称全部模式已经验收。

内部上下文构造器已读取固定版本的完整 JSON、自身说明和来源，按正式条目归属加入准备与清理，读取必要前置的真实已保存结果，保留结果身份和字面量路径。运行内尚未执行的准备输出保留为待解析引用，不能用计划中的示例值冒充实际输出。生产提示词增加完整冻结执行数据；显式自由测试不注入用例，显式冻结执行不重新检索替换版本；未声明执行依据的旧请求保留原参考召回行为。

报告区分目标、补入用例、准备步骤、预期、实际和证据。准备成功不计为目标通过。失败回归创建新运行，重新确认必要前置，保留原失败结果。

经工具和结果链路调研，P2b 的多工具结果采用结构化执行回执：每个正式项及所属准备/清理分别报告状态、检查及输出引用。检查引用该项固定 JSON 或准备说明中的预期位置，以及本次执行已保存 ToolJob 的具体输出位置；输出只声明引用，由服务读取实际值。确定性比较复用现有验证服务的算子，语义检查保存 AI 判断、理由和原文/工具证据，不伪装成确定性断言。引用必须来自本次受控执行记录，服务核对项目、运行、条目、attempt、会话、turn、call 和工具身份，读取完整已落库结果；缺失、未完成或其他运行的证据不能证明通过。工具完成和 Agent 自述通过均不能单独决定用例通过。此回执属于运行结果契约，不规定业务用例的字段模板。

回执生成与业务执行分开处理。现有模型验收已经出现引用错误、HTTP 失败和不完整 JSON；不能把重新生成回执变成再次执行创建、删除等操作。增加逐项只读生成入口，保留每项完整预期和已保存工具证据，最后合并并核对全部正式项、准备及清理；不是截断单个用例。只读模型请求不提供工具，模型要求调用工具时直接报告契约错误。输出结束原因、用量和解析失败必须可查；不补括号、不猜字段、不将不完整响应当作通过。纠正引用只在原执行预算内有限进行，不能无限重试或绕过 MySQL 配置提高预算。该入口和核验服务是内部能力，生产调用方的预算、持久化及恢复仍需接通。

2026-10-04 的实际模型结果：逐项调用中准备项返回完整 JSON，目标项返回 `finish_reason=length`、8192 completion tokens、正文 0 字符，整项验收失败（233.17 秒）。保留响应状态和用量样本，不推测未返回的思考内容；此前整份回执的不完整 JSON 没有记录结束原因，不能追认其也由同一原因造成。不再重复同一配置调用或自动修改 MySQL 模型配置。当前已验证服务能拒绝不完整回执，并使用实际样本回归；尚未证明默认模型能完成目标项回执，更没有完成自主执行业务和生产入口验收。

当前执行链的实际限制与后续接入顺序：

- `TestRunService.create_run` 仍要求用例历史模式与运行模式一致；`CaseExecutionAdapter` 仍将旧字段编译为模式参数。新增 Agent 策略应读取冻结计划及完整用例，保留旧策略恢复历史运行，不能用更多字段转换代替 Agent 理解。
- 原 `run_store` 只按位置领取，不能保证业务顺序。现已给运行条目增加固定依赖和必要输出路径；领取及启动检查声明条件，正式业务依赖要求通过，跨条目的准备依赖要求拥有者终态且相应准备通过，清理等待消费项终态。条件失败或必要输出在终态结果中缺失时，同事务保存未执行业务操作的 blocked 结果，独立项继续。真实 PostgreSQL 专项核对了上述行为；旧依赖默认要求通过，旧运行默认无依赖。
- `CasePlanRunService` 与 `plan_mapping` 已实现固定计划映射及创建服务。仅正式目标/依赖产生套件条目和 RunItem；准备步骤附属正式条目，并冻结执行前/执行后的归属。PostgreSQL 在同一事务重新确认项目、正式用例生命周期、精确版本及保存的计划，再写套件、运行、条目和 Outbox 意图；重复请求返回同一运行。当前服务由生产初始化注入，Agent 回归与公开保存计划启动复用该服务；真实存储及 Redis Worker 类专项已验证，接线不代表完整生产进程验收通过。
- `execution_basis` 及计划引用贯穿执行请求、图状态、`TurnState`、循环重组、持久快照和审批恢复。执行继续使用现有工具权限、资源租约和超时机制。先验收真实操作、输出绑定、依赖失败及恢复，再接入结果和新回归。

项目规划入口只生成和保存计划；公开启动入口读取 PostgreSQL 中已保存的计划，不再次发起模型规划。旧同步规划入口保留请求内执行；产品规划弹窗已改用 §2.6 的持久任务提交和查询。已保存计划的启动可以独立使用，不等待再次规划。现有运行条目的执行和审批入口、保存计划启动 API/UI 均已接入 Agent 策略；默认模型及完整产品/生产进程验收仍不能由规划成功或受控测试替代。

## 三、文档版本、差异与需求追踪

### 3.1 上传文档独立保存版本

上传文件使用现有对象存储和数据库保存。**上传、版本保存及比较均不依赖 Git。**

用户上传文件后，系统保存原件；无需仓库路径、commit、Git 缓存或 Git 提交。“文档版本”是系统数据库中的历史记录，并非 Git 版本。两种来源的操作关系如下：

上传入口只需要项目、文件及必要的文档信息。“上传新版本”另指定已有文档和预期父版本。普通上传不会同时调用 Git，也不会把文件放进用户仓库；后续比较只读取系统已保存的两个版本。这是本次文档升级的默认路径，可独立部署和验收。

| 操作 | 保存与比较方式 | 是否使用 Git |
|---|---|---|
| 普通上传 | 在当前项目创建文档身份及 V1，原件存 RustFS，元数据存 PostgreSQL | 否 |
| 在文档详情上传新版本 | 明确当前文档及父版本，另存 V2；V1 原件和快照保留 | 否 |
| 比较上传版本 | 读取指定 V1/V2 的完整文本或解析快照，以确定性规则计算差异 | 否 |
| 可选 Git 导入 | 只读获取用户指定仓库版本的文件，再交给上述保存、解析和比较服务 | 仅获取来源时使用；同仓库比较可附加 Git diff |

这张表描述升级目标。当前上传接口仍只创建独立目录记录，尚没有“上传新版本”或版本比较功能，不能把两次独立上传直接当成已实现的 V1/V2 链。

当前已经能保存上传内容；还需要新增的是稳定文档身份、父版本关联、原件与派生结果分离、解析快照和比较入口。现有 API 文档转换发生在存储之前，因而还必须调整保存顺序，不能直接把当前保存内容都标记为原件。

**可行性结论：可以在现有上传服务上增加独立版本管理，无需引入 Git。** 已核对上传服务、对象存储接口、目录模型和生产依赖注入，并重新运行相关测试；现有代码尚未提供文档 V1/V2 关联及新旧比较，以下是待实施设计。问题属于文档版本模型缺失，不能用 Git 缓存或同名覆盖代替。

这里确认的是现有存储能力可以承接升级。当前上传接口不具备完整需求文档处理能力：`api_document` 策略允许 Markdown 和 PDF，但没有允许 DOCX；`pyproject.toml` 尚未声明 `python-docx`、`pypdf`。因此还需要接通需求文档的格式策略、解析依赖及任务进程，不能直接把 API 文档上传接口当作已经支持这些需求。

当前需要升级的是：

- 将独立上传记录关联成同一文档的历史版本。
- 在转换前保存原件，转换结果另存。
- 将生成来源和差异比较关联到明确版本及解析快照。

流程确定为：

1. 首次上传创建项目所属文档身份及 V1。
2. 在文档详情选择“上传新版本”，明确关联当前文档。
3. 新原件保存为 V2，使用独立对象键；V1 保留。
4. 数据库记录文档 ID、版本 ID、前一版本、对象地址、字节哈希、上传时间及来源。
5. 解析成功后默认比较新旧相邻版本，也允许选择历史版本。

通用上传入口可以推荐已有文档，歧义时由用户选择。不能仅凭文件同名自动覆盖或合并。

同一请求的重试按请求身份返回已经提交的版本，不重复创建。新请求的原件与当前版本字节相同时，提示“内容未变化”并返回当前版本；解析器或选项变化仍可新增解析快照。

如果当前是 V2，用户明确上传与历史 V1 相同的内容，应追加 V3，记录 V2→V3 的恢复过程；不能仅因哈希曾出现就返回 V1 或改变当前版本指针。哈希不证明两个文件属于同一业务文档，也不能代替请求幂等身份。保存或解析失败明确呈现，不能报告比较成功。

原件、转换结果、解析快照分别保存。OpenAPI、Postman、HAR 转 Markdown 属于派生内容；项目 URL 等元数据修改不能覆盖原件。历史原件缺失时如实标注。

#### 数据如何关联

| 记录 | 保存内容 | 关联关系 |
|---|---|---|
| 文档身份 | 稳定文档 ID、项目、标题与当前版本引用 | 一个文档包含多个原件版本 |
| 原件版本 | 版本 ID、父版本、原始文件名/类型、字节哈希、对象地址、来源与时间 | 引用文档身份，原件不可原地修改 |
| 派生结果 | 转换器及版本、转换选项、对象地址、警告 | 引用原件版本，不替代原件 |
| 解析快照 | 解析器及版本、选项、文本/结构/来源位置、状态和警告 | 同一原件版本可产生多个快照 |
| 差异记录 | 两端原件版本及解析快照、比较选项和差异结果 | 明确比较依据，后续 AI 影响分析引用该记录 |

原件和较大的派生工件沿用 RustFS，业务元数据使用 PostgreSQL。解析器选择等可编辑配置使用 MySQL；解析快照保存当时实际使用的配置版本及内容，保证历史可追溯。上传文件无需先登记本地仓库。

#### 上传新版本的完整处理

```text
首次上传：选择当前项目 → 校验文件 → 保存原件 → 创建文档及 V1 → 异步解析
更新上传：打开已有文档 → 上传新版本 → 校验文件 → 保存新原件 → 关联 V2 → 异步解析
版本比较：选取 V1/V2 的明确解析快照 → 确定性差异 → 展示原文位置 → AI 影响候选
```

例如用户首次上传《需求说明.docx》，系统保存 V1。之后在该文档详情上传修改后的同名文件，保存 V2，再比较两版各自的解析快照。用户若从普通上传入口上传同名文件，默认创建另一份文档；不自动覆盖 V1，不自动绑定 Git，也不靠同名推断文档身份。AI 影响分析读取已经保存的差异和来源位置，不能替代原件保存及确定性比较。

版本提交在 PostgreSQL 事务中处理文档归属、重复请求和父版本检查。并发更新不能覆盖其他上传：基于提交时指定的父版本检查冲突，冲突时返回当前版本供用户重新选择。重复请求不创建重复版本；同名文件不能作为业务身份或幂等键。

RustFS 写入与数据库提交不是一个事务。数据库只发布原件已成功保存的版本；对象已写入但目录提交失败时，必须记录并补偿清理，保留可检索失败信息，不能返回上传成功。具体补偿接线先研究现有任务和存储错误处理，再实施。

数据库提交的响应丢失不等于事务未提交：先按本次请求身份核对版本记录；确认已提交时返回已有版本，确认未被引用后才清理本次对象。数据库暂时无法查证时保留对象并记录待核对状态，不能直接删除可能已经被版本引用的原件。

解析失败不删除已经保存的原件版本。界面区分“原件保存成功、解析失败、比较未完成”，允许重试并追加快照。两个版本都具备可比较内容后才展示差异结果。

前端文档详情增加版本列表、上传新版本、下载原件、解析状态及选择版本比较。普通上传仍创建新文档；只有用户明确选定已有文档，才加入其版本历史。

交互和接口按以下职责扩展现有文档入口，具体路由名在实施时与现有注册入口对齐：

| 用户操作 | 请求需要的信息 | 服务返回的依据 |
|---|---|---|
| 首次上传文档 | 正式项目、文件、标题与请求身份 | 文档身份、V1、原件保存状态及解析任务身份；相同请求重试返回同一提交 |
| 上传新版本 | 文档身份、预期父版本、文件与请求身份 | 已保存的新版本，或当前版本及冲突信息 |
| 查看或下载历史 | 文档身份与版本身份 | 指定历史原件及其元数据，不读取当前版本代替 |
| 重试解析 | 原件版本、解析器及选项 | 新的解析任务与快照，旧快照保留 |
| 比较版本 | 同一文档内两端版本及明确解析快照 | 可追溯的确定性差异，或尚不能比较的具体原因 |

上传入口不包含必填仓库、commit 或 Git 缓存参数。Excel 用例导入与需求文档上传各自保留业务入口，复用现有上传安全处理和对象存储能力，不混用用例导入批次与需求文档版本身份。

#### 历史数据迁移

已有目录记录可迁移成对应文档的首个历史版本，保留旧 ID 与对象引用的兼容映射，不自动按文件名合并。逐条判断对象保存的是原件还是转换结果；只有原件确实存在时才能标记为原件。仅剩 Markdown 转换结果时标记“历史原件缺失”，允许继续查看派生内容，不伪造原始文件及其哈希。

先完成独立上传、版本保存和比较验收，再接入可选 Git 来源。Git 功能缺失、未配置或调用失败，不影响上述上传流程。

| P3.3 解析快照 | 查证并声明 `python-docx`、`pypdf` 依赖；新增统一解析接口、轻量解析工厂和受限任务进程；前端展示任务、警告及重试；保留 Docling 注册入口 | 实际 Markdown、DOCX、文本型 PDF 的文本、结构与来源位置可核对；超时和失败可见；切换解析器或选项保留旧快照 |
| P3.4 版本比较 | 在指定快照间计算原始抽取文本与归一内容差异，保存两端引用及位置；增加版本选择和差异页面 | Git 未配置时仍能比较 V1/V2；确定性差异对应实际修改；不使用截断预览或 AI 改写文本代替比较依据 |
| P3.5 可选 Git 来源 | 新增项目所属本地仓库来源登记、只读文件获取及来源记录；接入已验收的原件保存、解析和比较服务 | 仓库工作区和历史不被修改；默认创建独立文档，明确选择目标文档后才能追加版本；失败不影响上传入口 |

P3.1—P3.4 不等待 P3.5。P4 使用已确认的版本及差异记录继续建立需求影响和追踪闭环。上述步骤是实施顺序，不在方案更新时新增产品代码或执行数据迁移。

### 3.2 Git 作为独立可选来源

用户选择项目已登记本地仓库的路径和 commit，系统只读获取文件，保存来源 commit、路径和 blob 身份，再进入文档保存、解析、比较及影响分析服务。

不向仓库写入上传文件，不克隆、不 checkout、不提交、不自动同步。

现有代码审查的本地项目路径解析与 Git 调用作为实现参考；正式文档 Git 导入入口及项目所属仓库来源登记需要新增。不能把代码审查中的自由文本 `root_path` 直接当成已经登记且属于当前项目的文档来源。

默认分别管理上传文档与 Git 导入文档。只有用户明确选择“导入为该文档的新版本”，才关联到已有文档；这仅复用系统文档身份，不把上传文件加入 Git，也不要求之后继续使用 Git。

**两种来源复用处理服务，不要求混用，也不要求上传文件经过 Git。**

### 3.3 轻量解析工厂

统一接口输入原件和解析选项，输出文本块、章节、表格、来源位置、解析器版本、能力及警告。

| 格式 | 首期实现 |
|---|---|
| Markdown | 文本解析 |
| DOCX | `python-docx` |
| 文本型 PDF | `pypdf` |
| 扫描 PDF | 明确提示首期不支持 OCR |
| Docling | 预留 HTTP 注册、能力声明和结果转换；首期不部署 |

解析放入可终止的独立任务进程，配置超时、内存、CPU、输入和输出限制。API 返回任务身份，父进程负责超时及进程树回收。

解析器或选项改变产生新快照；重解析历史原件也追加快照，不重写历史依据。无法可靠提取的结构给出警告。

### 3.4 确定性差异与影响判断

上传文档使用标准库 `difflib` 比较保存的文本或解析快照，不依赖 Git。Git 导入使用相同服务；同一仓库两个 commit 的比较可附加 Git diff 证据。

- 文本原件提供章节、行和字符差异。
- DOCX/PDF 提供原始抽取文本及结构差异，同时保留原件。
- 原文差异与确定性归一差异分别查看，保留来源映射。
- 不让 AI 改写文档后再比较。

AI 同时读取**现有用例、当时编写来源、具体文档变化**判断影响，并引用位置；同时考虑变化是否已在当前环境生效。

| 影响 | 处理 |
|---|---|
| 无影响、轻微影响 | 继续执行，保存说明 |
| 已生效的重大影响 | 停止相关版本在对应环境执行，生成更新草稿 |
| 尚未实现或尚未生效 | 保留适用于当前环境的旧版本，新草稿关联目标版本 |
| 无法确定 | 提交评审；没有明确失效证据时不全面阻断项目 |

新增需求生成新草稿；修改需求生成原用例的新版本草稿；删除需求提出停用候选。保留历史版本、原运行依据和结果。

### 3.5 需求追踪

保存稳定需求身份、需求版本、验证点及用例版本关联。

矩阵展示设计覆盖、未覆盖项、执行证据和待复核状态。关联数量与实际验证结果分别呈现，旧需求的通过结果不能证明新需求已通过。

### 5.3 验收要求

| 场景 | 必须证明 |
|---|---|
| 已有必要数据 | 不添加多余准备 |
| 前面用例产生数据 | 正确排序并传递实际输出 |
| 前置不直接符合用户目标 | 必要时仍补入，理由可查 |
| 没有正式前置用例 | 按可靠项目依据补运行内步骤 |
| 刻意未登录或使用无效数据 | 保留负向条件及预期 |
| 信息或依据不足 | 显示具体缺口，不编造操作 |
| 摘要遗漏关键步骤 | 完整版本读取后正确判断 |
| 前置成功但输出缺失 | 不将依赖视为满足 |
| 中断恢复 | 不盲目重复副作用操作 |
| HTTP 已成功但审批快照尚未保存 | 恢复读取同身份、同参数的终态工具证据，不再次发送 POST |
| 结果落库丢失后恢复为新 attempt | 重放原执行快照，结果记录当前 attempt 与原执行身份，保留原工具证据 |
| 已有执行意图但缺少快照，或工具仍处于未知状态 | 明确记录需核对，不重执行业务；不能报告为已自动恢复 |
| 审批决定落库后、进入原图前中断 | 使用原决定与备注自动恢复；拒绝不执行业务，批准只执行必要操作 |
| 外层请求带父会话或错误运行身份 | 工具资源使用已核对的冻结项目、内部会话、run/item 和原执行 attempt |
| 新用例包含旧模式字段 | Agent 不按旧字段预占资源或编译工具参数，实际工具负责自身资源 |
| 连续审批及重复投递 | 沿运行条目接口返回下一项审批或结果；等待、终态均不重复执行 |
| 多 Worker 领取 | 依赖未满足的条目不提前执行 |
| 耗时规划提交响应丢失或刷新页面 | 相同请求找回同一任务，最终计划不重复创建 |
| 规划 Worker 中断或租约失效 | 保留已读取版本、检查点和剩余额度，旧 attempt 无权提交；终态重投不重新规划 |
| Git 未配置或不可用 | 上传、保存版本及比较正常运行 |
| 上传同一文档的新版本 | 原件和旧版本均保留 |
| DOCX 需求文件上传 | 实际文件通过对应格式策略，下载字节与上传一致；不能以聊天附件上传成功代替需求文档入口验收 |
| API 文件转 Markdown 或修改项目 URL | 原上传字节不变，转换或重生成结果另存并记录来源版本 |
| 同名不同文档 | 不误合并 |
| 同一请求重试或上传与当前版本相同的原件 | 返回已有提交或当前版本，不生成无变化的重复版本 |
| 当前 V2 恢复为历史 V1 的内容 | 创建 V3 并保留 V2→V3 的差异及来源，不因历史哈希相同而返回 V1 |
| 并发更新或提交响应丢失 | 父版本冲突可见；先查证提交结果，已被版本引用的原件不被误删 |
| 首次上传响应丢失后重试 | 返回同一文档及 V1，不新建第二份文档；同请求身份但内容不同明确拒绝 |
| 解析失败或能力不足 | 明确显示并允许重试 |
| Git 导入 | 仓库只读，明确关联后才成为已有文档新版本 |
| 模板修改、项目隔离 | 旧用例执行含义不变，数据不跨项目 |
| 录制与工具报告 | 末尾事件可对账，结果与实际证据一致 |
| 文档影响与回归 | 轻微变化继续，重大变化处理相关用例，原失败结果保留 |

每阶段运行受影响测试、前端类型检查和构建、迁移验证及必要联调，记录实际结果与跳过原因。实施完成后按项目规范创建相关文件的中文 commit，不自动推送或创建 PR。

### 5.4 每一步的实施方式

按“读取实际调用链及消费者 → 用真实输入验证现状 → 核对并修正本节方案 → 实施 → 功能验证及相关回归 → 更新记录并提交”推进。研究发现原方案与系统不符时，先修正具体设计和依据，不在错误假设上继续增加兼容分支。

每项记录分别说明工作区实现、实际验证和提交状态。测试覆盖到服务、数据库或组件，就只报告对应范围；生产启动、浏览器操作和完整 Agent 链路需要各自的验收。受控测试使用独立项目、测试表及对象，只清理本次创建的数据。

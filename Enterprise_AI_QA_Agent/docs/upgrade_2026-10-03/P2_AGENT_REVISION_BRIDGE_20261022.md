# 执行中 Agent 重规划：持久任务与修订衔接

本项推进执行中发现新缺口后的重规划链路。此前提交 `30f367371` 仅验收人工选择已保存候选后的产品恢复，不证明 Agent 自主修订。

## 代码依据与采用方式

| 已核对依据 | 本次做法 |
|---|---|
| `agent_case_execution.py`、`agent_case_context.py` 固定已领取条目的快照与执行哈希 | 继续保护已领取条目；新计划只修改从未领取部分 |
| `agent_regression_service.py`、`planning_task_service.py` 先按原请求重放，再冻结目标及版本，复用持久规划 | 修订提交固定原目标、完整用例版本、原目标描述及运行状态，复用现有任务和 Outbox |
| `planning_workflow.py` 已支持固定目标校验及响应检查点恢复 | 原目标不得因重新规划被删除、换版本或降为依赖；可查询同项目依据并补依赖或准备 |
| `plan_run_service.py`、`run_store.py` 已有带 CAS 和幂等键的追加修订事务 | 候选保存后调用该事务，不新增执行引擎 |
| `planning_task_handler.py` 当前对终态投递直接返回 | 完成候选后及终态重投时继续确认修订结果；先查已提交历史，再决定是否应用 |
| `PostgresPlanningTaskStore` 使用 JSONB 固定输入与检查点 | 扩展可选修订来源和结果，无新配置项；运行数据继续保存 PostgreSQL，规划策略继续读取 MySQL |
| 本地课程 `Agent轨迹与协议鲁棒性.html` 的 Replan、幂等和恢复章节 | 验收调用轨迹、固定目标、任务重投、提交成功但确认丢失及并发；不能仅验语法 |

候选完成与修订生效是两个事实，任务查询分别呈现。修订最终确认按任务行锁串行，避免并发终态投递分别写入相互矛盾的结果；数据库故障继续重试，业务冲突记录为拒绝且保留候选。

不改供应商协议，不读取生成模板。当前条目需要改动自己的前置时，仍不能覆盖其固定快照；失败或新回归运行语义保留。

## 待验收边界

需以实际 JSON/需求文档、MySQL 配置及 PostgreSQL 任务/计划/运行验证提交、规划、应用和恢复。本批后端衔接通过不等于 Agent 工具调用、默认模型质量或完整产品流程通过；这些仍属于完整目标的后续工作。

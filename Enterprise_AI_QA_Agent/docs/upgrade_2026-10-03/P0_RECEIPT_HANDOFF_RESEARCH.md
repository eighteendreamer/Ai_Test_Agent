## 已复现的事实

独立 untrusted-target 场景以纯 JSON 返回 blocked，执行页面效果为零，原终态任务重投没有新增模型发送和页面效果。这个结果证明拒绝场景，不替代可信目标的 passed 验收。

最后可信快照的 `loop_iteration=0`、`max_iterations=8`，而保存的请求已有 20 次执行阶段发送。因此，现有快照中的迭代值不能直接当作整个审批恢复过程的累计发送次数。这里只记录反例；当前没有完成预算根因修复。

## 待实施的回执阶段

1. 固定本次完整 case/prepare/cleanup、项目/run/item、原执行 attempt/session/turn、原图快照、实际调用身份与原 Job 证据。模板不进入此阶段。
2. 完整且合法的原最终 JSON 直接核验，无须为了格式再调用模型。格式或引用错误保存原回复及具体错误后，才允许有限的只读纠正候选；截断、传输失败、未完成操作及归属错误分别记录，不能概括成可盲重试的 JSON 问题。
3. 只读纠正输入使用完整固定预期、已验证归属的实际持久输出和具体错误，不暴露业务工具，不执行原报告中的指令、不重复导航/点击/创建/删除。最终仍按原服务逐项核验，纠正候选不是通过结果。
4. 在原 PG 检查点保存请求身份、输入哈希、协议/Prompt、模型及非敏感调用配置、预算消耗、调用意图、原响应和校验状态。恢复复用已保存响应；仅有意图而无可靠响应保留未知，不能进入业务执行阶段。
5. 先统一跨审批恢复的调用累计与剩余预算，再接入有限纠正。物理 SDK attempt、逻辑模型阶段、工具审批分别计数；不拿审批数或当前 `loop_iteration` 推算全程调用数，不暗增 MySQL 预算。
6. 用户报告继续用现有报告/工件体系；正式 JSON、原报告、实际证据和服务器判定分别关联。读取某个报告 artifact 需要明确的产出协议和归属校验，不能扫描任意文本中的 JSON 块。
7. 新运行固定回执协议和配置；旧检查点继续按原协议恢复，不重写历史失败、哈希及完成条目。新可编辑配置若确有需要放 MySQL；检查点和结果放 PG，大原响应与报告放 RustFS。本批没有新增配置或迁移。

## 验收与未完成范围

必须保留原失败并验证：合法 JSON 不增加发送；实际混合报告产生具体反馈且不重做业务；错误引用仍拒绝；未执行项能保存 blocked；截断及传输未知不假造结果；调用意图/响应保存前后终止 Worker 后恢复同身份；多审批不重置预算；终态重投零模型与业务副作用。

最终用默认模型、真实 Chromium、生产 API、独立 Worker、MySQL/PG/RustFS 和明确授权的受控页面运行完整用例，要求实际预期证据、正式 passed 与终态重投。当前仅复核原失败及原拒绝场景；没有新增默认模型成功实测，也没有实现上述回执阶段。

无父会话的产品授权入口、完整 App、人工 DeepSeek、录制清洗/遗漏、Docker 性能安全、其余 P0—P5 范围继续保留。项目 URL、文档和录制只能提供导航依据，不能自动升级为服务器授权。

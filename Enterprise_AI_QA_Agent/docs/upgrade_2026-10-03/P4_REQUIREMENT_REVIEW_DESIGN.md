# 正式需求评审与版本追踪：实施前查证

研究基线：6abe525f。完整P0—P5继续执行；本步骤把已保存的影响候选接入正式需求治理，后续还需增量生成、环境适用和完整产品验收。

## 依据 → 采用方式

- `schemas/document_impact_workflow.py` / `document_impact_grouped.py`：rules.id是候选完整正文hash，origins保留原调用/核验；不是稳定业务身份。使用独立UUID需求身份，评审指定新建或关联，不按hash、标题或章节自动合并。
- `impact_workflow.read_snapshot` / 分组`_read_result`：读取时核对完整对象hash、范围、响应检查点和候选。新评审先复用此路径；不直接信任客户端发送的候选、原文或影响列表。
- `schemas/document_impact_responses.py`：规则候选与逐case判断分开；verification_points是模型字符串建议。评审采用完整规则及逐用例判断作为证据，明确选择验证点和用例版本关联；不将所有none/minor/major判断当成覆盖。
- `test_cases/version_reviews.py`：治理在不可变内容之外追加事件，同请求改变参数拒绝；原启用版本不因新草稿变化。需求评审也追加不可变事件/版本，同请求恢复原决定；不修改原AI结果或用例生命周期。
- `planning_store.py` / `import_store.py`：PG JSONB记录、参数化SQL、线程内独立事务、正式project_id及锁内活动状态校验。采用项目行锁序列化本项目评审写入，并在同事务核对固定snapshot、目标需求父版本及用例版本项目归属。
- 本地`线上流量闭环与评测集治理.html`的证据关联、人工审核和版本打标；`评测工程化与CICD.html`的版本可追溯；`测试数据合成与用例自动生成.html`的来源治理：采用追溯原则，不照搬课程阈值或统计值。

## 契约与事务

明确的评审请求接受、拒绝或暂缓某个固定snapshot/rule。接受时提供需求正文、变更分类、验证点（需求内稳定key）及明确用例版本/验证点关联；关联已有需求必须给出当前父版本。候选缺失/外项目/错误固定版本拒绝。partial结果可以逐候选评审，依据限制随评审保存，不假装整份分析完整。

PG新增需求身份、不可变需求版本及评审事件三类表。评审事件固定snapshot对象hash、输入/清单hash、原rule与所有case判断/来源检查点；不复制原文大输入。源大对象仍在RustFS；没有新可编辑策略，所以不新建MySQL配置。API新字段与前端DTO/客户端同时增加，原影响契约不变。

请求身份在项目内唯一，包含文档/snapshot及全部决定参数。提交先查原请求，恢复不再次读取RustFS/模型/当前配置；事务丢回执保留原决定，按原请求找回。新请求校验候选上次评审ID、需求预期父版本；并发不能默默覆盖。归档后的既有查询/重放允许，新决定拒绝。

版本中的验证点UUID按同一需求的明确key保留；版本正文不可变，旧矩阵可读取。覆盖只来自明确评审关联，未关联的验证点显示未覆盖。更新版本不复制旧覆盖，上一版本已有关系显示待复核。删除追加removed版本，不自动停用用例/删除历史。执行证据尚未接入时明确not_assessed，不能把设计覆盖展示为测试通过。

## 必须实际验证

用真实MD/DOCX/PDF文件走上传、解析、比较、受控HTTP影响、PG/RustFS，再通过真实ASGI请求保存评审；检查新需求身份、版本/验证点、明确覆盖、父版本冲突、并发同请求/不同请求、外项目与历史重放。模拟真实PG提交回执丢失，按原请求恢复；归档后查询/恢复不调用模型或读取原文。原影响对象/用例版本/启用指针不改写。API错误返回与前端类型/构建另验。后续完整App和真实业务评审、增量生成/部署/运行证据继续保留未完成。

# P2 清理来源误归属与默认 Step 只读对照

本次先重读用户原方案附件，沿实际 r4 失败请求、固定逻辑、任务范围、原始工具契约和执行证据采集代码查证。没有改供应商协议、生产模型配置、原失败计划或已冻结检查点。

## 实际逻辑问题

`p2-default-multi-case-r4-20261020/PG-planning.json` 的逻辑选择包含创建订单前置和查询订单目标；创建发生在前置，目标的完整 JSON 只查询和删除前置订单。但目标填写了 `cleanup_sources=["query-order-target"]`，引用了自身。

`planning_effect_tasks.task_roles` 按清理来源确定 produced 范围。因此本样本虽然 bindings 正确声明前置 produced、目标 cleanup，系统仍要求前置和目标都提供 produced 声明。`normalize_relation_scopes` 允许自身来源是为了支持同一个完整正式用例内部创建后清理；它不读取任意业务 JSON 判断是否实际创建。本样本的结构合法不能证明业务来源正确。

四个历史多候选检查点中，r4 和 `p2-default-multi-case-step-20261019` 目标误引用自身；`native-schema-low-corrected-20261020` 和 `step-timeout600-20261019` 则引用正确前置。因此此前“逻辑阶段通过”的说法必须收窄为：目标/前置选取和排除干扰项有证据，不能推出清理逻辑全部正确。当前提示突出同项创建/清理，字段 Schema 没有解释来源含义；这可能影响判断，但本轮没有证明它是全部根因，也没有用按 HTTP 方法推断的服务端规则代替 AI。

## 只读反事实实验

脚本 `p2-cleanup-source-probe-20261020.py` 从原 produced 请求构建独立诊断副本，仅纠正该清理来源及其必然派生的逻辑 SHA、produced scope。完整用例、文档、原生工具契约、system prompt、绑定回执、E/T 目录、默认模型和8192输出上限保持原值。副本不恢复原任务、不创建 Run、不调用业务工具、不写配置；不是合法的原计划修订。

2026-10-20实际结果：退出1，**120.752秒**；一次 SDK 调用、一次物理 HTTP200，正常收到流终止，`finish_reason=length`、completion8192、prompt9409，正文0字符，没有 canonical 回执。原文件 SHA 和全局模型参数读回均未改变。结果原件在 `p2-cleanup-source-probe-20261020/verification.json` 和同目录 `physical/`；只保存推理字段计数，不保存其正文。

结论：清理来源误归属是真实缺陷，但纠正来源并缩小 scope 仍不足以解决 produced 输出耗尽。本轮停止同类参数/提示微调与重复发送；不能把这个失败对照计为P2验收通过。

## 仍需设计和验收

- 选取、传值及清理来源的业务含义需要一起核对。旧冻结计划保留，不自动改来源或重新启用。
- 证据任务提示允许 `unresolved`，Schema 却要求 scope 各项至少一份声明，最终关系校验也要求完整产生/清理对应。无法取得可靠结构时能否诚实形成未解决计划，需要独立失败样本和契约研究；本轮未新增放行分支。
- 多候选 fixture 的 DELETE 文档只说明状态200，未描述返回对象形状；当前清理覆盖要求从原返回提取同一业务身份。不能凭创建响应推断删除响应，须继续核对文档信息不足与正常无正文删除接口的适用边界。
- 默认 AI 项目选取、补全、完整准备生命周期、正式执行和终态重投的整体闭环仍未验收。性能模式的独立 Agent 验收不能替代它。

已有模型接入采用统一内部契约与按 transport 分派的原生客户端，继续保留。配置 MySQL、业务 PostgreSQL、原件 RustFS；整体 P0—P5仍未完成。

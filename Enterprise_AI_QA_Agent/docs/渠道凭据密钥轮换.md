# 渠道凭据密钥轮换

渠道凭据保存在 MySQL `system_channel_config.credential_ciphertext`。新配置必须使用 `cryptography.fernet.Fernet.generate_key()` 生成的 URL-safe Base64 密钥，填入 `DATABASE__CHANNEL_CREDENTIAL_ENCRYPTION_KEY`。服务不会再把普通短语直接做一次 SHA-256 后当作密钥，也不会把解密失败伪装成空凭据。

已有密文的部署先备份数据库和旧密钥，并暂停所有会读写渠道配置的服务实例。把新密钥配置到 `DATABASE__CHANNEL_CREDENTIAL_ENCRYPTION_KEY`，把**旧密钥**只放在运行轮换脚本的进程环境变量 `CHANNEL_CREDENTIAL_LEGACY_KEY` 中；不要把它提交到仓库、写进命令参数或日志。脚本兼容旧版直接使用的 Fernet 密钥，以及旧版从短语做 SHA-256 派生的密钥。

在 `Agent_Server` 目录执行：

```powershell
uv run --no-sync python scripts/rotate_channel_credentials.py
uv run --no-sync python scripts/rotate_channel_credentials.py --apply
uv run --no-sync python scripts/rotate_channel_credentials.py
```

第一条只核对：全部非空密文必须能被新密钥或旧密钥解开，输出 `encrypted_rows`、`already_current`、`to_rotate` 计数。第二条在单个 MySQL 事务中更新经解密和新密钥回读验证的密文；任何一行失败即回滚。第三条应显示 `to_rotate: 0`，此时再启动服务并移除进程中的旧密钥。运行中不要并行启动使用旧密钥的服务，否则它无法读取已经轮换的记录。

若预检报某行两把密钥都无法解开，先查找该行历史密钥或从数据库备份恢复；不要清空、重置或覆盖密文。本机此次核查渠道配置表为 0 行，因此仅更换了本机 `.env` 中的弱密钥，无历史密文需要轮换。其他部署的数据量和旧密钥情况须各自预检，不应借用本机结果。

# Enterprise AI QA Agent 参考项目深度调研与系统增强路线图

> 调研日期：2026-08-17
> 调研对象：当前项目、`项目借鉴/llm-testing-course`、`项目借鉴/WHartTest`
> 证据范围：三个本地仓库的源码、配置、测试、文档与 Git 元数据。未把产品宣传文字直接当作已验证能力；涉及外部服务的端到端能力没有在本次调研中启动整套基础设施。

## 1. 结论先行

这三个项目不是同一赛道上的三个替代品，而是刚好覆盖企业 AI QA 平台的三个不同层面：

| 项目 | 本质定位 | 最强能力 | 当前短板 |
| --- | --- | --- | --- |
| 当前项目「御策天检」 | AI QA Agent 控制面与运行时 | 多 Agent 编排、能力注册、事件流、审批、中断恢复、回放、跨测试模式执行 | 缺少成熟的测试资产业务域、组织权限、评测数据集与质量门体系 |
| WHartTest | 测试管理与自动化执行平台 | 需求、用例、套件、接口资产、UI 资产、任务、执行历史、团队权限的完整业务闭环 | Agent 运行时的可观察粒度、恢复协议、统一跨模式控制面不如当前项目清晰；部署与业务模块较重 |
| llm-testing-course | 大模型测试方法论与课程资产库 | LLM/RAG/Agent/MCP/多模态/推理引擎/安全/评测科学/CI/CD/线上数据回流的知识覆盖 | 是纯静态课程站，不提供可运行平台、持久化模型、统一执行器或可验证测试包 |

最重要的战略判断是：

> 不要把当前系统改造成 WHartTest 的复刻，也不要把课程内容简单塞进知识库。正确方向是保留当前项目的 Agent 控制面，把 WHartTest 的“测试资产域与团队协作域”抽象为一等业务对象，再把课程中的“评测科学与数据闭环”实现为新的 Evaluation Plane。

理想目标架构可以概括为：

```text
llm-testing-course 贡献：评测标准、指标、数据治理、质量门、专项方法论
                              ↓
当前项目贡献：Agent 控制面、LangGraph 编排、权限审批、事件/SSE、快照/回放、产物
                              ↓
WHartTest 贡献：项目/需求/用例/套件/接口/UI/任务/执行记录/组织权限业务域
```

## 2. 调研方法与证据纪律

本次结论按以下优先级形成：

1. 直接读取可运行源码与配置。
2. 读取测试文件、迁移、路由和数据模型，确认能力不是只有页面或文档。
3. 读取 README/设计文档补充项目意图，但把“宣称能力”和“验证能力”分开。
4. 运行不修改业务数据的验证命令，记录真实结果。

本次主要事实盘点：

- 当前项目实际存在 14 个 mode 包、63 个 Skill 包、30 个 application 子包、15 个 API 路由文件；README 中“8 种模式、14 组路由”的描述已经滞后。
- 当前后端测试库存为 48 个 `test_*.py` 文件；使用正确导入路径后，本次实际结果为 `392 passed, 3 failed, 1 skipped, 2 errors`。
- WHartTest 是 v2.6.0 的完整 Monorepo，本地包含 25 个 Django 业务应用、10 个 Vue feature 域、Actuator、MCP、Skills、Docker Compose 与 57 个测试 Python 文件（已排除 migrations 中名称含 test 的文件）。
- llm-testing-course README 宣称 60+ 课时，本地实际有 65 个 HTML 内容页；页面结构检查全部通过，但没有独立可执行测试工程。

## 3. 三个项目的架构剖面

### 3.1 当前项目：Agent-first 的 QA 控制面

当前项目的核心不是“测试用例管理系统”，而是“能够驱动测试工作的 Agent Runtime”。README 明确把它定义为企业级多 Agent 编排工作台，后端采用 FastAPI + LangGraph，前端采用 Vue + Electron。

最有价值的架构资产包括：

1. **统一能力注册面**

   Agent、Tool、Model、Skill、MCP、Mode 六类能力都走 Registry。它让新增能力可以被发现、筛选、授权和按模式暴露，而不是直接写死在对话节点里。

2. **明确的执行状态机**

   `graph/builder.py` 把上下文构建、路由、规划、权限门、Prompt 组装、模型调用、工具执行、收尾和回复组成固定图。这个骨架比普通的“一个聊天接口 + 几个 function calling”更适合作为企业运行时。

3. **运行时可观测与可恢复**

   会话具有事件、快照、审批、tool job、artifact、interrupt/resume、replay。`execution_logging.py` 会给事件写入 turn/trace/correlation 信息并推入 SSE 队列；这是当前项目相对 WHartTest 最明显的优势。

4. **测试模式是编排单元，不只是菜单项**

   API、性能、安全、兼容性、冒烟、UI、代码评审等模式有独立的 manifest/runtime/contracts/tools/skills。性能模式已包含负载建模、k6/JMeter、目标保护、smoke 前置、结果分析和报告；安全模式有独立执行环境、目标约束、取证和复现包；兼容性模式有 runner 调度与产物上传。

5. **多种持久化介质各司其职**

   PostgreSQL 存会话运行时与向量记忆，MySQL 存配置，Memgraph 存知识/UI 图谱，Redis 做协调，MinIO 存产物。能力强，但基础设施复杂度也明显高于 WHartTest 的主数据库中心模式。

6. **UI Explorer 的事实源约束清晰**

   当前 UI Explorer 明确以 Playwright ARIA snapshot 为事实源，大模型负责策略与语义解释，页面结构不能靠模型猜。这种“模型不是事实源”的约束非常适合继续扩展到 API、RAG、评测和报告系统。

当前项目最适合的场景：

- 长时间、多步骤、跨工具的 QA Agent 任务。
- 需要人工审批、暂停、恢复、回放和审计的执行。
- 安全、性能、兼容性等存在执行风险或环境约束的专业测试。
- 需要多个 Worker Agent 分工并由 Coordinator 汇总的复杂任务。
- 需要把工具结果、截图、报告、复现包统一沉淀为 artifact 的任务。

当前项目的结构性缺口：

- 缺少 `Project → Requirement → TestCase → TestSuite → TestRun → Result → Defect` 的一等领域模型。
- 报告和会话很强，但测试用例本身、用例版本、套件、计划、环境、变量、接口定义等长期资产偏弱。
- 缺少 LLM Evaluation 的一等对象：EvalSet、EvalCase、Rubric、Judge、Baseline、Gate、Slice、Feedback。
- 缺少组织、成员、角色、项目级权限、API Key 与完整操作审计的产品闭环。
- README 与真实代码库存已出现漂移，说明能力目录需要自动生成或 CI 校验。
- 运行时基础设施较多，当前没有一个和 WHartTest `docker-compose.yml` 同等明确的整套部署入口。

### 3.2 WHartTest：Asset-first 的测试业务平台

WHartTest 的核心优势不是某一个 AI Agent，而是“测试团队每天会用到的业务对象已经基本齐全”。它用 Django/DRF 组织 25 个业务应用，Vue 前端按业务 feature 拆分，并通过 Celery、Channels、Actuator、MCP、Skills 和 Docker Compose 把执行链路补齐。

最有价值的架构资产包括：

1. **完整的测试资产生命周期**

   Django 路由和模型覆盖项目、需求、功能用例、用例模块、测试套件、执行、接口模块、接口定义、环境变量、全局 Header、数据库配置、自定义函数、接口用例、接口任务、同步历史和报告。这是当前项目最需要补齐的一层。

2. **需求到用例的业务闭环**

   需求文档不仅是上传附件，还具有解析、拆分、专项分析、评审状态、进度和版本化报告。它能把“AI 帮我测一下”转换为团队能维护、复用和追责的结构化资产。

3. **接口测试资产深度明显更高**

   WHartTest 不只执行一个临时 HTTP 请求，而是把接口、环境、变量、数据库检查、函数、标签、断言、前后置逻辑、用例组、任务和报告都建模。内置 httprunner 代码进一步说明它有真实执行核心，而不是只有 CRUD 页面。

4. **UI 自动化有独立执行器**

   Actuator 通过 WebSocket 与服务端通信，支持页面步骤、单用例、批量用例、停止执行，并回传步骤状态、截图和耗时。项目还包含视频、Trace、持久浏览器、文件上传下载等测试。这种“远程执行机”模型很适合被当前项目吸收为统一 Runner 协议的一种实现。

5. **企业协作面成熟**

   账户、组织、用户、权限、项目、API Key、操作日志、JWT、项目嵌套路由都已存在。对真正多人使用的测试平台而言，这部分业务价值往往比增加一个新的 Agent 更直接。

6. **知识库管理更接近产品功能**

   包含文档上传、分块、向量、BM25、Embedding、Reranker、检索和统计相关模块。当前项目的知识图谱与运行时记忆更强，而 WHartTest 的文档知识库产品化更完整，二者应互补。

7. **交付与部署更完整**

   根目录包含 Docker Compose、本地 Compose、安装脚本、Nginx 配置、多个 Dockerfile 和环境变量样例。对于用户试用与团队部署，WHartTest 的“从仓库到可用服务”路径更短。

WHartTest 最适合的场景：

- 测试团队集中管理需求、用例、套件、接口资产和执行历史。
- 需要组织、成员、权限、项目隔离和操作审计的多人协作。
- 需要稳定重复执行 API/UI 回归任务，而不是每次从自然语言重新规划。
- 需要独立执行机、定时任务、批量任务、截图/视频/Trace 回放。
- 需要把 AI 用例生成嵌入已有测试管理流程。

WHartTest 的结构性风险与限制：

- Django 业务应用很多，跨应用契约和迁移成本高；直接整体搬入当前 FastAPI 架构会形成双核心。
- Agent/LangGraph、MCP、Prompt、Skills、业务任务存在多套扩展入口，统一能力寻址不如当前项目的六大 Registry 清晰。
- Channels 默认配置仍写着内存通道层，只适合单进程开发；生产多实例需要 Redis Channel Layer。
- Settings 中保留开发默认密钥和默认 `DEBUG=True` 的路径，部署必须依赖环境校验避免误用。
- 其事件/任务日志更偏业务执行历史，缺少当前项目这种统一 turn/trace/correlation、节点级 SSE 和 replay 语义。
- 整套部署包含较多服务和重量级依赖，后续升级需要强版本治理。

### 3.3 llm-testing-course：Methodology-first 的评测知识平面

llm-testing-course 是纯静态 HTML/CSS/JS 课程站。它没有后端、数据库、runner 或统一 Python 包，但内容范围远超另外两个项目当前已经产品化的 AI 评测能力。

最有价值的知识资产包括：

1. **LLM Evaluation 科学**

   覆盖规则评分、传统指标、Embedding 指标、LLM-as-Judge、Judge 偏差、稳定性、一致性、Cohen's Kappa、人工对齐、Elo、Slice 评测和完整 Pipeline。当前项目虽有 verification/evaluation 组件，但没有如此完整的 Judge 校准体系。

2. **评测集治理与线上回流**

   课程明确提出线上 bad case 采集、脱敏、分类、通过标准、分层 EvalSet、样本生命周期、衰减淘汰、版本元数据、分布漂移和自动归因。这正是当前系统从“执行型 Agent”升级为“持续质量平台”的关键。

3. **质量门与 CI/CD**

   把 Prompt、模型、知识库、数据集和基线一起版本化，并在变更时触发自动评测、基线比较、门禁判定和通知。当前项目有任务与报告，但还没有稳定的“变更 → 评测 → Gate → 发布决策”协议。

4. **RAG 分层评测**

   课程不只看最终答案，而是拆成文档切分、Embedding、召回、Rerank、Prompt 拼接、生成、引用、拒答、权限穿透等层次，并提供 Golden Set 和 RAG Triad 思路。当前项目已有 pgvector、Memgraph、knowledge-rag，最适合把这一套直接实现为可运行评测模式。

5. **Agent/MCP 协议与轨迹鲁棒性**

   包含 Agent Card、JSON-RPC、流式事件、工具发现、参数校验、超时/重试、轨迹质量、循环检测、预算和协议异常。当前项目已经有 MCP 与 Agent Runtime，因此这些知识可以很快转化为自动化契约测试。

6. **覆盖新型 AI 测试对象**

   多模态、OCR/ASR、实时音视频、端侧模型、量化、推理引擎差异、解码稳定性、模型升级、幻觉、偏见、公平性、PII、合规备案等专题，可以补足当前模式目录的业务方法论。

7. **安全与红队的 LLM 专项深度**

   课程对 Prompt 注入、间接 RAG 注入、越狱、MCP 危险调用、Agent 越权、PII 泄露、安全基线和回归触发条件有系统化矩阵。当前项目安全模式更偏执行与取证，两者结合后可形成“传统应用安全 + LLM 应用安全”的双层体系。

llm-testing-course 最适合的场景：

- 为当前系统定义评测指标、数据模型、基线和质量门。
- 作为 Skill/知识库的内容来源和测试设计参考。
- 训练测试人员理解 LLM、RAG、Agent、MCP 和多模态的缺陷机理。
- 为新 mode 建立验收清单，而不是直接作为执行器。

课程项目的结构性限制：

- HTML 中的代码是教学片段，不是安装后可运行的统一包，不能直接视为已测试实现。
- 没有数据 schema、迁移、服务 API、队列、租户、权限、运行时状态或产物协议。
- 课程仓库没有发现 LICENSE 文件；在把大段内容或代码复制进产品前，需要先确认授权。更稳妥的方式是提炼方法论并自行实现。
- 部分行业数字和“最新协议”描述可能随时间变化；产品化前应按当前官方规范再校验。

## 5. 对当前系统最有价值的可迁移能力

### 5.1 从 WHartTest 借鉴：建立 QA 业务资产层

建议新增下列稳定领域对象，而不是继续把所有信息塞在 session metadata 或 artifact 中：

```text
Organization
└── Project
    ├── Requirement
    │   └── RequirementVersion
    ├── TestCase
    │   ├── TestCaseStep
    │   └── TestCaseVersion
    ├── TestSuite
    │   └── SuiteCaseBinding
    ├── TestEnvironment
    │   ├── VariableSet
    │   └── SecretReference
    ├── TestPlan
    ├── TestRun
    │   ├── TestCaseResult
    │   ├── StepResult
    │   └── ArtifactReference
    └── Defect / Finding
```

关键原则：

- Session 是“执行过程”，TestRun 是“业务记录”，二者不能混为一张表。
- Artifact 继续由当前 MinIO/ArtifactService 承载，业务表只保存引用与校验信息。
- Requirement/TestCase/TestSuite/TestRun 必须都带 `project_id`、版本、创建人和审计字段。
- Agent 可以生成和修改资产，但所有变更都应形成版本或审批记录。
- API/UI/性能/安全等 mode 都输出同一套 `TestRunResult` 外壳，专业字段放扩展 payload。

### 5.2 从课程借鉴：建立 Evaluation Plane

建议把以下对象做成新的正式领域：

```text
EvalDataset
├── dataset_version
├── level: smoke / regression / deep / redteam
├── slices
└── EvalCase[]

EvalCase
├── input
├── context
├── expected_behavior
├── reference_answer / evidence
├── tags / risk / source
└── privacy_state

EvalRubric
├── rubric_version
├── dimensions
├── deterministic_rules
└── judge_prompt

EvalRun
├── model_version
├── prompt_version
├── knowledge_version
├── tool_skill_versions
├── dataset_version
├── judge_version
├── results_by_slice
└── gate_decision
```

最低可用指标应覆盖：

- 功能：exact/contains/schema/contract/business-rule。
- RAG：Recall@K、MRR、Context Relevance、Faithfulness、Answer Relevance、Citation Correctness、拒答准确率。
- Agent：任务成功率、工具选择准确率、参数合法率、无效步骤率、循环率、重试率、预算超限率、轨迹一致性。
- 模型稳定性：多次运行一致率、温度敏感度、输出结构稳定率。
- 性能与成本：TTFT、总延迟、P50/P95/P99、tokens、单 case 成本、缓存命中率。
- 安全：攻击成功率、提示注入成功率、越权工具调用数、PII 泄露率。
- Judge 质量：与人工的一致率、Cohen's Kappa、重复打分方差、位置偏差、长度偏差。

### 5.3 合并两者：需求—用例—评测集—线上反馈闭环

目标数据流：

```text
需求文档
  → RequirementVersion
  → AI 需求评审
  → 生成/人工维护 TestCase
  → 组成 TestSuite / EvalDataset
  → Agent Runtime 执行 TestRun / EvalRun
  → Verification + Judge
  → Baseline Compare + Quality Gate
  → Report / Defect
  → 线上 Bad Case 回流
  → 脱敏、归因、人工确认
  → 新 EvalCase / 回归用例
```

这条链路一旦成立，当前系统就从“一次性完成测试任务”升级为“持续积累质量资产并阻断回归”的平台。

## 6. 推荐的目标架构

### 6.1 保留当前项目作为唯一控制面

以下模块应该继续以当前项目为准，不从 WHartTest 平移：

- Agent/Tool/Model/Skill/MCP/Mode Registry。
- LangGraph 执行图和权限门。
- Session/Event/Snapshot/Approval/Replay。
- ToolJob/Artifact/MinIO。
- Coordinator/Worker 调度。
- 模型 Provider 适配。
- 测试 mode 的专业运行时。

### 6.2 新增两个业务平面

1. **QA Asset Plane**

   管理 Project、Requirement、TestCase、TestSuite、Environment、TestPlan、TestRun、Defect。

2. **Evaluation Plane**

   管理 EvalDataset、EvalCase、Rubric、Judge、Baseline、EvalRun、QualityGate、Feedback。

这两个平面通过应用服务调用当前 Runtime，不应反向控制 LangGraph 内核。

### 6.3 建立统一 Runner 协议

从 WHartTest Actuator 和当前 Compatibility Runner 提炼统一协议：

```text
RunnerRegistration
RunnerCapability
TaskAssignment
Heartbeat
ProgressEvent
StepResult
ArtifactUpload
FinalResult
Cancel / Retry / Resume
```

Runner 类型可以包括：

- 本地进程 Runner。
- Docker Runner。
- 远程 UI Actuator。
- API/httprunner Runner。
- k6/JMeter Runner。
- 移动端设备 Runner。
- Browser/Playwright Runner。

所有 Runner 事件最终映射到当前统一 ExecutionEvent，所有文件映射到 ArtifactService。

### 6.4 知识层采用“双模型”而不是二选一

- 文档知识：参考 WHartTest，使用 Corpus/Document/Chunk/Embedding/Rerank 管理。
- 关系知识：保留当前 Memgraph 的 Page/Element/Entity/Observation 图谱。
- 运行记忆：保留当前 Session Memory/Observation。
- 评测知识：新增 EvalDataset/BadCase/Baseline，不要混在普通 RAG 文档中。

## 8. 不建议直接照搬的部分

1. **不要把 WHartTest Django 后端作为第二个主后端。**

   双后端会导致账户、项目、任务、权限、文件、日志、模型配置都有双数据源。应借鉴领域模型和交互流程，在当前 FastAPI/application 分层中重建稳定契约。

2. **不要直接复制课程 HTML 中的脚本当生产代码。**

   课程代码适合作为算法/验收参考，生产实现必须进入当前的 contracts、runtime、registry、tests 和 artifact 协议。

3. **不要把所有测试资产继续挂在 Session metadata。**

   Session 是运行时对象，会话删除、压缩或重放不能改变 TestCase/EvalCase 的业务身份。

4. **不要为每个 mode 自建一套任务、报告、Runner 和结果表。**

   统一外壳应是 TestPlan/TestRun/ExecutionEvent/Artifact/VerificationResult，mode 只扩展专业 payload。

5. **不要先做大而全的组织权限再做评测闭环。**

   对当前系统提升最大的是 P0 的测试资产与 Evaluation Plane；RBAC 可以在模型稳定后补齐。

这些问题不是本次调研的修复范围，但会影响后续增强的可信度：

## 12. 最终建议

如果只选一个近期主攻方向，优先做 **Evaluation Plane + 最小测试资产层**，而不是继续新增更多 mode。

原因是当前系统已经具备很强的“执行能力”，但还缺少回答下面三个企业级问题的统一数据模型：

1. 这次执行验证的是哪个版本的需求、用例、Prompt、模型、知识库和数据集？
2. 与上一个基线相比，究竟哪一个 Slice 退化了，是否应该阻断发布？
3. 线上出现的坏案例，是否已经脱敏、归因并沉淀进下一轮回归？

WHartTest 能补第一问的测试资产业务基础，llm-testing-course 能补第二、第三问的方法论，当前项目则是把三问真正运行起来并做到可观察、可审批、可恢复的最佳承载层。
